# 업무를 찾고 만들기

## 언제 찾고 만드는가

| 상황 | 할 일 |
| :--- | :--- |
| 코드·문서·설정을 바꾸는 요청 | **첫 수정 전에** 관련 업무를 찾고, 없으면 만든다 |
| 사용자가 참조를 줌(`ORM-14`) | 그 업무를 `get_work_item_context`로 읽고 시작한다([작업하는 동안](work.md)) |
| 작업 중 이번 요청과 다른 문제를 찾음 | 지금 고치든 아니든 따로 업무를 만든다. 지금 고쳤으면 그 업무에 결과를 남기고 닫는다(PR로 들어가면 [저장소 연동](repository.md)대로 병합에 맡긴다) |
| 질문, 설명, 코드 읽기만 | 만들지 않는다. 사용자가 원하면 만든다 |
| 같은 업무의 작은 후속 수정(오타, 한 줄) | 새 업무 없이 진행 중인 업무에 댓글로 남긴다 |

## 찾기

`list_work_items`에 `query`(제목 검색어)와 `project`를 주고, 끝난 일일 수도 있으면 `include_closed: true`도 준다. 같은 일을 다루는 업무가 있으면 새로 만들지 않고 그것을 쓴다.

## 만들기

1. **제목**은 무엇을 바꾸는지 한 줄로 쓴다(예: "로그인 실패 시 남은 시도 횟수 표시"). 원인이나 방법은 설명에 쓴다.
2. **설명**에는 요청과 배경, 다 됐다고 볼 기준을 짧게 쓴다. 버그는 현상, 재현 순서, 기대와 실제를 쓴다.
3. **속성**은 아래 표대로 정한다. 모르는 것만 묶어 한 번 묻는다.
4. 한 요청이 여러 커밋이나 여러 날에 걸치거나 유형(에픽·스토리 등)이 있는 서버면 [큰 일 나누기](split.md)를 따른다.
5. `create_work_item`으로 만든다. 받은 번호(`ORM-20`)는 그 뒤에야 브랜치·커밋에 쓴다.

## 속성 정하기

요청에서 알 수 있는 속성은 그대로 쓴다. 알 수 없는데 일정이나 담당에 영향을 주는 속성만, 추천값을 채워 **한 번에 묶어** 묻는다. 속성마다 따로 묻지 않는다.

| 속성 | 정하는 법 |
| :--- | :--- |
| 담당자 | 지금 이어서 작업할 업무면 `me`(API 키의 주인, 곧 이 에이전트에게 일을 맡긴 사람). 사용자가 다른 사람을 말하면 `list_members`로 확인해 넣는다 |
| 시작일 | 지금 시작하는 일이면 오늘(사용자 시간대의 날짜)을 추천한다 |
| 기한 | 사용자가 말한 날. 말하지 않았으면 물을 목록에 넣고, 추천값은 '비움'이다 |
| 우선순위 | 사용자가 말한 것. 다른 일을 막는 버그면 `high`를 추천하고, 그 밖에는 `medium` |
| 라벨 | `list_labels`에 있는 것 중 맞는 것. 없는 라벨은 지어내지 않는다. 필요해 보이면 만들지 물을 목록에 넣는다 |
| 유형·상위 | 업무 유형이 있는 서버면 [큰 일 나누기](split.md)를 따른다 |
| 상태 | 주지 않으면 첫 '할 일' 칸이다. 나중으로 미뤄 두는 업무만 `backlog`로 만든다 |

묻는 법:
- 추천값을 채운 한 문장으로 묻는다. 예: "이렇게 만들까요? 담당 나, 시작 오늘(10/28), 기한 없음, 우선순위 보통, 라벨 '버그'." 사용자는 "네"라고 하거나 고칠 것만 말하면 된다.
- 객관식 질문 도구가 있으면 '추천값대로'와 '고쳐서' 같은 선택지로 묻는다.
- 묻지 않는 때:
  - 사용자가 이미 다 말했을 때
  - "알아서 해"라고 맡겼을 때. 추천값으로 만들고 무엇을 넣었는지 한 줄로 알린다
  - 작업 중 찾은 문제를 나중으로 미뤄 두는 업무일 때. 담당자·날짜를 비워 둔다
  - 프로젝트 지침에 기본값이 적혀 있을 때
- 사용자가 "앞으로도 이렇게"라고 하면, 기본값을 프로젝트 지침에 한 줄 적자고 제안한다. 그다음부터는 묻지 않는다.

```markdown
- BIT 업무 기본값: 지금 맡는 일은 담당 me·시작 오늘·기한 없음·우선순위 보통. 미뤄 두는 일은 모두 비움.
```
