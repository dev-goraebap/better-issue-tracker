# 작업하는 동안

1. **시작:** `get_work_item_context`로 설명과 댓글, 활동을 읽는다. 앞선 사람이나 에이전트가 남긴 결정과 막힌 점이 거기 있다. 그다음 `move_work_item`으로 '진행 중'에 옮긴다. 담당자가 비어 있으면 `update_work_item`으로 `assignee: "me"`를 넣는다. 시작일이 비어 있으면 [업무 만들기](create.md)의 속성 정하기대로 오늘을 넣는다. 다른 사람이 맡고 있으면 바꾸지 않고 사용자에게 알린다.
2. **앞선 결정 읽기:** 이 업무와 상위 업무(에픽)의 '결정' 댓글을 읽고 따른다. 같은 영역의 다른 업무를 찾았으면 그 업무의 댓글도 읽는다. 저장소가 따로 결정 기록 파일을 두면 그것도 읽는다. 결정과 어긋나게 해야 하면 바꾸기 전에 사용자에게 말한다.
3. **진행 댓글:** 의미 있는 단계마다 `add_comment`로 남긴다. 무엇을 했고, 무엇을 알게 됐고, 무엇이 남았는지를 쓴다. 도구를 부를 때마다 남기지 않는다. 한 작업에 보통 2~4개면 충분하다.
4. **결과 댓글:** 커밋했으면 커밋 해시와 한 줄 요약, 실행한 검증(테스트, 직접 확인)과 하지 못한 검증을 남긴다. 커밋하지 않았으면 그렇다고 쓴다. 예는 [쓰는 말](../references/writing.md)에 있다.
5. **연결된 문서 확인:** `list_relations`로 이 업무와 이어진 문서를 본다. 이번 작업이 그 문서가 설명하는 동작을 바꿨으면 문서를 고치거나, 지금 못 고치면 후속 업무를 만든다([문서 만들고 고치기](document.md)).
6. **닫기:** 작업이 끝나고 검증까지 됐으면 '완료'로 옮긴다. 하지 않기로 한 일은 까닭을 댓글로 남기고 '취소'로 옮긴다(닫히되 완료로 세지 않는다). 사용자 확인이 필요한 일(배포, 화면 확인)이 남았으면 진행 중으로 두고 남은 것을 댓글에 쓴다. 저장소와 연결된 프로젝트에서 PR로 들어가는 작업은 직접 옮기지 않고 병합에 맡긴다([저장소 연동](repository.md)).

## 결정

앞으로 다른 작업이 따라야 할 선택(규칙, 방식, 제약)을 하거나 전에 정한 것을 바꾸면, 그 선택이 나온 업무에 `## 결정: <한 줄 요약>`으로 시작하는 댓글을 하나 남긴다. 따로 업무나 문서를 만들지 않는다. 결정을 따로 두면 같은 일이 두 장이 되고, 결정이 그 일과 떨어져 찾기 어려워진다.

| 경우 | 남기는 곳 |
| :--- | :--- |
| 여러 안 중 하나를 골랐고, 이후 작업이 그것을 따라야 함 | '결정' 댓글 |
| 전에 정한 것이나 지켜 오던 동작을 바꾸거나 뒤집음 | '결정' 댓글. 맥락에 바꾸는 결정이 있는 업무 참조를 적는다 |
| 이번 작업에서만 쓰고 끝나는 선택, 새 기능을 더하는 것 자체, 오타·단순 수정 | 평범한 진행 댓글 |

- **결정한 순간에 쓴다.** 작업이 끝난 뒤 되짚어 쓰면 검토한 대안 같은 맥락이 사라진다.
- **세 부분만 쓴다.** 맥락과 결정은 각각 몇 문장이다. 검토한 대안은 실제로 따져 본 안이 있을 때만 쓴다. 지어내지 않는다. 구현 절차와 테스트 기록은 결과 댓글에 둔다.
- **남긴 결정은 고치지 않는다.** 바뀌면 새 '결정' 댓글을 단다.
- **저장소에 따로 결정 기록이 있으면**(예: `docs/decisions.md`) 그 저장소의 규칙도 따른다.

```markdown
## 결정: 외부 결제 호출의 재시도 규칙

**맥락.** 결제 실패를 고치다가(PAY-12) 실패한 호출을 언제 다시 시도할지 정해야 했다. 결제 대행사는 1분에 10회를 넘는 호출을 막는다.

**결정.** 외부 결제 호출은 모두 지수 백오프로 세 번까지 다시 시도하고, 그래도 실패하면 수동 처리 대기열에 넣는다.

**검토한 대안.** 고정 간격 5회(대행사 호출 한도에 걸린다).
```
