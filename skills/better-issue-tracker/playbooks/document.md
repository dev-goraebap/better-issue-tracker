# 문서 만들고 고치기

문서는 요구사항·설계·기획·회의록·설명서처럼 **오래 두고 고쳐 가며 보는 글**이다. 업무는 일이 끝나면 닫히고 결정기록은 대체될 때까지 그대로지만, 문서는 제품이 바뀌면 같이 바뀐다. 문서 도구가 없는 서버면 긴 글은 업무 설명에 쓴다([도구](../references/tools.md)).

## 어디에 쓰나

| 글 | 쓰는 곳 |
| :--- | :--- |
| 이번 일의 요청·배경·완료 기준, 진행과 결과 | 업무 설명과 댓글 |
| 앞으로 다른 작업이 따라야 할 선택 | 결정기록([결정기록](decision.md)) |
| 제품이나 기능이 어떻게 생겼고 어떻게 쓰는지, 오래 두고 고칠 글 | 문서 |
| 회의에서 나온 것 | 회의록 문서. 거기서 나온 할 일은 업무로, 선택은 결정기록으로 따로 만든다 |

같은 내용을 두 곳에 쓰지 않는다. 문서가 결정을 설명해야 하면 결정기록 참조(`ORM-31`)를 적고 내용은 옮겨 적지 않는다. 원본이 둘이면 하나는 낡는다.

## 만들고 고치는 때

- 사용자가 설명서·설계·회의록을 부탁할 때 만든다.
- 업무를 닫을 때, 연결된 문서가 이번에 바뀐 동작을 설명하면 고친다. 지금 고칠 수 없으면 후속 업무를 만든다([작업하는 동안](work.md)).
- 문서의 '문서 기준' 이후 그 코드가 바뀌었으면 다시 본다(아래 '낡은 문서 찾기').

## 쓰는 순서

1. **업무를 만든다.** 문서 쓰기도 일이다. 쓰는 동안의 진행과 팩트 시트는 그 업무에 남는다([업무 만들기](create.md)).
2. **유형을 고른다.** 제품설명서·사용자설명서·인수인계면 [문서 유형](../references/document-types.md)의 프로필을 따른다. 그 밖이면 프로필 없이 독자와 질문부터 정한다.
3. **독자 한 명을 정한다.** 누가 무엇을 하려고 읽는지 한두 문장으로 쓴다. 무엇을 설명하고 무엇을 생략할지는 이 문장으로 정한다.
4. **팩트 시트를 먼저 만든다.** 문장을 쓰기 전에, 독자가 답을 얻어야 할 질문마다 확인한 사실을 출처와 함께 모은다. 출처는 코드(`경로:줄`), 실행한 화면이나 명령의 결과, 결정기록 참조, 사용자의 답이다. 문서와 코드가 어긋나면 코드를 믿고 어긋난 것을 적는다. 기능이 있다는 것만 적지 말고 **기본값과 조건**(기본으로 켜져 있나, 언제만 일어나나, 무엇이 빠지나)까지 확인한다. 이 부분이 가장 자주 틀린다. 팩트 시트는 문서 업무의 댓글로 남긴다.
5. **팩트 시트에 있는 것만 쓴다.** 확인하지 못한 것은 쓰지 않거나 "확인하지 못함"이라고 쓴다. 빈자리를 수식어로 메우지 않는다. 쓰는 말은 [쓰는 말](../references/writing.md)을 따른다.
6. **'문서 기준' 블록을 끝에 둔다.** 형식은 아래와 같다.
7. **다른 눈으로 대조한다.** 하위 에이전트를 띄울 수 있으면, 문서를 쓰지 않은 에이전트에게 문서와 저장소만 주고 주장을 하나씩 맞음·틀림·근거 없음·부분으로 대조하게 한다. 빠진 것과 헷갈리는 문장도 묻는다. 결과로 고치고, 대조 결과는 문서 업무에 댓글로 남긴다. 띄울 수 없으면 스스로 숫자·목록·'아직 없다'는 주장부터 다시 확인한다.
8. **올리고 잇는다.** `create_document`(또는 `update_document`)로 프로젝트의 폴더에 둔다. 폴더는 프로젝트 지침이나 문서 지도를 따르고, 없으면 유형별 폴더(`제품`, `설계`, `회의록`)에 둔다. `link_document`로 문서 업무와, 문서가 설명하는 기능의 업무와 잇는다.

## '문서 기준' 블록

문서가 무엇을 근거로 언제 쓰였는지 적는다. 이 형식을 그대로 쓴다. 나중에 사람·에이전트·서버가 이 블록으로 낡은 문서를 찾는다.

```markdown
## 문서 기준

- 기준 커밋: `a1b2c3d` (2026-10-30)
- 설명하는 코드: `server/src/main/java/.../workitem/`, `client/src/pages/workspace/work-items/`
- 근거: ORM-31(결정기록), ORM-40(문서 업무의 팩트 시트)
```

- 기준 커밋은 사실을 모은 때의 커밋이다. 저장소가 없는 프로젝트면 날짜만 쓴다.
- 설명하는 코드는 문서가 설명하는 동작이 사는 경로(폴더나 파일)를 쓴다. 다섯 개 안팎이면 충분하다.

## 낡은 문서 찾기

문서를 고치기 전이나 업무를 닫을 때, 기준 커밋 이후 설명하는 코드가 바뀌었는지 본다.

```bash
git diff --name-only <기준 커밋>..HEAD -- <설명하는 코드 경로들>
```

출력이 있으면 그 파일이 바꾼 동작을 문서와 대조해 고치고, 기준 커밋을 지금 커밋으로 바꾼다. 출력이 없으면 기준을 바꾸지 않는다.
