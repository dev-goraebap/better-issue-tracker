# 문서 만들고 고치기

문서는 요구사항·설계·기획·회의록·설명서처럼 **오래 두고 고쳐 가며 보는 글**이다. 업무는 일이 끝나면 닫히지만, 문서는 제품이 바뀌면 같이 바뀐다. 문서 도구가 없는 서버면 긴 글은 업무 설명에 쓴다([도구](../references/tools.md)).

## 어디에 쓰나

| 글 | 쓰는 곳 |
| :--- | :--- |
| 이번 일의 요청·배경·완료 기준, 진행과 결과 | 업무 설명과 댓글 |
| 앞으로 다른 작업이 따라야 할 선택 | 그 선택이 나온 업무의 '결정' 댓글([작업하는 동안](work.md)) |
| 제품이나 기능이 어떻게 생겼고 어떻게 쓰는지, 오래 두고 고칠 글 | 문서 |
| 회의에서 나온 것 | 회의록 문서. 거기서 나온 할 일은 업무로 만들고, 선택은 그 일을 다루는 업무에 '결정' 댓글로 남긴다 |

같은 내용을 두 곳에 쓰지 않는다. 문서가 결정을 설명해야 하면 결정이 있는 업무의 참조(`ORM-31`)를 적고 내용은 옮겨 적지 않는다. 원본이 둘이면 하나는 낡는다.

## 매뉴얼로 작성할 때

사용자가 매뉴얼 기능을 선택했고 서버에 `list_manuals`가 있으면, 사용자 설명서·개발 지침은 매뉴얼에 작성한다. 기존 문서/HTML 페이지를 자동으로 옮기거나 기존 자료를 덮어쓰지 않는다. 기능 도구가 없는 서버에서는 기능이 생긴 것처럼 쓰지 않는다.

1. `list_manuals`에서 공간·프로젝트를 확인하고 `get_manual`로 기존 책을 읽거나 `create_manual`로 새 책을 만든다. 프로젝트를 생략한 생성은 워크스페이스 공통이다.
2. 섹션은 `create_manual_section`/`update_manual_section`, 페이지는 `create_manual_page`/`update_manual_page`로 작성한다. 쓸 때마다 최신 응답의 version을 expected_version으로 준다. 409이면 최신 내용을 읽고 내 변경과 합치며 자동 덮어쓰지 않는다.
3. 이미지 원본은 기존 REST 파일 업로드로 보낸다. 페이지의 Markdown `attachment:id`와 upload_ids를 함께 주어 확정한다. 원본 크기를 유지하며 서버의 파일 용량·형식 제한을 따른다. 다른 문서의 첨부 ID를 그대로 가져다 쓰지 않는다.
4. `reorder_manual`은 모든 섹션/페이지 ID를 한 번씩 주고 페이지별 소속을 맞춘다. 개선 의견은 add_manual_comment, 해결/재열기는 resolve_manual_comment를 사용한다.
5. 저장한 책을 화면에서 다시 읽어 탐색·본문·목차·이미지와 내보내기를 확인한다. 아래 실제 사용·촬영·팩트 시트 기준도 그대로 적용한다. 작업 결과와 기준 커밋은 관련 업무에 남긴다.

## 만들고 고치는 때

- 사용자가 설명서·설계·회의록을 부탁할 때 만든다.
- 매뉴얼 사용 프로젝트의 기능 변경은 [매뉴얼 유지관리](../references/manual-maintenance.md)에 따라 별도 작성 요청 없이 관련 페이지도 갱신한다. 이 규칙은 매뉴얼 미사용 프로젝트에 새 책을 만드는 지시가 아니다.
- 업무를 닫을 때, 연결된 문서가 이번에 바뀐 동작을 설명하면 고친다. 지금 고칠 수 없으면 후속 업무를 만든다([작업하는 동안](work.md)).
- 문서의 '문서 기준' 이후 그 코드가 바뀌었으면 다시 본다(아래 '낡은 문서 찾기').

## 쓰는 순서

1. **업무를 만든다.** 문서 쓰기도 일이다. 쓰는 동안의 진행과 팩트 시트는 그 업무에 남는다([업무 만들기](create.md)).
2. **유형을 고른다.** 제품 사용법을 부탁받으면 [문서 유형](../references/document-types.md)의 사용자 가이드 프로필을 따른다. 도입을 설득하는 제품 소개로 바꾸지 않는다. 구조·코드 스타일·협업·배포 지침은 같은 파일의 개발 매뉴얼 프로필과 [개발 매뉴얼 작성](../references/development-manual.md)을 따른다. 인수인계도 문서 유형의 프로필을 따른다. 그 밖이면 독자와 질문부터 정한다.
3. **독자와 제품 맥락을 정한다.** 누가 무엇을 하려고 읽는지 한두 문장으로 쓴다. 사용자 가이드는 [매뉴얼 작성과 대조](../references/manual-authoring.md)에 따라 제품의 목적·용어/관계·역할·대표 업무 흐름을 먼저 확인한다. 기존 제품 문서·현재 구현·실제 화면을 근거로 하며 업계 관행을 제품 기능으로 추정하지 않는다. 맥락은 팩트 시트에 남기고 독자에게 필요한 개념만 본문에 쓴다.
4. **팩트 시트를 먼저 만든다.** 문장을 쓰기 전에, 독자가 답을 얻어야 할 질문마다 확인한 사실을 출처와 함께 모은다. 출처는 코드(`경로:줄`), 실행한 화면이나 명령의 결과, '결정' 댓글이 있는 업무 참조, 사용자의 답이다. 문서와 코드가 어긋나면 코드를 믿고 어긋난 것을 적는다. 기능이 있다는 것만 적지 말고 **기본값과 조건**(기본으로 켜져 있나, 언제만 일어나나, 무엇이 빠지나)까지 확인한다. 이 부분이 가장 자주 틀린다. 팩트 시트는 문서 업무의 댓글로 남긴다.
5. **가이드라면 대표 작업부터 조작하고 촬영한다.** 입력 항목·조건·오류/차단 상태와 진입·중요한 선택·완료 결과를 먼저 대조표로 정한다([매뉴얼 작성과 대조](../references/manual-authoring.md)). 시험 계정으로 끝까지 따라 하고 사진과 본문 단계를 연결한다. 새 매뉴얼이나 설명 깊이·사진 배치를 바꾸는 작업은 대표 페이지를 먼저 완성해 사용자 검토를 받은 뒤 전체에 적용한다. 사용자가 이미 대표 양식을 승인했거나 일괄 작성을 명시했다면 재승인을 요구하지 않는다. 화면을 사용할 수 없으면 사진 자리나 합성 화면을 넣지 않고 미검증 범위를 밝힌다. 촬영·묶음 기준은 [문서 유형](../references/document-types.md)을 따른다.
6. **팩트 시트에 있는 것만 쓴다.** 확인하지 못한 것은 쓰지 않거나 "확인하지 못함"이라고 쓴다. 빈자리를 수식어로 메우지 않는다. 쓰는 말은 [쓰는 말](../references/writing.md)을 따른다.
7. **'문서 기준' 블록을 끝에 둔다.** 형식은 아래와 같다. 밖으로 나가는 글(기획팀, 고객에게 주는 문서)이면 본문에 두지 않고 문서 업무의 댓글에 남긴다([문서 유형](../references/document-types.md)).
8. **주장과 빠진 단계를 대조한다.** 본문의 주장뿐 아니라 팩트 시트의 입력·오류·촬영 항목이 어디에 설명됐는지도 역으로 확인한다. 페이지·사진 개수가 아니라 독자가 작업을 끝내고 오류에서 회복할 수 있는지로 판단한다. 별도 에이전트 검토가 허용된 환경이면 문서를 쓰지 않은 에이전트에게 문서와 근거를 주어 맞음·틀림·근거 없음·부분 및 누락을 대조하게 한다. 그렇지 않으면 스스로 대조한다. 결과와 미검증 범위는 문서 업무에 남긴다.
9. **올리고 잇는다.** 매뉴얼을 선택했으면 위 매뉴얼 도구로 저장하고 책/페이지 링크를 업무에 남긴다. 그 밖의 마크다운은 `create_document`(또는 `update_document`), HTML·사진 묶음은 purpose `page`로 업로드한 뒤 `create_page`(또는 `update_page`)로 올린다. 폴더는 프로젝트 지침이나 문서 지도를 따른다. 문서는 `link_document`로 문서 업무와 설명하는 기능의 업무에 잇는다.

## 완료 기준

- 가이드에 있는 절마다 실제 진입 위치·사용 단계·완료 결과를 확인했다.
- 스크린샷의 예제·화면 이름과 본문이 일치하고, 비밀값·개인정보·사진 자리 표시가 없다.
- 제품 용어·역할·업무 흐름의 근거가 있고, 적용되는 입력 조건·오류/차단 상태·필요한 사진을 항목별로 본문과 대조했다. 적용되지 않거나 미확인인 항목은 구분했다.
- HTML 페이지의 상대 경로 사진과 인쇄 CSS를 확인했다. PDF 저장 동작은 BIT가 제공하며, 결과물 안에 별도 인쇄 버튼을 만들지 않았다.
- 확인하지 못한 기능과 촬영 범위를 업무에 기록했다.

## '문서 기준' 블록

문서가 무엇을 근거로 언제 쓰였는지 적는다. 이 형식을 그대로 쓴다. 나중에 사람·에이전트·서버가 이 블록으로 낡은 문서를 찾는다.

```markdown
## 문서 기준

- 기준 커밋: `a1b2c3d` (2026-10-30)
- 설명하는 코드: `server/src/main/java/.../workitem/`, `client/src/pages/workspace/work-items/`
- 근거: ORM-31(결정 댓글), ORM-40(문서 업무의 팩트 시트)
```

- 기준 커밋은 사실을 모은 때의 커밋이다. 저장소가 없는 프로젝트면 날짜만 쓴다.
- 설명하는 코드는 문서가 설명하는 동작이 사는 경로(폴더나 파일)를 쓴다. 다섯 개 안팎이면 충분하다.

## 낡은 문서 찾기

문서를 고치기 전이나 업무를 닫을 때, 기준 커밋 이후 설명하는 코드가 바뀌었는지 본다.

```bash
git diff --name-only <기준 커밋>..HEAD -- <설명하는 코드 경로들>
```

출력이 있으면 그 파일이 바꾼 동작을 문서와 대조해 고치고, 기준 커밋을 지금 커밋으로 바꾼다. 출력이 없으면 기준을 바꾸지 않는다.
