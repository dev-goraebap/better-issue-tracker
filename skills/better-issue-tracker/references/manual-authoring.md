# 매뉴얼 작성과 대조

[문서 만들고 고치기](../playbooks/document.md)의 사용자 가이드 작업에 사용한다. 아래 표는 작성·검수 자료다. 고객 본문에 조사표나 검증 기록을 그대로 넣지 않는다.

## 제품을 먼저 이해하기

기능 목록을 목차로 옮기기 전에 다음 질문에 근거를 붙인다. 이미 확인된 제품 자료는 재사용하고 변경된 영역만 대조한다. 전체 산업 조사나 모든 코드 읽기를 선행 조건으로 만들지 않는다.

| 파악할 것 | 확인할 질문 |
| --- | --- |
| 사용자와 목적 | 누가 어떤 상황에서 어떤 결과를 얻으려고 쓰는가? |
| 용어와 관계 | 화면의 핵심 개념은 무엇이며 서로 어떻게 연결되는가? 비슷한 용어는 어떻게 다른가? |
| 역할과 범위 | 누가 어느 공간의 자료를 보고 만들고 바꿀 수 있는가? |
| 대표 흐름 | 진입 → 선행 작업 → 주요 선택 → 저장/실행 → 결과와 다음 작업은 무엇인가? |
| 상태와 경계 | 상태가 바뀌면 가능한 행동이 어떻게 달라지는가? 외부 설정·미구현·이번 설명 밖인 것은 무엇인가? |

프로젝트 문서·결정·현재 UI/API/도메인 검증과 실제 조작을 대조한다. 업계에서 보통 한다는 이유로 승인 절차·법적 효력·권한·자동화를 지어내지 않는다. 산업 전문 지식이 필요하면 확인된 자료를 인용하고, 사용자에게 물어야 할 미확정 사항을 분리한다. 충돌은 조용히 한쪽을 선택하지 말고 차이와 확인 범위를 업무에 남긴다.

팩트 시트에는 `질문 | 확인 사실 | 근거 | 미확인/불일치`를 남긴다. 제품의 모든 개념을 설명하는 대신, 해당 페이지의 작업에 필요한 개념만 짧게 소개하거나 관련 개념 페이지로 연결한다.

## 작업별 대조표

### 입력과 실행 조건

폼의 실제 항목을 하나씩 대조한다. 화면에서 입력할 수 없는 서버 필드는 사용자 옵션처럼 설명하지 않는다.

| 항목/행동 | 필수·선택/기본값 | 길이·범위·형식 | 다른 항목·권한·상태 조건 | 화면 동작과 근거 | 본문 위치 |
| --- | --- | --- | --- | --- | --- |
| 실제 필드 또는 실행 버튼 | 확인된 값 | 적용되는 제한만 | 해당 조건 또는 해당 없음 | 실제 조작과 구현 | 절/단계 |

첨부가 있으면 형식·개별/전체 용량·개수도 확인한다. 제한이 없다는 주장은 추측하지 않는다. UI에서 확인하지 못한 구현 한도는 그렇게 구분한다. 작은 범위의 조작으로 확인 가능한 경계와 오류를 우선 재현하고 운영에 과부하를 주는 한도 실험은 하지 않는다.

### 오류에서 회복하기

| 실제 메시지 또는 화면 상태 | 발생 조건 | 사용자가 할 행동 | 확인 근거 | 본문 위치 |
| --- | --- | --- | --- | --- |
| 관찰한 문구 또는 ‘저장 버튼 비활성’ 등 | 실제 입력·권한·상태 | 수정할 값/선행 작업/문의 대상 | 화면·응답·구현 | 막힐 때/관련 단계 |

입력 제한으로 애초에 들어가지 않는 값, 버튼 비활성, 제출 후 필드 안내, 서버 실패를 구분한다. 차단되는데 오류 메시지가 뜬다고 쓰지 않는다. 코드에만 있는 메시지를 실제 화면 문구로 인용하지 않는다. 화면과 구현이 다르면 실제 경험을 설명하고 불일치는 업무에 남긴다.

### 단계와 사진

| 작업 단계 | 필요한 화면 상태/보여줄 대상 | 사진 필요 이유 또는 생략 이유 | 캡처 파일 | 본문 단계/설명 | 확인 결과 |
| --- | --- | --- | --- | --- | --- |
| 진입·중요한 선택·입력·저장·완료 중 하나 | 메뉴/선택 창/결과 등 | 위치나 결과를 이해하는 데 필요한가? | 원본 경로 또는 촬영 못함 | 사진 바로 아래 행동·확인 결과 | 확인/미확인 |

모든 클릭을 촬영하지 않는다. 핵심 선택 창이나 완료 결과를 설명하는데 그 상태가 빠진 경우를 잡는다. 저장한 캡처 파일도 직접 열어 원하는 값·메뉴·오류가 찍혔는지 대조한다. 엉뚱한 전체 화면 한 장으로 여러 단계를 촬영했다고 세지 않는다. 원본 보존·테마·예제·사진 처리 기준은 [문서 유형](document-types.md)의 촬영 규칙을 따른다.

## 페이지 유형별 구성

| 페이지 | 구성 예 | 생략해도 되는 것 |
| --- | --- | --- |
| 조작/따라 하기 | 목적·시작 위치·준비 → 번호 단계와 필요한 사진 → 입력 조건 → 완료 확인 → 막힐 때 → 다음 작업 | 없는 첨부·오류의 가상 사례 |
| 조회/찾기 | 어떤 정보를 찾는지 → 진입 → 검색/필터·상태 해석 → 원하는 항목을 연 결과 → 결과가 없거나 접근 불가일 때 | 입력 폼이 없으면 저장 단계·필수 입력표 |
| 참고 | 조회할 값/조건 → 항목별 같은 형식의 표 → 예외·관련 작업 링크 | 모든 항목의 스크린샷·번호 단계 |
| 개념/설명 | 용어의 뜻 → 관계·범위 → 예시 → 관련 조작 페이지 | 형식적인 ‘준비물’·‘저장 후’ |

길고 드문 제약은 참고 절/페이지로 분리하고 현재 단계에는 선택에 필요한 조건만 둔다. 표는 목적이 있을 때 쓰며 같은 제한을 여러 페이지에 복제하지 않는다.

## 조작 페이지 예시

다음은 BIT의 ‘프로젝트 만들기’ 본문 예다. 수치와 문구는 이 제품의 확인된 계약을 설명하는 예시이며 다른 제품의 기본값이 아니다. 실제 전달본의 사진과 근거는 해당 프로젝트에서 직접 확보한다. 아래는 문장·구성 예시이므로 촬영하지 않은 사진이나 임시 attachment ID를 넣지 않았다.

> # 프로젝트 만들기
>
> 같은 목표의 이슈와 자료를 한곳에서 관리하려면 프로젝트를 만듭니다. 프로젝트 키는 업무 번호 앞에 붙습니다. 예를 들어 키가 WEB이면 첫 업무 번호는 WEB-1입니다.
>
> ## 시작하기 전에
>
> 작업할 워크스페이스를 선택합니다. 프로젝트 생성에는 워크스페이스 설정을 수정할 권한이 필요합니다.
>
> ## 만들기
>
> 1. 왼쪽 메뉴에서 ‘프로젝트’를 엽니다.
> 2. 상단의 ‘프로젝트 만들기’를 누릅니다.
> 3. ‘프로젝트 이름’에 ‘고객 포털’을 입력합니다.
> 4. ‘프로젝트 키’에 WEB을 입력합니다. 한글 이름만 입력했다면 키는 직접 적습니다.
> 5. 필요하면 설명과 아이콘·색을 정합니다.
> 6. ‘프로젝트 만들기’를 누릅니다.
>
> 생성되면 새 프로젝트의 이슈 화면으로 이동합니다. 사이드바 상단에 ‘고객 포털’이 표시되는지 확인합니다.
>
> ## 입력 조건
>
> | 항목 | 조건 |
> | --- | --- |
> | 프로젝트 이름 | 필수, 공백만 입력할 수 없으며 최대64자 |
> | 프로젝트 키 | 필수, 영문 대문자·숫자2~10자. 같은 워크스페이스에서 현재 또는 과거에 쓴 키는 다시 쓸 수 없음 |
> | 설명 | 선택, 최대20,000자 |
>
> ## 만들 수 없을 때
>
> | 보이는 안내 | 해결 방법 |
> | --- | --- |
> | ‘프로젝트 이름을 입력해 주세요.’ | 이름을 입력한 뒤 다시 만듭니다. |
> | ‘키는 영문 대문자·숫자 2~10자로 적어 주세요.’ | 한글·기호를 빼고2~10자의 키를 입력합니다. |
> | ‘이 워크스페이스에서 이미 쓴 키입니다.’ | 새 키를 입력합니다. 예전 프로젝트가 쓰던 키도 재사용할 수 없습니다. |

실제 대표 페이지에는 진입 위치, 입력한 생성 창, 재현한 중요 오류, 생성 후 화면을 설명과 함께 배치한다. 한 사진으로 충분히 설명되는 단계는 함께 참조해도 된다. 이 예만 복사해 촬영·입력 조건 조사를 완료했다고 하지 않는다.

## 대표 페이지와 최종 대조

새 매뉴얼은 입력과 오류가 있는 대표 작업을 실제 페이지로 완성한다. 사용자가 설명 깊이·사진 배치를 검토한 뒤 나머지에 적용한다. 이미 승인된 양식/일괄 작성 요청은 재승인 대상이 아니다. 제품에 입력 폼이 없다면 검색과 결과 해석 등 실제 대표 흐름을 고른다.

작성 뒤에는 본문에서 근거로 가는 확인과, 입력·오류·사진 대조표에서 본문으로 돌아오는 누락 확인을 모두 한다. 독자가 결과에 도달하고 예상 오류에서 회복하는지 따라 해 본다. 완료한 페이지와 미작성 목차, 화면/API만 확인한 범위, 촬영/인쇄하지 못한 범위를 업무에 구분한다. 사진 장수·페이지 수·이미지 로드 성공만으로 전체 매뉴얼을 검수 완료라고 하지 않는다.
