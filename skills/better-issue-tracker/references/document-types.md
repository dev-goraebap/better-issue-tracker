# 문서 유형

[문서 만들고 고치기](../playbooks/document.md)에서 고르는 유형의 프로필이다. 같은 유형이면 매번 같은 구성으로 쓴다. 독자는 기본값이고, 사용자가 다른 독자를 말하면 그것을 따른다.

## 글의 종류는 넷이고, 한 문서는 하나만 맡는다

독자가 문서를 여는 이유는 넷 중 하나다. 한 문서에 둘을 섞으면 어느 독자에게도 맞지 않는다. 섞어야 할 것 같으면 문서를 나누고 서로 링크한다.

| 종류 | 독자가 여는 이유 | 담는 것 | 담지 않는 것 |
| :--- | :--- | :--- | :--- |
| 따라 하기 | 처음 써 보며 배우려고 | 처음부터 끝까지 되는 예 하나, 중간중간 잘 되고 있다는 확인 | 여러 갈래의 선택지, 모든 옵션 |
| 하는 법 | 이미 알고, 일 하나를 끝내려고 | 준비할 것, 번호 단계, 결과 확인, 막힐 때 | 내부 동작 설명, 기초 개념 |
| 참고 | 값 하나를 찾으려고 | 빠짐없는 사실: 기본값, 한도, 예외. 항목마다 같은 꼴(표) | 이야기, 배우는 순서 |
| 설명 | 왜 이렇게 되어 있는지 알려고 | 배경, 고른 이유, 다른 안과 그 대가, 다른 부분과의 관계 | 하라는 지시 |

사용자 가이드는 '하는 법'을 중심으로, 처음 쓰는 사람의 '따라 하기'와 옵션 '참고'를 절로 구분한다. 인수인계는 하는 법과 참고를 나눠 담는다.

밖으로 나가는 사용자 가이드에는 코드 경로, 커밋, 내부 업무 번호를 본문에 쓰지 않는다. 그런 관리 정보('문서 기준')는 문서와 연결한 업무의 댓글에 남긴다.

## 사용자 가이드

- **기본 독자:** 제품을 처음 사용하거나 필요한 기능의 사용법을 찾는 사람이다. 사용자 매뉴얼·사용자설명서 요청도 이 프로필을 쓴다.
- **답할 질문:** 누가 어떤 상황에서 이 작업을 하는가. 어디서 무엇을 입력·선택하는가. 결과로 무엇이 보이는가. 막히면 어떻게 하는가.
- **구성:** 필요한 제품 개념 → 첫 작업 따라 하기 → 작업별 사용법 → 옵션 참고. 조작 페이지는 준비할 것 → 단계와 사진 → 결과 확인 → 막힐 때를 기본으로 삼되 조회·참고·개념 페이지에 입력표와 저장 단계를 억지로 넣지 않는다. 제품의 장점을 나열하는 소개 페이지로 채우지 않는다.
- **규칙:** 단계는 번호를 붙이고 한 단계에 행동 하나. 화면의 글자는 화면에 보이는 그대로 따옴표로 쓴다. 단계를 실제 화면에서 따라 해 본 것만 쓴다.
- **작성 자료:** [매뉴얼 작성과 대조](manual-authoring.md)를 먼저 읽는다. 제품·도메인 파악, 입력/오류/촬영 대조표, 페이지 유형별 구성과 조작 페이지 예시를 제공한다. 표와 예시의 수치·문구를 다른 제품에 복사하지 않는다.

### 화면 촬영과 전달

- 먼저 설명할 기능과 촬영할 상태를 목록으로 정한다. 실제로 사용할 수 있는 기능만 다루며, 권한·외부 설정·미완성 기능은 구분한다.
- 시험 계정과 현실적인 예제 데이터를 쓴다. 한 문서 안에서는 같은 프로젝트·업무 이름을 이어 쓴다. 비밀번호·키·실제 연락처가 나오는 화면은 촬영하지 않는다.
- 같은 테마와 읽기 좋은 창 크기로 촬영한다. 화면이 안정된 뒤 불필요한 메뉴·툴팁·로딩 표시를 닫는다. 단계에 필요한 메뉴는 펼친 상태로 찍는다.
- 원본 캡처를 보관한다. 핵심 동작을 찾기 어려울 때만 여백을 자르거나 번호·윤곽을 더하고, 버튼 글자·값·상태는 고치지 않는다. 사진 아래에 동작과 확인할 결과를 적는다.
- 캡처 도구가 반환한 실제 형식에 파일 확장자와 업로드 형식을 맞춘다. JPEG 바이트를 이름만 PNG로 저장하지 않는다. 원본을 다시 압축하거나 확대해 선명해졌다고 하지 않는다.
- HTML은 본문·CSS·스크린샷을 상대 경로로 묶어 페이지로 올린다. 목차 링크, 좁은 화면의 사진·표, A4 인쇄에서 잘림과 읽기 크기를 확인한다. 페이지 안에 'PDF로 저장'이나 인쇄 버튼을 넣지 않고 BIT의 공통 기능을 이용한다.
- 촬영하지 못한 화면은 사진 자리로 남기지 않는다. 확인한 내용으로 범위를 줄이고, 남은 촬영·검증은 업무에 적는다.

## 개발 매뉴얼

- **기본 독자:** 프로젝트에 새로 참여하거나 변경·검증·배포 작업을 하는 개발자와 에이전트다.
- **답할 질문:** 무엇을 만드는가. 어디를 고쳐야 하는가. 어떤 규칙과 계약을 따라야 하는가. 어떻게 실행·검증·릴리스·복구하는가. 근거와 정본은 어디인가.
- **구성:** 작업별 읽기 안내 → 제품/도메인·구조 → 변경 작업과 규칙 → 협업·검증 → 릴리스·운영. 실제 프로젝트에 있는 내용만 고르고, 절차·설명·참고를 페이지 목적에 맞춰 나눈다. 항목 수나 arc42 전체 구성을 강제하지 않는다.
- **작성 자료:** [개발 매뉴얼 작성](development-manual.md). 현재 코드·검사 설정·원본 지침 대조, 명령 검증, 문체와 페이지 예시를 따른다.
- **규칙:** 사용자 매뉴얼의 클릭 사진 양식을 그대로 적용하지 않는다. 구조는 작은 다이어그램과 실제 경로, 스타일은 적용 이유와 실제 예, 절차는 실행 위치·명령·결과·실패 시 회복을 제공한다. 아직 실행하지 않은 배포·복구를 실행 완료로 쓰지 않는다.

## 인수인계

- **기본 독자:** 이 제품을 이어 맡을 개발자나 에이전트가 첫 작업 전에 읽는다.
- **답할 질문:** 어떻게 띄우고 검사하는가. 코드는 어떻게 나뉘는가. 꼭 지켜야 할 결정은 무엇인가. 지금 진행 중이거나 막힌 일은 무엇인가. 어디에 무엇이 기록되는가.
- **구성:** 띄우기와 검사 → 구조(폴더 지도) → 지켜야 할 결정(결정 댓글이 있는 업무 참조 목록) → 진행 중인 일(업무 참조) → 기록이 있는 곳 → 문서 기준.
- **규칙:** 결정은 내용을 옮겨 적지 않고 업무 참조와 한 줄 요약만 쓴다. 명령은 실제로 돌려 본 것만 쓴다.
