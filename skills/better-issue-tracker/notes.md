# better-issue-tracker 수정 기록

최신이 위다. 각 항목은 증상(무엇이 틀렸나), 수정, 확인으로 쓴다.

## 2026-10-26 · 담당자와 저장소 연동 (BIT-19)
- 증상: 에이전트가 만든 이슈(BIT-17, BIT-18)에 담당자가 비어 있었다. 스킬, MCP 안내문, `create_issue` 설명 어디에도 담당자를 넣으라는 말이 없었다. 또 BIT-17·BIT-18 시험에서 스킬이 저장소 연동을 몰랐다. 브랜치·PR 이름 규칙이 없었고, "검증되면 완료로 옮긴다"를 따르면 PR 병합 전에 저장소 이슈가 닫힌다. 서버를 업데이트한 뒤에는 연결된 세션이 옛 도구 이름으로 남아 `Unknown tool`이 났다.
- 수정: 이슈를 만들 때와 맡을 때 `assignee: "me"`(미뤄 두는 이슈는 비움). 5절 '저장소와 연결된 프로젝트'(이름 규칙, 칸 규칙 표, PR 작업은 병합에 맡김, 저장소 이슈 중복 금지, 댓글 공개 주의). 7절과 README에 다시 연결 안내. MCP 안내문과 `create_issue`·`update_issue` 설명에도 담당자와 이름 규칙을 넣었다.
- 확인: 이 수정을 커밋한 세션에서 BIT-19를 `assignee: me`로 만들었다. 에이전트가 프로젝트의 연결 여부를 도구로 알 수 없어 5절은 지침과 활동 기록으로 판단하게 했다. 도구로 알려 주는 일은 BIT-20.

## 2026-10-26 · 처음 만듦
- 계기: BIT를 만드는 세션에서 에이전트가 프로젝트 지침에 "이슈는 BIT에 남긴다"가 있는데도 작업 두 건과 버그 두 건을 이슈로 남기지 않았다. 지침이 "이슈를 읽고 시작한다"만 말하고, 이슈가 없을 때 먼저 만든다는 계기가 없었다. 또 작업 이슈(BIT-1, ID 형식 바꾸기)에 결정기록 라벨을 붙였다. "의미 있는 판단은 결정기록"이라는 기준이 모호했고, 작업과 결정을 잇는 도구가 없어 하나로 몰아넣었다.
- 만든 것: 이슈를 찾고 만드는 계기(첫 수정 전), 진행·결과 댓글, 결정기록의 정의와 쓰는 때 표, 3섹션 양식, 확정 뒤 대체 규칙. 결정기록 규칙은 Gitifact의 결정기록 안내(쓰는 때 표, 대상 연결, 고치지 않고 새 기록, 섹션 길이)를 이슈 트래커에 맞게 옮겼다.
- 확인: 아직 다른 프로젝트에서 써 보지 않았다. 다음 작업들에서 첫 수정 전에 이슈를 만드는지, 작업과 결정기록을 나누는지 본다.
