# better-issue-tracker 수정 기록

최신이 위다. 각 항목은 증상(무엇이 틀렸나), 수정, 확인으로 쓴다.

## 2026-10-28 · 속성 정하기, 큰 일 나누기, 업무 유형 (BIT-89, D-104)
- 증상 1: 스킬이 담당자만 정하라고 해서, 에이전트가 만든 업무에 시작일·기한·우선순위가 늘 비어 있었다. 사용자가 나중에 화면에서 하나씩 채워야 했다(사용자 지적).
- 증상 2: 하위 업무·연결·프로젝트 해제·첨부·리액션 도구가 생겼는데 7절 도구 표에 없었다. 업무 유형(에픽·스토리·작업·버그)과 유형별 상위 규칙도 생겨, 규칙을 모르면 만들기가 거절된다.
- 증상 3: 0.13.0 릴리스 때 업무를 만들기 전에 다음 번호(BIT-87)를 짐작해 커밋에 먼저 썼다. 번호가 맞아서 문제는 없었지만, 그 사이 다른 업무가 생겼다면 엉뚱한 업무에 붙었다.
- 수정:
  - 2절에 '속성 정하기'를 넣었다. 속성별로 정하는 법을 두고, 모르는 것만 추천값을 채운 질문 한 번으로 묻는다. 묻지 않는 때와, 기본값을 프로젝트 지침에 적어 반복 질문을 없애는 법도 적었다.
  - 2절에 '큰 일 나누기'를 넣었다. `create_subtask`, `link_targets`(`subtask_of`), 유형 규칙과 거절 때 대처를 적었다.
  - 3절 시작 단계에서 비어 있는 시작일을 채우게 했다.
  - 5절에 "키는 업무를 만든 뒤에 쓴다"를 넣었다.
  - 7절 도구 표를 실제 도구 목록에 맞췄다.
- 확인: 운영 BIT의 MCP 도구 목록(`create_subtask`, `link_targets`, `list_relations`, `unlink_targets`, `set_work_item_project`, `attach_files`, `set_reaction`, `list_detail_engagement`)과 대조했다. 유형 도구는 BIT-89 서버 구현(`list_work_item_types`; `create_work_item`·`create_subtask`·`update_work_item`의 `type`; `update_work_item`의 `parent`; `list_work_items`의 `type`)에 맞췄다.

## 2026-10-27 · 프로젝트 문서 읽기
- 요청: 운영 프로젝트 문서를 MCP로 읽고 작업한다(BIT-62).
- 수정: 프로젝트 지침의 문서 지도를 찾아 본문을 읽고 필요한 영역만 조회한다. 특정 서버를 배포 스킬에 고정하지 않는다.
- 확인: BIT 운영의 문서 지도·arc42·영역별 문서를 조회하고 project/folder 범위를 확인했다.

## 2026-10-27 · 일정 알림 (BIT-39)
- 증상: 일정에 참석자 알림이 생겼는데 스킬의 도구 표에는 알림 시점을 정하는 방법이 없었다.
- 수정: 7절의 `create_work_item`에 `remind_before`(시작 몇 분 전, 시각 일정은 생략하면 10분 전)를 적었다. 에이전트가 사람을 담당자나 참석자로 넣으면 그 사람의 받은함에 알림이 간다.
- 확인: 서버 통합 테스트가 담당·초대·댓글·시각 변경 알림, 자기 변경 제외, 일정 알림과 기한 알림이 한 번씩만 가는 것을 확인했다.

## 2026-10-27 · 반복 업무 (BIT-38, D-092)
- 증상: 업무가 반복할 수 있게 됐는데 스킬의 도구 표에는 반복을 정하거나 이후 회차까지 고치는 방법이 없었다.
- 수정: 7절의 `create_work_item`에 `repeat`, `update_work_item`에 `scope: "following"`과 `repeat: "none"`을 적었다. 회차는 각각 따로 된 업무라서 한 회차의 댓글·연결은 그 회차에만 붙는다.
- 확인: 서버 통합 테스트가 주간 일정 8주치 만들기, 이후 모두 고치기, 이후 회차 취소, 작업의 다음 회차 하나만 만들기를 확인했다.

## 2026-10-26 · 일정과 사람 여럿 (BIT-37, D-092)
- 증상: 업무에 종류(작업·일정), 사람 여럿, 시각이 생겼는데 스킬의 도구 표는 담당자 하나와 날짜만 말했다.
- 수정: 7절의 `create_work_item`·`update_work_item` 줄에 `kind`, `people`, `starts_at`·`ends_at`을 적었다. `assignee: "me"`는 그대로 쓰고(사람 하나로 들어감) 여럿이면 `people`이다.
- 확인: 서버 통합 테스트가 일정 만들기, 사람 여럿, 작업 → 일정 바꾸기, 백로그에서 일정 빠짐을 확인했다.

## 2026-10-26 · 문서 도구 (BIT-40, D-093)
- 증상: 서버에 문서(프로젝트 폴더에 두는 마크다운 글)와 MCP 도구 `list_documents`·`get_document`·`create_document`·`update_document`·`link_document`가 생겼는데, 스킬은 긴 글을 둘 곳을 말하지 않았다.
- 수정: 7절 도구 표에 문서 도구 다섯 개와 "문서 도구가 없는 서버면 업무 설명에 쓴다"를 더했다. MCP 안내문에도 문서를 쓰는 때를 한 문장 넣었다. 결정기록을 문서로 옮기는 일(D-094)은 BIT-42에서 하므로 4절은 아직 업무 기준이다.
- 확인: 통합 테스트가 API 키로 문서 도구를 불러 만들기·폴더 경로·고치기·업무 잇기·찾기를 확인했다.

## 2026-10-26 · 이슈를 업무로 (BIT-36, D-091)
- 증상: 결정 D-091로 일감의 이름이 화면에서는 '업무', 코드·API·MCP에서는 work item이 됐다. 스킬과 MCP 안내문은 '이슈'와 `get_issue_context`·`list_issues`·`create_issue`·`update_issue`·`move_issue`를 쓰고 있었다.
- 수정: 스킬 본문과 README의 '이슈'를 '업무'로, 도구 이름을 `get_work_item_context`·`list_work_items`·`create_work_item`·`update_work_item`·`move_work_item`으로 바꿨다. 저장소의 이슈(GitHub·GitLab·Gitea의 issue)는 그대로 '저장소 이슈'다. 7절에 issue 이름을 쓰던 서버(D-084~D-091 사이)의 도구 이름을 남겼다. MCP 안내문(`McpServerConfig`)과 도구 설명도 같이 바꿨다.
- 확인: 서버 검사(단위 48개, 통합 110개)와 화면 검사가 통과했다. 운영 서버에 배포한 뒤 연결된 세션은 다시 연결해야 새 도구 이름이 보인다.

## 2026-10-26 · 담당자와 저장소 연동 (BIT-19)
- 증상: 에이전트가 만든 이슈(BIT-17, BIT-18)에 담당자가 비어 있었다. 스킬, MCP 안내문, `create_issue` 설명 어디에도 담당자를 넣으라는 말이 없었다. 또 BIT-17·BIT-18 시험에서 스킬이 저장소 연동을 몰랐다. 브랜치·PR 이름 규칙이 없었고, "검증되면 완료로 옮긴다"를 따르면 PR 병합 전에 저장소 이슈가 닫힌다. 서버를 업데이트한 뒤에는 연결된 세션이 옛 도구 이름으로 남아 `Unknown tool`이 났다.
- 수정: 이슈를 만들 때와 맡을 때 `assignee: "me"`(미뤄 두는 이슈는 비움). 5절 '저장소와 연결된 프로젝트'(이름 규칙, 칸 규칙 표, PR 작업은 병합에 맡김, 저장소 이슈 중복 금지, 댓글 공개 주의). 7절과 README에 다시 연결 안내. MCP 안내문과 `create_issue`·`update_issue` 설명에도 담당자와 이름 규칙을 넣었다.
- 확인: 이 수정을 커밋한 세션에서 BIT-19를 `assignee: me`로 만들었다. 에이전트가 프로젝트의 연결 여부를 도구로 알 수 없어 5절은 지침과 활동 기록으로 판단하게 했다. 도구로 알려 주는 일은 BIT-20.

## 2026-10-26 · 처음 만듦
- 계기: BIT를 만드는 세션에서 에이전트가 프로젝트 지침에 "이슈는 BIT에 남긴다"가 있는데도 작업 두 건과 버그 두 건을 이슈로 남기지 않았다. 지침이 "이슈를 읽고 시작한다"만 말하고, 이슈가 없을 때 먼저 만든다는 계기가 없었다. 또 작업 이슈(BIT-1, ID 형식 바꾸기)에 결정기록 라벨을 붙였다. "의미 있는 판단은 결정기록"이라는 기준이 모호했고, 작업과 결정을 잇는 도구가 없어 하나로 몰아넣었다.
- 만든 것: 이슈를 찾고 만드는 계기(첫 수정 전), 진행·결과 댓글, 결정기록의 정의와 쓰는 때 표, 3섹션 양식, 확정 뒤 대체 규칙. 결정기록 규칙은 Gitifact의 결정기록 안내(쓰는 때 표, 대상 연결, 고치지 않고 새 기록, 섹션 길이)를 이슈 트래커에 맞게 옮겼다.
- 확인: 아직 다른 프로젝트에서 써 보지 않았다. 다음 작업들에서 첫 수정 전에 이슈를 만드는지, 작업과 결정기록을 나누는지 본다.
