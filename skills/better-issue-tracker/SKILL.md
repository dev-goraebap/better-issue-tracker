# BIT로 일하기

BIT는 업무와 결정기록을 한곳에 두는 셀프호스팅 업무 트래커다. 에이전트는 MCP 도구로 업무를 찾고 만들고, 진행과 결과를 댓글로 남긴다. 사람은 같은 업무를 화면에서 읽는다. 다음 세션의 에이전트도 그 업무를 읽고 이어서 일한다.

이 스킬의 목표는 두 가지다. **한 일은 업무에 남고, 앞으로 따를 선택은 결정기록에 남는다.** 대화에만 있고 업무에 없는 작업은 세션이 끝나면 사라진다.

## 1. 시작할 때

1. `whoami`로 연결과 계정, 속한 워크스페이스를 확인한다. 도구가 없거나 인증 오류면 사용자에게 알리고 BIT 없이 일한다고 말한다.
2. 어느 워크스페이스·프로젝트에 남길지 정한다. 순서대로 본다.
   - 프로젝트 지침(`AGENTS.md`, `CLAUDE.md` 등)에 적힌 워크스페이스와 프로젝트 키
   - 워크스페이스가 하나이고 `list_projects`의 프로젝트가 하나뿐이면 그것
   - 그래도 모르면 사용자에게 한 번 묻고, 답을 프로젝트 지침에 적어 두자고 제안한다
3. 계정에 워크스페이스가 여럿이면 모든 도구 호출에 `workspace`(이름이나 슬러그)를 준다. 빠뜨리면 오류가 난다.

## 2. 업무를 언제 찾고 만드는가

| 상황 | 할 일 |
| :--- | :--- |
| 코드·문서·설정을 바꾸는 요청 | **첫 수정 전에** 관련 업무를 찾고, 없으면 만든다 |
| 사용자가 참조를 줌(`ORM-14`) | 그 업무를 `get_work_item_context`로 읽고 시작한다 |
| 작업 중 이번 요청과 다른 문제를 찾음 | 지금 고치든 아니든 따로 업무를 만든다. 지금 고쳤으면 그 업무에 결과를 남기고 닫는다 |
| 질문, 설명, 코드 읽기만 | 만들지 않는다. 사용자가 원하면 만든다 |
| 같은 업무의 작은 후속 수정(오타, 한 줄) | 새 업무 없이 진행 중인 업무에 댓글로 남긴다 |

찾을 때는 `list_work_items`에 `query`(제목 검색어)와 `project`를 주고, 끝난 일일 수도 있으면 `include_closed: true`도 준다. 같은 일을 다루는 업무가 있으면 새로 만들지 않고 그것을 쓴다.

만들 때:
- **제목**은 무엇을 바꾸는지 한 줄로 쓴다(예: "로그인 실패 시 남은 시도 횟수 표시"). 원인이나 방법은 설명에 쓴다.
- **설명**에는 요청과 배경, 다 됐다고 볼 기준을 짧게 쓴다. 버그는 현상, 재현 순서, 기대와 실제를 쓴다.
- **담당자**는 지금 이어서 작업할 업무면 `assignee: "me"`로 만든다. `me`는 API 키의 주인, 곧 이 에이전트에게 일을 맡긴 사람이다. 찾은 문제를 나중으로 미뤄 두는 업무는 비워 둔다. 사용자가 다른 사람을 말하면 `list_members`로 확인해 그 사람을 넣는다.
- 라벨은 `list_labels`에 있는 것만 쓴다. 없는 라벨을 지어내지 않는다.

## 3. 작업하는 동안

1. **시작:** `get_work_item_context`로 설명과 댓글, 활동을 읽는다. 앞선 사람이나 에이전트가 남긴 결정과 막힌 점이 거기 있다. 그다음 `move_work_item`으로 '진행 중'에 옮긴다. 담당자가 비어 있으면 `update_work_item`으로 `assignee: "me"`를 넣는다. 다른 사람이 맡고 있으면 바꾸지 않고 사용자에게 알린다.
2. **관련 결정 읽기:** 바꾸려는 영역에 결정기록이 있는지 `list_work_items`(`label: "결정기록"`, `include_closed: true`, `query`)로 찾아 따른다. 결정과 어긋나게 해야 하면 바꾸기 전에 사용자에게 말한다.
3. **진행 댓글:** 의미 있는 단계마다 `add_comment`로 남긴다. 무엇을 했고, 무엇을 알게 됐고, 무엇이 남았는지를 쓴다. 도구를 부를 때마다 남기지 않는다. 한 작업에 보통 2~4개면 충분하다.
4. **결과 댓글:** 커밋했으면 커밋 해시와 한 줄 요약, 실행한 검증(테스트, 직접 확인)과 하지 못한 검증을 남긴다. 커밋하지 않았으면 그렇다고 쓴다.
5. **닫기:** 작업이 끝나고 검증까지 됐으면 '완료'로 옮긴다. 사용자 확인이 필요한 일(배포, 화면 확인)이 남았으면 진행 중으로 두고 남은 것을 댓글에 쓴다. 저장소와 연결된 프로젝트에서 PR로 들어가는 작업은 직접 옮기지 않고 병합에 맡긴다(5절).

결과 댓글의 예:

```markdown
`a1b2c3d`에서 로그인 실패 시 남은 시도 횟수를 응답과 화면에 보이게 했습니다.

- 검증: 서버 테스트 통과, 로컬 화면에서 5회 실패까지 직접 확인
- 못 한 것: 운영 배포 전이라 실제 계정 잠금 메일은 확인하지 않음
```

## 4. 결정기록

결정기록은 **앞으로 다른 작업이 따라야 할 선택**(규칙, 방식, 제약)을 남기는 업무다. `결정기록` 라벨을 달아 만든다. 할 일이 아니라 기록이므로 그 선택이 나온 작업 업무와 따로 만든다. 작업 업무는 일이 끝나면 닫히고, 결정기록은 나중에 다른 결정으로 대체될 때까지 유효하다.

### 쓰는 때

| 경우 | 결정기록 |
| :--- | :--- |
| 기존 결정이나 지켜 오던 동작을 바꾸거나 뒤집음 | 쓴다. 옛 방식이 사라지므로 이유를 남길 곳이 여기뿐이다 |
| 여러 안 중 하나를 골랐고, 이후 작업이 그것을 따라야 함 | 쓴다 |
| 이번 작업에서만 쓰고 끝나는 선택 | 쓰지 않는다. 작업 업무 댓글에 남긴다 |
| 새 기능을 더하는 것 자체 | 쓰지 않는다. 요청이 곧 이유다 |
| 다른 결정을 따르느라 함께 바꾼 것 | 따로 쓰지 않는다. 원래 결정기록에 댓글로 더한다 |
| 오타, 문장 다듬기, 단순 버그 수정 | 쓰지 않는다 |

판단이 어려우면 이렇게 묻는다. **"나중에 누군가 '왜 이렇게 했지?' 하고 이 기록을 찾아올까?"** 그렇다면 결정기록이고, 아니면 댓글이다. 선택지를 비교했다는 것만으로는 결정기록이 되지 않는다.

### 쓰는 법

- **결정한 순간에 쓴다.** 작업이 끝난 뒤 되짚어 쓰면 검토한 대안 같은 맥락이 사라진다.
- **제목**은 대상과 동작을 담은 명사구로 쓴다(예: "API 오류 응답의 RFC 9457 형식", "삭제한 게시물의 30일 보관"). 주제만 적지 않고("오류 응답"), 이유는 본문에 둔다.
- **본문**은 아래 세 섹션만 쓴다. 맥락과 결정은 각각 2~5문장으로 쓴다. 구현 절차, API 필드 목록, 테스트 기록은 작업 업무나 커밋에 둔다.

```markdown
## 맥락

무엇 때문에 정해야 했는지: 드러난 문제(잰 수치가 있으면 그것), 누가 무엇을 요청했는지, 지켜야 할 제약.
이 결정이 나온 작업 업무: ORM-20

## 결정

무엇을 하기로 했고 어디까지 적용하는지, 예외가 있으면 그것.

## 검토한 대안

- 고르지 않은 안 (그 까닭을 짧게)
```

  검토한 대안은 실제로 따져 본 안이 있을 때만 쓴다. 지어내지 않는다.
- **상태:** 사용자가 정한 결정은 만든 뒤 '완료' 칸으로 옮긴다(확정). 아직 사용자의 결정을 기다리는 제안이면 '할 일'에 두고, 정해지면 본문을 확정 내용으로 고친 뒤 옮긴다.
- **확정한 결정은 고치지 않는다.** 결정이 바뀌면 새 결정기록을 만들고, 새 기록의 맥락에 "ORM-31을 대체한다"를 적는다. 옛 기록에는 "ORM-45로 대체됨" 댓글을 단다.
- **작업 업무와 잇기:** 업무를 잇는 도구가 있으면 그것으로 잇는다. 없으면 결정기록의 맥락에 작업 업무 참조를 적고, 작업 업무에는 "결정기록 ORM-31로 남김" 댓글을 단다.

### 예

결제 모듈을 고치다가 실패한 결제를 언제 다시 시도할지 골라야 했다(작업 업무 PAY-12).

- 이번 수정에서만 쓰는 재시도 간격이라면 → PAY-12 댓글에 남긴다.
- 앞으로 모든 외부 결제 호출이 따를 규칙("재시도는 지수 백오프 3회, 그 뒤 수동 처리 대기열")이라면 → 결정기록 PAY-13을 따로 만들고, 맥락에 PAY-12를 적는다.

## 5. 저장소와 연결된 프로젝트

BIT 프로젝트는 GitHub, GitLab, Gitea 저장소와 연결될 수 있다. 연결되면 업무 키를 단 브랜치, PR, 커밋이 업무에 붙고 칸을 옮긴다. 업무의 제목, 설명, 칸, 댓글은 저장소 이슈와 서로 반영된다.

**연결됐는지 알기:** 프로젝트 지침에 적혀 있거나, `get_work_item_context`의 활동에 `GitHub · <계정>`처럼 호스트 이름으로 남은 기록이 있으면 연결된 것이다. 아래 이름 규칙은 연결이 없어도 해가 없으니 늘 따른다.

**이름에 업무 키를 넣는다.**
- 브랜치: `<키 소문자>-<번호>-<짧은 영문>`. 예: `orm-14-login-retry-count`. BIT 업무 화면의 '브랜치 이름 복사'와 같은 형식이다.
- 커밋 메시지와 PR 제목에 `ORM-14`를 넣는다. 여러 업무를 다루면 모두 넣는다.
- PR 본문에 `Closes #12`처럼 저장소 이슈 번호를 쓰면, 그 저장소 이슈와 이어진 BIT 업무도 PR에 붙는다.

**칸은 연동이 옮긴다.** 기본 규칙은 아래와 같고, 프로젝트 설정에서 바꿀 수 있다. 칸은 앞으로만 옮기고 되돌리지 않는다.

| 저장소에서 | BIT 업무 |
| :--- | :--- |
| 업무 키가 든 브랜치를 처음 push | 시작 전이면 첫 '진행 중' 칸으로 |
| PR 열기(초안에서 풀기 포함) | 진행 중 계열의 마지막 칸(예: 검토 중)으로 |
| PR 병합, 저장소 이슈 닫기 | 완료 칸으로 |

- PR로 들어가는 작업은 '완료'로 직접 옮기지 않는다. 먼저 옮기면 병합 전에 저장소 이슈가 닫힌다. 결과 댓글만 남기고 병합을 기다린다.
- 시작할 때 '진행 중'으로 옮기는 것은 그대로 한다.
- PR 없이 기본 브랜치에 바로 커밋하는 작업은 3절대로 직접 옮긴다. 커밋은 업무에 붙기만 하고 칸을 옮기지 않는다.

**저장소 이슈를 따로 만들지 않는다.** 이슈 동기화가 켜져 있으면 BIT 업무를 만들 때 저장소 이슈가 함께 생기고, 저장소에서 연 이슈는 BIT 업무로 들어온다. 같은 일을 양쪽에 따로 만들지 않는다.

**댓글은 저장소에서도 보인다.** 이슈 동기화가 켜져 있으면 BIT의 설명과 댓글이 저장소 이슈에 그대로 복사된다. 공개 저장소면 누구나 읽는다. 내부 주소, 로컬 경로, 사내 사정처럼 저장소 밖에 둘 내용은 쓰지 않는다.

## 6. 쓰는 말

- 본문과 댓글은 마크다운이다. 사람이 화면에서 읽는다고 생각하고 짧게 쓴다.
- 프로젝트 지침이 정한 언어로 쓴다. 정한 것이 없으면 사용자와 대화하는 언어로 쓴다.
- 비밀번호, API 키, 토큰, 개인정보는 업무에 쓰지 않는다.
- 하지 않은 일을 한 것처럼 쓰지 않는다. 확인하지 못한 것은 확인하지 못했다고 쓴다.

## 7. 도구

| 도구 | 쓰는 때 |
| :--- | :--- |
| `whoami` | 연결, 계정, 워크스페이스 확인 |
| `list_projects` | 프로젝트 키와 보드 칸 이름 확인 |
| `list_members` | 담당자로 지정할 사람 확인 |
| `list_labels` | 쓸 수 있는 라벨 확인(`결정기록`은 시스템 라벨) |
| `list_work_items` | 업무·결정기록 찾기(`query`, `label`, `include_closed`, `assignee`) |
| `get_work_item_context` | 업무 하나를 설명, 댓글, 활동까지 읽기 |
| `create_work_item` | 업무·결정기록 만들기. 일정은 `kind: "event"`와 `starts_at`·`ends_at`(예: `2026-10-28T10:00+09:00`), 사람이 여럿이면 `people`. 반복은 `repeat: "weekly"`(와 `repeat_on`, `repeat_until`), 일정 알림은 `remind_before`(분) |
| `update_work_item` | 제목, 설명, 라벨, 사람, 날짜·시각, 종류 고치기(준 값만 바뀜). 반복 업무의 이후 회차까지 고치려면 `scope: "following"`, 반복을 끝내려면 `repeat: "none"` |
| `move_work_item` | 칸(할 일, 진행 중, 완료 등) 옮기기, 보관 |
| `add_comment` | 진행, 결과, 막힌 점 남기기 |
| `list_documents` | 문서 찾기(`query`, `label`, `project`) 또는 폴더 열기(`folder`: "설계/화면") |
| `get_document` | 문서 하나를 본문, 연결된 업무, 댓글까지 읽기 |
| `create_document` | 요구사항·설계·기획·회의록처럼 오래 두고 고쳐 가며 보는 글 남기기(없는 폴더는 만듦) |
| `update_document` | 문서 본문·제목·라벨 고치기, `project`·`folder`로 옮기기 |
| `link_document` | 문서를 그 문서가 다루는 업무와 잇기(`remove: true`면 끊기) |

문서 도구가 목록에 없으면 문서가 없는 서버다(D-093 전). 그때 긴 글은 업무 설명에 쓴다.

도구 이름이 이 표와 다르거나 `Unknown tool` 오류가 나면, 서버가 업데이트됐는데 연결이 옛 도구 목록을 들고 있는 것이다. 사용자에게 MCP 서버를 다시 연결하거나 새 세션을 열어 달라고 한다. 0.8 이후에 나와 이름을 issue로 바꿨던 서버(D-084~D-091 사이)는 업무 도구 이름이 `get_issue_context`, `list_issues`, `create_issue`, `update_issue`, `move_issue`이다. 연결된 서버의 도구 목록에 있는 이름을 쓴다.
