# T-002. 인증과 API 키 (Codex 작업 지시서)

> 작성: 2026-10-22. 선행 작업: T-001 (`381a759`). 상태: **추천안 확정 / 구현·자동 검증 완료**.
> `AGENTS.md`, `bit-backend`, `bit-api-contract`, `bit-database`, `bit-frontend` 스킬을 따른다.
> 사용자가 추천안대로 구현을 요청했다. 추천안 1~3과 인증 기본값은 D-036~D-039로 확정했다.

## 목표

메일 없이 첫 관리자가 설치를 시작하고 이메일·비밀번호로 로그인한다. 로그인한 사람은 자기 API 키를 발급·폐기하고, 에이전트는 그 키로 자기 신원을 확인할 수 있다.
브라우저 세션과 Bearer 인증을 후속 REST·MCP 기능이 함께 사용할 기반으로 만든다. 워크스페이스·프로젝트·업무 데이터는 만들지 않는다.

SandboxHr를 추가 참고하면 읽기만 하고 `credentials/`, `.env`, `CLAUDE.local.md`는 열지 않는다. 계정·이메일·도메인·HR 권한을 가져오지 않는다.

## 추천안 1. 가입은 첫 관리자 직접 가입 + 이후 초대

| 선택지 | 장점 | 비용·위험 | 추천 |
|---|---|---|---|
| 첫 관리자만 직접 가입, 이후 초대 | 개인 설치가 간단하고 설치 주소만 안다고 계정이 늘어나지 않음 | 초대 기능은 워크스페이스 작업에서 필요 | **채택** |
| 계속 공개 가입 | 여러 사람이 자유롭게 참여 | 계정 남용 방어와 가입·참여 정책이 더 필요 | 보류 |
| 관리자가 모든 계정을 직접 생성 | SMTP 없이 여러 계정 운영 가능 | 임시 비밀번호 전달·강제 변경 업무가 기본 가입 흐름이 됨 | 복구 수단으로만 사용 |

- T-002는 **첫 관리자 가입만 구현**한다. 이후 가입은 닫고 안내한다. 다음 워크스페이스 작업에서 초대 링크로 가입·참여를 연다. 초대 링크는 SMTP 없이도 복사·전달할 수 있게 한다.
- 최초 설치에서만 가입 가능하다. 사용자 행이 하나라도 있으면(소프트 삭제된 사용자 포함) 초기 가입을 다시 열지 않는다. 마지막 관리자 부재를 새 설치로 취급하지 않는다.
- 첫 가입은 `iam_user`와 `iam_password`를 같은 쓰기 트랜잭션에서 만들고 `is_instance_admin = 1`로 한다. 동시 요청도 관리자 한 명만 성공해야 한다. 화면의 `canBootstrap` 값은 안내이며 서버가 다시 검사한다.
- 비밀번호 해시는 트랜잭션 밖에서 계산한 뒤, 짧은 `BEGIN IMMEDIATE` 트랜잭션에서 최초 가입 가능 여부를 재확인하고 저장한다.
- 가입 입력은 이름·이메일·비밀번호다. 이메일은 양끝 공백 제거·소문자 정규화를 가입과 로그인에 동일 적용한다. 비밀번호는 trim·대소문자 변경·정규화를 하지 않는다.
- SMTP가 없으므로 이메일 소유를 검증했다고 표시하지 않는다. 초기 설치는 운영자가 먼저 접근하는 환경을 전제로 하며 인터넷에 공개하기 전에 첫 가입을 마친다.
- 가입 성공 후 로그인 화면으로 이동한다. 워크스페이스는 자동 생성하지 않는다.

## 추천안 2. 인스턴스 관리자와 워크스페이스 권한 분리

인스턴스 관리자는 계정 복구·설치 운영을 맡는다. 관리자라는 이유로 모든 워크스페이스의 업무 내용을 읽거나 수정하지 않는다.
워크스페이스 역할은 기존 결정대로 `owner`, `admin`, `member`, `viewer` 네 개만 사용한다.

다음 표는 **후속 워크스페이스·업무 기능의 추천 계약**이다. T-002에서 없는 테이블·가짜 워크스페이스나 미사용 권한 프레임워크를 만들지 않는다.

| 동작 | owner | admin | member | viewer |
|---|---|---|---|---|
| 소속 워크스페이스의 프로젝트·업무 내용 조회 | 허용 | 허용 | 허용 | 허용 |
| 작업항목·결정·세션·산출물 생성·수정·보관, 링크·댓글 작성 | 허용 | 허용 | 허용 | 거부 |
| 자기 댓글 수정·삭제 | 허용 | 허용 | 허용 | 거부 |
| 다른 사람 댓글 삭제, 업무 자원 삭제·복원 | 허용 | 허용 | 거부 | 거부 |
| 프로젝트·보드·워크스페이스 라벨 관리 | 허용 | 허용 | 거부 | 거부 |
| 워크스페이스 일반 설정 | 허용 | 허용 | 거부 | 거부 |
| member·viewer 초대·역할 변경·제거 | 허용 | 허용 | 거부 | 거부 |
| admin 지정·해제·제거 | 허용 | 거부 | 거부 | 거부 |
| 소유권 이전·워크스페이스 삭제 | 허용 | 거부 | 거부 | 거부 |

- admin은 자기 자신을 owner로 승격하거나 다른 admin·owner를 제거할 수 없다. 마지막 owner 제거는 금지하고 소유권 이전은 원자적으로 처리한다.
- 후속 워크스페이스 생성은 정상 로그인한 사용자에게 허용하고 생성자를 owner로 둔다. 인스턴스 관리자 지정 권한과 연결하지 않는다. 역할의 허용은 각 엔티티의 상태 전이·불변식 검사를 생략할 권한이 아니다.
- 멤버별 프로젝트 접근 제한은 MVP에 넣지 않는다. 비멤버에게는 대상 존재를 드러내지 않는 404, 멤버의 역할 부족에는 403을 반환한다.
- API 키 권한은 저장된 역할 사본이 아니라 매 요청 시점의 키 주인·멤버십·역할로 판정한다. 삭제·역할 변경이 즉시 반영돼야 한다.
- **대안**: member의 수정을 자기 작성물로만 제한하면 협업 작업항목·공유 산출물을 함께 고치기 어렵다. 역할을 사용자 정의로 만들면 권한 편집 UI와 관리 비용이 늘어난다.

## 추천안 3. API 키는 업무 API 읽기·쓰기, 계정 보안은 세션 전용

| 영역 | 브라우저 세션 | API 키 Bearer |
|---|---|---|
| 내 신원 조회 | 허용 | 허용, 키의 `agent_name`도 반환 |
| 후속 업무 REST API·MCP 도구 | 역할에 따라 허용. MCP는 Bearer 전용 | 키 주인의 역할에 따라 읽기·쓰기 허용 |
| API 키 목록·발급·폐기 | 본인만 허용 | 거부 |
| 비밀번호 변경·현재/전체 세션 관리 | 본인만 허용 | 거부 |
| 인스턴스 관리자 API·임시 비밀번호 발급 | 관리자만 허용 | 거부 |
| 후속 초대·멤버 역할·소유권 변경, 외부 연동 비밀값 등록 | 해당 역할에 따라 허용 | 거부 |

- D-021의 “사람 계정으로 움직임”과 업무 쓰기 허용을 유지한다. 키마다 별도 역할·scope·사용자 계정을 만드는 기능은 이번 범위 밖이다.
- 제한은 업무 역할과 별개인 **인증 수단 제한**이다. owner의 API 키여도 키를 추가 발급하거나 소유권을 넘길 수 없다. 단순히 모든 `/api/v1/**`에 Bearer를 허용하지 않는다.
- 앞으로 API를 추가할 때 세션 전용인지 업무 API인지 명시한다. 새 경로는 검토·등록 전 기본 거부다.
- 유효한 Bearer로 인증된 업무 요청만 CSRF 검사에서 제외한다. `Authorization` 헤더가 있다는 이유만으로 제외하지 않는다.
- 잘못되거나 만료·폐기된 Bearer는 쿠키가 함께 있어도 세션 인증으로 되돌아가지 않고 401이다. 유효한 Bearer와 세션 쿠키가 함께 오면 Bearer 주체와 인증 수단 제한을 적용한다.
- Bearer 전용 요청은 Origin 부재를 허용한다. 브라우저 CORS를 넓게 열지 않는다. 향후 MCP의 Origin·Host 검증은 MCP 프로토콜 요구에 맞게 별도 적용한다.
- **대안**: GET 전용 키는 에이전트의 작업 기록·상태 변경을 막는다. 계정 보안 API까지 허용하면 업무용 키 하나로 추가 키를 만들거나 계정을 장악할 수 있다.

## 할 일

### 1. 서버: 계정·비밀번호

- `module/iam`에 공개 계약과 `application`, 순수 Java `domain`, package-private `infrastructure` 구현을 둔다. 컨트롤러·MCP가 권한을 따로 갖지 않게 Service/Facade에서 검증한다.
- 인증 필터와 이를 조립하는 `AuthSecurityConfig`는 IAM의 HTTP 진입 계층(`module/iam/application`)에 둔다. T-001의 `shared/config/SecurityConfig`를 대체하고, `shared`가 `IamFacade` 등 업무 모듈을 참조하게 만들지 않는다. `shared/web/CurrentUser`는 업무 모듈에 의존하지 않는 공통 주체 타입으로 유지한다.
- D-027대로 `DelegatingPasswordEncoder`의 bcrypt를 사용한다. 원문 비밀번호·세션 토큰·API 키를 DB와 로그에 남기지 않는다.
- 비밀번호 추천 기준: 15~64 Unicode 코드 포인트, UTF-8 최대 72바이트. bcrypt 입력 한계 때문에 바이트 길이도 검사하며 넘는 값을 잘라 쓰지 않는다. 공백·Unicode를 허용하고 문자 종류 조합·정기 변경을 강요하지 않는다. UI에 문자/바이트 제한을 설명한다.
- 같은 계정의 연속 5회 실패 시 15분 잠금, 성공 시 실패 횟수 초기화. **실패 횟수 저장이 로그인 예외로 롤백되지 않게** 트랜잭션 경계를 설계한다. 잠금 중 시도로 만료 시각을 계속 늘리지 않는다.
- 없는 이메일·비밀번호 불일치·잠금은 같은 401 코드/문구로 답한다. 없는 계정에도 고정된 더미 해시 비교를 수행해 뚜렷한 빠른 실패 경로를 없앤다.
- 로그인·초기 가입에는 계정 잠금과 별도로 IP별 요청 제한을 둔다(추천 기본 분당 10회, 429). 단일 인스턴스용 크기·TTL 제한 메모리 저장소로 시작한다. 임의 `X-Forwarded-For`를 신뢰하지 않는다. 한도·시계는 테스트 가능하게 둔다.
- 임시 비밀번호는 관리자 재인증 후 서버가 생성해 한 번만 반환한다. 대상의 세션·키를 전부 무효화하고 `must_change = 1`, 실패 횟수·잠금을 초기화한다. 자기 비밀번호 변경은 일반 변경 경로를 쓴다.
- `must_change` 사용자는 세션 신원 확인·비밀번호 변경·로그아웃·CSRF 조회만 허용한다. API 키는 사용할 수 없고 새로 만들 수도 없다.
- 본인 비밀번호 변경 시 현재 비밀번호를 확인한다. 다른 세션과 모든 API 키를 무효화하고, 현재 세션 토큰과 CSRF 토큰을 교체한 뒤 `must_change = 0`으로 만든다.

### 2. 서버: DB 세션·API 키·공통 인증 주체

- `iam_session`의 불투명 난수 토큰을 `bit_session` 쿠키로 발급한다. JWT·브라우저 localStorage 토큰을 도입하지 않는다.
- 토큰은 CSPRNG 최소 32바이트로 생성하고 `AUTH_SECRET` 기반 HMAC-SHA-256을 저장한다. 세션·API 키·CSRF는 서로 다른 용도 문자열로 구분한다. 비교에는 상수 시간 비교를 사용한다.
- 세션 추천 기본값: 유휴 만료 7일, 절대 만료 30일, `last_seen_at`/유휴 만료 갱신 최소 간격 5분. 슬라이딩 갱신은 절대 만료를 넘지 않는다. 쿠키 수명도 서버 만료와 맞추고 로그아웃 시 동일 Path·속성으로 제거한다.
- 요청에서 삭제된 사용자·만료된 세션·키를 거부한다. `Clock`을 주입해 만료와 잠금을 검증한다. 서버 재시작 뒤에도 동일 DB·비밀값이면 유효 세션이 유지된다.
- `CurrentUser`는 `shared/web`에 두고 사용자 ID·인스턴스 관리자 여부·인증 수단·API 키 ID/`agent_name` 등 필요한 최소 정보만 담는다. 키 원문은 담지 않는다. workspace 역할은 아직 넣지 않는다.
- `iam_api_key`: `bit_` 접두어 + 최소 32바이트 난수, 원문은 생성 시 한 번만 반환한다. `name`, 선택 `agent_name`, 만료 1·7·30·90일 또는 없음. 추천 기본 만료 30일, 무기한은 명시 선택이다.
- 목록에는 ID·이름·접두부·에이전트 이름·생성/사용/만료/폐기 시각만 반환한다. HMAC·원문을 반환하지 않는다. `last_used_at` 저장은 최대 분당 한 번으로 제한한다.
- 키 생성에는 현재 비밀번호 재확인을 요구한다. 자기 키만 폐기 가능하고, 자기 키의 중복 폐기는 204, 다른 사람 키는 404다.
- V1의 `active_workspace_id`는 이 작업에서 null로 유지한다. workspace 모듈을 임시로 구현하거나 가짜 역할을 부여하지 않는다.

### 3. 서버: 보안 경계·API 계약

- `bit_session`: `HttpOnly; Path=/; SameSite=Lax`. Secure 기본 true, 로컬 `dev`만 false. 원격 HTTP 설치는 HTTPS 사용을 안내한다. 루프백 컨테이너 테스트에서 HTTP가 필요하면 명시적으로 false를 설정한다.
- 상태 변경은 초기 가입·로그인도 포함해 CSRF + Origin 검증을 적용한다. 로그인 전에도 CSRF를 받을 수 있어야 하며 로그인 성공 시 토큰을 교체한다.
- CSRF는 프레임워크의 확장 지점을 사용한 서명·세션 결합 double-submit 방식으로 구현한다. 로그인 전에는 서명된 익명 nonce를 사용한다. 단순히 임의 쿠키와 헤더가 같은지만 비교하지 않는다. 인증 쿠키는 항상 HttpOnly다.
- `GET /api/v1/auth/csrf`가 `{token, headerName}`을 반환하고 필요한 CSRF 쿠키를 발급한다. 이 응답과 인증·키 응답은 `Cache-Control: no-store`다.
- 세션 요청의 Origin을 허용 목록과 정확히 비교하고, Origin이 없으면 Referer의 origin을 검사한다. 둘 다 없거나 `Origin: null`이면 상태 변경을 거부한다. 실제 세션 전용 인가와 CSRF 검사를 둘 다 유지한다.
- `AUTH_ALLOWED_ORIGINS`는 dev에서 localhost:4402·localhost:8080을 기본 허용한다. 그 밖의 환경은 기본 localhost:8080으로 시작하고 배포 공개 출처를 명시 설정한다. 요청의 Host나 임의 전달 헤더를 허용 출처의 근거로 삼지 않는다. 모든 출처 허용과 자격 증명 CORS를 함께 켜지 않는다.
- 익명 401, 인증됐으나 허용 안 된 인증 수단/권한 403, 소유하지 않은 키 등 존재 은닉 대상 404. 필터 단계도 RFC 9457 + `code`·`traceId`다. CSRF 실패는 `AUTH_CSRF_INVALID` 403, Origin 거부는 `AUTH_FORBIDDEN` 403.
- 인스턴스 관리자 경로는 본문 바인딩보다 먼저 관리자/세션 여부를 검사한다. JSON이 깨진 비관리자 요청도 입력 규칙을 드러내는 400으로 바뀌지 않아야 한다.
- 기존 health·capabilities는 계속 공개한다. 아래 공개 경로만 추가하며 공개 GET의 HEAD도 허용한다. 정적 SPA는 공개하되 화면의 데이터는 API에서 보호한다. OpenAPI 문서 주소를 운영 공개 목록에 넣지 않는다.

| 메서드·경로 | 인증 | 성공 계약 |
|---|---|---|
| `GET /api/v1/auth/bootstrap` | 공개 | 200 `{canBootstrap}`만. 사용자 수·이메일 없음 |
| `GET /api/v1/auth/csrf` | 공개 | 200 CSRF 정보, no-store |
| `POST /api/v1/auth/bootstrap` | 최초 설치만, CSRF/Origin 필수 | 201, 빈 본문, `Location: /api/v1/me`. 이미 초기화됐으면 409 `AUTH_BOOTSTRAP_CLOSED` |
| `POST /api/v1/auth/sessions` | 공개, CSRF/Origin 필수 | 201, 빈 본문, 세션 쿠키, `Location: /api/v1/auth/sessions/current` |
| `GET /api/v1/auth/sessions/current` | 세션 | 200 사용자·유휴/절대 만료·`mustChangePassword` |
| `DELETE /api/v1/auth/sessions/current` | 세션 | 204, 현재 세션 무효화·쿠키 삭제 |
| `DELETE /api/v1/auth/sessions` | 세션 | 204, 전 기기 로그아웃·쿠키 삭제. API 키는 유지 |
| `GET /api/v1/me` | 세션 또는 Bearer | 200 사용자 ID·이름·이메일·관리자 여부·강제 변경 여부·인증 수단·`agentName`(없으면 null) |
| `PUT /api/v1/me/password` | 세션 | 204, 비밀번호 변경 및 현재 세션 교체 |
| `GET /api/v1/me/api-keys` | 세션 | 200 목록. 누적 목록은 공통 커서 계약 사용 |
| `POST /api/v1/me/api-keys` | 세션 + 현재 비밀번호 확인 | 201 `{id,key,prefix,expiresAt}`, 키 자원 Location. 키 원문 반환의 명시적 계약 예외 |
| `DELETE /api/v1/me/api-keys/{keyId}` | 세션 | 204, 자기 키 폐기 |
| `POST /api/v1/admin/users/{userId}/temporary-passwords` | 관리자 세션 + 관리자 현재 비밀번호 확인 | 200 `{temporaryPassword}` 한 번만. 저장 자원이 없는 임시 자격 증명 발급이므로 POST 201/빈 본문 원칙의 명시적 예외 |

초기 가입의 Location은 로그인 이후 접근한다. 키 Location은 그 키의 식별 주소이며 이번 작업에서 단건 GET을 추가할 필요는 없다.
요청·응답 DTO와 성공·오류 계약은 OpenAPI로 명시한다. 임시 비밀번호 응답도 no-store이며 액세스 로그/APM 등에 응답 본문을 수집하지 않는다.

### 4. 클라이언트

- `pages/entry`에 첫 관리자 가입·로그인·강제 비밀번호 변경 화면, `pages/settings`에 내 비밀번호·API 키 관리 화면을 만든다. 위치와 공개 API는 페이지 우선 FSD를 따른다.
- 익명 사용자는 로그인/초기 설정으로, 정상 세션은 기존 앱 셸로, `mustChangePassword` 세션은 변경 화면으로 보낸다. 워크스페이스가 없는 상태를 정상으로 안내한다.
- 부모 loader가 세션을 읽고 capabilities를 함께 캐시한다. 화면은 실제 데이터 없는 Inbox·문서함을 완성된 업무 기능처럼 표시하지 않는다.
- 공통 HTTP 계층에 204·Location 검증·쿠키·CSRF 헤더를 추가한다. 동시에 시작한 명령은 CSRF 조회 하나를 공유하고 `AUTH_CSRF_INVALID` 응답만 토큰 갱신 후 한 번 재전송한다. 네트워크 오류나 일반 실패의 mutation을 자동 재시도하지 않는다.
- 401 세션 만료는 진행 중 쿼리 취소·캐시 파기 후 로그인으로 보낸다. 로그인 자격 증명 불일치는 폼에 표시하며 전역 401 처리에서 제외한다. 명시적 로그아웃도 캐시를 지운다.
- 키 이름·만료·에이전트 이름 입력, 키 원문 한 번 표시·복사, 목록·폐기를 구현한다. 원문을 URL·브라우저 영구 저장소·토스트·로그에 남기지 않고 화면을 떠나면 메모리에서 제거한다. 화면 자체의 API 호출은 Bearer를 쓰지 않는다.
- 관리자의 임시 비밀번호 발급 API는 구현하되 사용자 검색·관리 화면은 후속 멤버/운영 UI 작업에서 붙인다. T-002는 테스트 계정 fixture로 관리자 경로를 검증한다.
- 내 계정과 로그아웃 진입을 데스크톱 셸과 모바일 더보기에 연결한다. Astryx 컴포넌트는 CLI 확인 후 사용한다. dev 사용자 선택 로그인·자동 로그인은 추가하지 않는다.

## 하지 않는 것과 후속 연결

- 워크스페이스·프로젝트·멤버십 테이블, 초대 링크 발급·수락, 사용자 관리 전체 UI와 관리자 지정·해제.
- MCP 엔드포인트/도구 자체. Bearer 인증은 `/api/v1/me`로 검증하고 이후 MCP가 같은 주체와 Facade 인가를 사용하도록 둔다.
- OTP·SMTP 어댑터, 소셜 로그인, MFA, 비밀번호 재설정 이메일. 이번 capabilities의 `mail`은 false이며 SMTP가 설정돼도 구현 전에는 true로 바꾸지 않는다.
- 계정 삭제·이메일 변경·프로필 사진, 무단 관리자 자동 재생성, 운영 DB 수동 수정 스크립트.
- 유일한 관리자가 비밀번호를 잊고 유효 세션도 없는 경우의 오프라인 복구 명령은 별도 운영 작업이다. 공개 bootstrap 재개방으로 대신하지 않고 README에 한계를 적는다.
- 키별 scope, 프로젝트별 접근 제한, 사용자 정의 역할, 업무 기준 시간대 결정.
- 링크 모듈 의존 방향과 `record_session` 다중 애그리거트 트랜잭션은 해당 기능 전 결정할 사항으로 유지한다. 인증 작업의 선행 조건은 아니다.

API 키로 업무 쓰기 허용은 아직 업무 API가 없으므로 T-002에서 검증 완료라고 표시하지 않는다. 첫 업무 API/MCP 작업에 “동일 사용자의 세션/Bearer 역할 판정 일치·쓰기 성공” 수용 조건을 이어 붙인다.
워크스페이스 권한 표의 인가 테스트도 실제 워크스페이스가 생길 때 수행하며 T-002 통과로 대체하지 않는다.

- 커밋은 사용자가 요청할 때만 한다.

## 보안 근거 (2026-10-22 확인)

- [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html): MFA 없는 비밀번호의 길이, 로그인 실패 응답·재인증·잠금 검토 근거. 본 작업의 구체적인 수명·요청 제한 값은 제품 추천안이다.

- [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html): 로그인 CSRF, 서명·세션 결합 double-submit, Origin/Referer 검증과 토큰 전달 제한 근거.

### 검증 한계·후속 확인

- 브라우저에서는 새 비밀번호를 입력·제출하지 않았다. 가입/비밀번호 변경/키 생성·폐기 요청의 서버 동작은 HTTP 통합 테스트로 확인했다. **가입·새 비밀번호 제출, 키 생성→복사→화면 이탈→폐기의 전체 수동 클릭 시나리오는 추가 확인 항목**이다. 클립보드 권한 실패 시 직접 복사 안내를 제공한다.
- 워크스페이스·초대·역할 검사·업무 REST/MCP 쓰기는 이 작업의 구현/검증 범위가 아니다. T-003과 첫 업무 API/MCP의 수용 조건으로 넘긴다. 관리자 복구 API의 사용자 검색/운영 UI, OTP·SMTP, 유일한 관리자 복구 CLI도 후속이다.
- `npm audit`는 기존 개발 도구 의존성에서 high 6개를 보고했다(steiger의 glob 계열, Vite 개발 서버). 이번에 의존성을 추가/업그레이드하지 않았다. 강제 major 변경은 적용하지 않았고 개발 도구 갱신 작업으로 남긴다. Vite 번들 크기 경고와 Gradle/Mockito·jOOQ 분석 경고는 검사 실패가 아니다.
- 검증용 사용자·비밀번호·키는 별도 DB/볼륨의 fixture다. 기본 개발 DB에 테스트 계정을 넣지 않았다. 비밀값·토큰을 문서나 Git에 기록하지 않았다.
- 사용자 요청 전에는 커밋하지 않는다.
- 정리: 검증 컨테이너와 전용 Docker 볼륨은 제거했다. 자동 승인 검토가 `.tmp/t002-dev-data`의 재귀 삭제를 정책상 차단해, 해당 검증 DB/비밀값과 smoke 스크립트는 Git에서 무시되는 `.tmp/`에 남겼다. 기본 개발 DB 및 현재 개발 서버와는 분리되어 있다.
