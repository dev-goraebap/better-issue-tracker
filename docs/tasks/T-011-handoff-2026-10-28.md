## 1. BIT-99 배포 (0.15.0)

상세에서 제목·본문을 바로 고치고 저장 바로 저장한다. 편집 페이지는 없앴고 옛 `/edit` 주소는 상세로 넘긴다. 서버 변경과 마이그레이션은 없다(V26 그대로). 무엇을 했고 어떻게 확인했는지는 BIT-99 댓글에 있다.

1. 릴리스 업무를 만든다. 예: "0.15.0 릴리스와 운영 배포 (상세에서 바로 고치기)", 담당 me, 진행 중. 받은 번호(아래 `BIT-N`)를 이후에 쓴다.
2. `C:\tmp\bitbody`에서 `git push -u origin bit-99-inline-edit`.
3. PR을 연다. 제목에 `BIT-99`를 넣는다. CI(client·server)가 통과하면 `gh pr merge --merge`로 병합한다. 병합하면 BIT-99가 완료로 옮겨진다.
4. 배포 스킬 `.agents/skills/bit-release/SKILL.md`를 그대로 따른다.
   - main을 받는다. 검사: `server`에서 `./gradlew.bat check`, `client`에서 `npm run check`.
   - `node scripts/set-version.mjs 0.15.0`, 커밋 `chore: BIT-N release 0.15.0`, main 푸시.
   - 태그 `v0.15.0-rc.1`을 단다. `gh run watch`로 이미지가 만들어지기를 기다린다. 로컬 Docker에서 후보 이미지를 받아 띄우고 health·화면을 확인한다(포트 18080).
   - 같은 커밋에 `v0.15.0`을 단다. 이미지가 만들어지면 `gh release create v0.15.0 --verify-tag --generate-notes --title "BIT 0.15.0"`.
   - 로컬 Docker Desktop이 꺼져 있으면 사용자에게 켜 달라고 한다.
5. 운영 배포는 `docs/deployment.md`를 따른다. 지난 두 번(0.13.0·0.14.0)에 쓴 실제 방법은 다음과 같다.
   - 접속: `ssh -p 23022 dev-goraebap@220.80.109.248`(키 인증, `.local/home-deploy/README.md`). `sudo -n`이 된다.
   - 서버에는 GHCR 인증이 없다. 로컬에서 `docker save -o C:/tmp/bit-0.15.0.tar ghcr.io/dev-goraebap/better-issue-tracker:0.15.0`로 저장한다. `scp -P 23022`로 서버 **홈 디렉터리**에 보낸다. snap Docker는 `/tmp`를 따로 써서 그 파일을 못 읽는다. SHA-256을 비교한 뒤 `/snap/bin/docker load -i ~/bit-0.15.0.tar`, 리비전 라벨이 릴리스 커밋과 같은지 본다.
   - 배포 스크립트는 지난 것을 복사해 버전만 바꾼다: `cd ~/apps/bit && sed -e 's/0\.14\.0/0.15.0/g' -e 's/0\.13\.0/0.14.0/g' deploy-0.14.0.py > deploy-0.15.0.py`. `diff`로 바뀐 줄이 버전 9줄뿐인지 확인한다.
   - `sudo -n python3 deploy-0.15.0.py deploy <릴리스 커밋 SHA>`: 중지 → 전체 볼륨 백업 → compose 이미지를 0.15.0으로 저장 → `up --wait` → 데이터 보존·무결성 비교.
   - `sudo -n python3 deploy-0.15.0.py verify`. 공개 주소 `https://bit.goraebap.xyz/api/v1/health`가 UP이고 화면 번들에 `0.15.0`이 있는지 본다. MCP 조회가 되는지도 본다.
   - `sudo -n python3 deploy-0.15.0.py prune`(백업은 최근 5개만). 서버와 로컬의 tar 파일을 지운다.
6. 릴리스 업무에 태그·커밋·백업 위치·검증 결과를 댓글로 남기고 완료로 옮긴다.

## 2. BIT-89 업무 유형 마무리와 배포

워크스페이스가 업무 유형과 유형별 상위 규칙을 정한다. 서버는 규칙에 어긋나는 변경을 거절한다. 설계와 세부 결정은 D-104와 BIT-89 댓글(서버 구현 요약, 구현 중 정한 것)에 있다.

**들어 있는 것** (이 저장소 폴더, 커밋 전)
- 서버
  - 마이그레이션 `V27__work_item_types.sql`: 워크스페이스마다 기본 유형 넷을 넣고, 기존 작업은 '작업'이 된다.
  - 유형 모듈(`module/workitem`의 `WorkItemType*`), `SubtaskRuleSpi`, 권한 경로, MCP(`list_work_item_types`; `type`·`parent` 인자), MCP 안내문 두 줄.
  - 테스트. `gradlew check` 통과.
- 화면
  - 워크스페이스 설정 '업무 유형', '만들기 ▾'의 유형별 항목과 상위 고르기, 하위 만들기의 유형.
  - 상세·수정의 유형 바꾸기, 목록·카드의 유형 아이콘, 주소 필터, 활동 문장.
  - `npm run check` 통과.
- 문서: `docs/06-schema.md`, `docs/07-mcp.md`, `docs/decisions.md`(D-104·D-105·D-106), 배포 스킬 `skills/better-issue-tracker/SKILL.md`·`notes.md`.
  - 스킬에는 속성 정하기, 큰 일 나누기, 유형, "키는 만든 뒤에 쓴다", 도구 표 갱신이 들어 있다.

**할 일**
1. 1이 병합된 뒤 main을 이 브랜치에 합친다. 겹치는 곳:
   - `client/src/pages/project/work-item-edit/ui/EditForm.tsx`: 이 브랜치는 유형 고르기를 더했고, BIT-99는 파일을 지웠다. **지운 쪽을 따른다.** 유형은 상세 속성에서 바꾼다.
   - `client/src/widgets/work-item-detail/ui/WorkItemProperties.tsx`: BIT-99의 '종류' 속성과 이 브랜치의 '유형' 속성을 둘 다 남긴다.
   - `WorkItemDetail.tsx`, `DetailLayout`, `markdown-editor/*`: BIT-99 쪽 구조(InlineBody·저장 바)를 바탕으로 이 브랜치의 변경(유형 `typeId` 전달 등)을 옮긴다.
   - `docs/decisions.md`: D-107은 BIT-99에 들어갔다. 이 브랜치의 D-104~D-106을 그 뒤에 이어 붙인다. 번호 순서가 섞여도 내용은 그대로 둔다.
2. 화면을 **직접 띄워** 확인한다(아래 '로컬 환경'). 하위 에이전트가 검사만 돌렸고 실제 화면은 아무도 보지 않았다. 볼 것:
   - 설정의 유형 만들기·고치기·순서·삭제 막힘
   - 스토리를 상위 없이 만들 때의 거절 문장
   - 에픽 밑 스토리 만들기, 작업 밑 버그
   - 목록·보드·카드의 유형 아이콘 정렬
   - 활동의 '유형을 …로 바꿨습니다'
3. 하위 에이전트가 보고한 남은 점을 정리한다.
   - `openapi.json`의 `WorkItem.type`이 필수로 나온다(일정은 null). nullable로 고친다.
   - 상위 업무 고르기가 제목으로만 찾는다(키 `BIT-12`로는 못 찾음).
   - 유형 필터가 저장된 뷰에는 들어가지 않는다(주소 필터만).
   - FSD `@x` 교차 참조가 처음 쓰였다(`entities/work-item-type/@x/work-item.ts`). 이 셋은 결정으로 남길지 판단한다.
4. 커밋을 나눈다(서버 / 화면 / 문서·스킬). PR 제목에 `BIT-89`를 넣는다.
5. 배포는 1과 같다. 단 **V27 마이그레이션이 있다.**
   - 배포 스크립트 `deploy-0.x.py`의 `assert str(version) == '26'`을 `'27'`로 바꾼다.
   - 백업 비교 표(`TABLES`)에 `work_item_type`을 넣을지 판단한다.
   - 운영 워크스페이스 2개에 유형이 씨앗으로 들어가고, 기존 작업(약 215건)이 '작업'이 되는지 확인한다.
6. 배포 스킬 설치본(`.agents/skills`, `.claude/skills`)은 gitignore다. 세션을 시작할 때 동기화된다.

## 3. BIT-92 기본 라벨

설계는 BIT-92 설명과 D-105에 있다.
- 지울 수 없는 시스템 라벨을 없앤다. 워크스페이스를 만들 때 기본 라벨을 넣는다: 결정기록·회의록(문서용), 기능·개선·디자인(업무용).
- 기본 라벨은 '어느 기본 라벨인지' 표시(지금 `system_key` 자리)만 남는 평범한 라벨이다.
- 지우면 업무·문서와의 연결은 남기고 숨긴다. 설정의 '기본 라벨 되살리기'로 되살리면 연결도 돌아온다. 같은 이름의 라벨이 있으면 되살리지 않는다.
- 시스템 라벨에 기대던 곳을 기본 라벨 '결정기록'(표시 `decision`)으로 바꾼다.
  - 기본 뷰 '결정기록'의 필터: `WorkItemView.java`의 `Map.of("label", "system")`
  - 화면 템플릿: `entities/work-item/model/templates.ts`
  - 캘린더 색: `WorkItemCalendar.tsx`
  - MCP `list_labels` 설명
- 기존 워크스페이스에는 없는 기본 라벨만 넣는다. 운영 '고래밥 스튜디오'에는 지금 '결정기록'(시스템)과 'UI/UX'가 있다.
- 운영 업무 22개가 '결정기록' 라벨로 결정을 담고 있다. 라벨 ID가 바뀌면 안 된다.

## 4. BIT-91 업무 목록 개편

설계는 BIT-91 설명과 D-106에 있다.
- 데스크톱 목록 `entities/work-item/ui/WorkItemTable.tsx`(SheetTable)를 휴대폰 `WorkItemRows`와 같은 행 리스트로 합친다.
  - 왼쪽(폭 고정): 우선순위·키·상태·유형·제목·하위 진행도
  - 오른쪽(있는 것만): 라벨·PR·기한·사람·수정일
- 그룹 기준(없음·상태·사람·우선순위·유형·라벨·프로젝트)은 뷰에 저장한다. 서버 뷰 모델(`module/view`)과 마이그레이션이 필요하다.
- 하위 업무는 `parentId`(BIT-89)로 상위 밑에 들여 보인다. 그룹이 다르면 자기 그룹에 상위 이름을 붙인다.
- 참고 화면: Linear 이슈 목록과 Display 메뉴(사용자가 BIT-91 대화에 붙인 스크린샷).
