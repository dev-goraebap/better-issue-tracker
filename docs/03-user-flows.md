# 03. 사용자 흐름

원칙: **대부분의 작업은 가벼운 경로로 끝나고, 무거운 경로는 가끔.**
매번 결정·문서를 거치게 만들면 아무도 안 쓴다.

## A. 혼자 에이전트와 개발 (가장 자주)
1. 작업항목 BIT-42를 열거나, 없으면 에이전트에게 바로 말한다.
   - 작업항목 없이 시작하면 에이전트가 먼저 작업항목을 만든다.
2. 에이전트가 MCP로 작업항목·관련 결정·문서를 읽고 작업한다.
3. 커밋 메시지에 BIT-42 포함 → 웹훅으로 자동 연결.
4. 세션 끝에 "오늘 정한 거 기록해줘" → 세션 요약 + 결정(있으면) 저장.

사용자가 화면을 거의 안 열어도 기록이 쌓인다. **여기가 매끄러우면 나머지는 따라온다.**

## B. 버그·발견 처리 (자주, 가벼움)
발견 → 작업항목 생성(트리거: 발견) → 수정·커밋 → 종료.
결정도 문서 개정도 없는 경우가 대부분. 고치다가 설계 문제로 번지면 결정을 만들고 C로.

## C. 요구 변경 (가끔, 무거움)
고객·PM 요청 → 회의(또는 혼자 검토 세션) → 결정 D-007 확정
→ 영향받는 문서 개정(요구사항서, 설계서) → 작업항목 여러 개로 분해
→ 각각 개발·커밋 → 결정 화면에 "이행 2/3"처럼 진행이 보이고, 모두 끝나면 "이행 3/3" (D-012).
회사 업무의 주 흐름. 산출물 관리가 가장 중요해지는 지점. 문서 개정 부분은 관리 문서(이후, D-019)가 있어야 완성된다.

## D. 역추적 "이거 왜 이렇게 돼 있지?" (가끔, 가치 최대)
코드 한 줄 / 문서 한 항목 → 커밋 → 작업항목 → 결정 → 원래 세션·회의록.
몇 달 뒤의 본인·동료·에이전트가 쓴다. 이 플랫폼을 만드는 진짜 이유.

## E. 오랜만에 프로젝트 복귀
프로젝트 열기 → 최근 결정, 진행 중 작업항목, 최근 개정 문서 요약 확인
→ 에이전트에게 "여기서 이어서 하자".
개인 프로젝트를 여러 개 돌리므로 자주 쓰인다. 프로젝트 첫 화면을 이 용도에 맞춘다.

## F. 릴리스·납품 (이후)
릴리스 생성 → 현재 확정된 문서 버전 목록 + Git 태그를 기준선으로 스냅샷 → 산출물 묶음 내보내기.
"이 버전 코드는 어떤 설계서 기준이었나?"에 바로 답할 수 있다.
