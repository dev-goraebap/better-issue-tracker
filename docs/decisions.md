# 결정 기록

형식: 무엇을 / 왜 / 기각한 대안. 상태: 제안 → 확정 → 대체됨.
출처는 모두 2026-10-22 Claude와의 기획 세션.

---

## D-001. 기존 시스템에 Office 문서를 Git으로 넣지 않는다 — 확정
- **왜**: 원하는 건 문서를 Git에 넣는 게 아니라 흩어진 맥락(코드·이유·근거)을 잇는 것.
  docx/xlsx는 Git에서 diff·merge가 안 되어 얻는 게 적다.
- **기각한 대안**: Git LFS + textconv diff로 문서를 저장소에 보관 → 보관은 되지만 추적성 문제는 그대로.

## D-002. 기존 도구 위 연결층 대신, 올인원 플랫폼을 만든다 — 확정
- **왜**: 개인 프로젝트에선 사용자가 본인뿐이라 "아무도 안 넘어오는 또 하나의 장소" 문제가 없다.
  회사 쪽은 사용자가 만든 사내 플랫폼이 이미 운영 중이고 Redmine 이전까지 합의됨.
  회사 플랫폼과의 연동도 허락받음(연동은 나중에).
- **기각한 대안**: GitLab/Redmine/SharePoint는 그대로 두고 MCP 연결층만 만들기
  → 회사 환경에선 유효하지만 개인 프로젝트의 문제를 풀지 못함. 연동 시 참고.

## D-003. Git hosting은 포함하지 않는다 — 확정
- **왜**: 재구현 비용 대비 얻는 게 적다. 플랫폼은 Git을 "소유"하지 않고 "참조"한다.
  웹훅으로 커밋·MR을 받아 작업항목에 연결하면 GitLab·Gitea·GitHub 모두 붙일 수 있다.
- **기각한 대안**: Gitea 같은 경량 Git 엔진을 내장.

## D-004. Kaneo를 베이스로, 기술 스택은 사용자의 평소 스택으로 — 확정
- **왜**: Kaneo는 프로젝트별 작업항목에 집중한 경량 오픈소스(MIT), 자체 MCP 서버도 있다.
  UI/개념은 Kaneo를, 코드 구조와 규칙은 사용자의 예시 프로젝트를 따른다.
  (Kaneo MCP 서버는 실제로 있음: stdio 패키지와 인스턴스 내장 HTTP 두 형태 — 2026-10-22 확인)
- **기각한 대안**: 기획 세션에서 기록하지 않음.
- **후속**: Kaneo 코드 분석, 예시 프로젝트 규칙 정리 → D-009, D-010, `conventions.md`로 완료

## D-005. "결정"과 "세션"을 독립 엔티티로 둔다 — 확정
- **왜**: 트리거와 변경 사이에는 항상 결정이 있다. 이슈에 뭉치면 "왜?"를 찾기 어렵다.
  혼자 작업할 땐 에이전트 세션이 곧 회의이므로, 회의록과 세션 요약을 같은 개념(Session)으로 다룬다.
- **기각한 대안**: 결정을 작업항목 댓글/필드로만 남기기.

## D-006. 에이전트를 1순위 사용자로, API/MCP 먼저 — 확정
- **왜**: 출발 동기가 "로컬 에이전트에게 맥락 전달이 번거롭다"였다.
  기록도 사람이 아니라 에이전트가 대부분 남기게 한다.
- **기각한 대안**: 기획 세션에서 기록하지 않음.

## D-007. 산출물은 원본 + 텍스트 변환본을 함께 저장하고, 확정본은 불변 — 대체됨 (D-093)
- **왜**: 원본은 제출용, 텍스트는 검색·diff·에이전트용. 바이너리라 병합이 불가능하므로
  통제는 잠금·사유 필수·확정본 불변으로 한다. 통제 강도는 프로젝트별 모드(개인/팀).
- 폴더 감시는 선택 기능으로 두되, 바로 버전화하지 않고 반영 대기함을 거친다.

## D-008. 프로젝트 이름은 lite-alm — 대체됨 (D-024)
- **왜**: 제품 분류가 ALM(애플리케이션 생애주기 관리)에 가깝고, 기존 무거운 ALM과 달리 경량.
  정식 제품명은 나중에 정한다.
- **기각한 대안**: agent-alm, devtrace, 실마리, Asterism, Lyra, Helix 등.
  AIDLC를 이름에 직접 넣는 것은 AWS 용어에 묶여 보여서 제외.

## D-009. Kaneo는 포크하지 않고 개념·화면 구조만 차용한다 — 확정
- **무엇을**: 인스턴스 생성(첫 가입자 = 관리자), 워크스페이스 단위로 여러 프로젝트를 관리하는 계층,
  워크스페이스 멤버·역할·초대, 작업 키 `{프로젝트 키}-{번호}`, 보드/리스트/백로그/타임라인, 사이드바·설정 메뉴 구조를 대부분 차용.
- **왜**: Kaneo는 TypeScript(Hono + Drizzle + PostgreSQL + better-auth)이고 BIT는 사용자 스택(D-010)으로 만든다.
  스택이 달라 코드를 이어 쓸 수 없다. 대신 검증된 개념과 화면 흐름은 그대로 가져온다.
- **기각한 대안**: Kaneo를 포크해 확장 → 사용자가 평소 쓰지 않는 스택을 유지해야 하고, 결정·세션·산출물 추가 시 Kaneo의 task 중심 테이블(`activity`, `task_relation`)을 크게 고쳐야 함.
- **차용하지 않는 것**: 작업별 라벨 사본 행, `task.status` 문자열과 `columnId` 이중 저장, 별도 Expo 네이티브 앱.

## D-010. 스택은 React + Astryx / Spring Boot, 구조와 관리 방법론은 SandboxHr를 따른다 — 확정
- **왜**: 사용자의 평소 스택. Astryx는 적응형(모바일) UI 대응이 잘 되어 있다.
  SandboxHr의 에이전트 스킬에 구조·규칙·스킬 관리 방법이 정리되어 있고, Kaneo와 전체 레이아웃이 비슷해 옮기기 쉽다.
- **결과**: DB는 SandboxHr를 따라 SQLite 파일 하나(Kaneo는 PostgreSQL). 셀프호스팅 컨테이너 하나 원칙과 맞는다.
  쓰기가 직렬화되므로 트랜잭션 안에서 외부 호출(문서 변환 등) 금지 규칙을 지킨다. 세부는 `conventions.md`.
- **기각한 대안**
  - Kaneo 스택(TypeScript, shadcn 계열 UI) 채택.
  - 백엔드를 Go + sqlc로(2026-10-22 검토): 써 보고 싶어 검토했으나 사용자가 Spring Boot 유지로 되돌렸다. 바꾸면 SandboxHr 백엔드 규칙·스킬(conventions 1·3절)을 새로 써야 한다.

## D-011. 프로젝트 키는 바꿀 수 있고, 옛 키는 별칭으로 영구 보관한다 — 확정
- **무엇을**: 작업항목 키는 `{프로젝트 키}-{번호}`(예: `BIT-42`). 프로젝트 키를 바꾸면 옛 키를 별칭 테이블에 남긴다.
  - 웹훅 파싱·검색·URL은 현재 키와 별칭을 모두 인식한다. 화면과 새 참조에는 현재 키만 쓴다.
  - 키 중복 검사는 같은 워크스페이스의 현재 키 + 별칭 전체를 대상으로 한다. 별칭으로 쓰인 키는 다른 프로젝트가 가져갈 수 없다.
  - 작업항목 번호는 키가 바뀌어도 그대로다(`BIT-42` → `BT-42`).
  - 구현: 현재 키와 별칭을 `project_key` 테이블 하나에 `is_current`로 구분해 두고, 워크스페이스 안 고유를 DB가 지킨다 (`06-schema.md`).
- **왜**: 커밋 메시지·브랜치 이름은 푸시 후 고칠 수 없다. 키를 바꿔도 과거 참조가 살아 있어야 역추적(흐름 D)이 된다.
  동시에 프로젝트 이름·성격이 바뀌면 키도 바꿀 수 있어야 한다.
- **기각한 대안**
  - 생성 후 변경 불가: 가장 단순하지만 오타나 프로젝트 성격 변화를 바로잡을 수 없다.
  - Kaneo 방식(변경 허용, 옛 키 버림 — `apps/api/src/project/controllers/update-project.ts`): 키를 바꾸는 순간 과거 커밋 참조가 끊긴다.

## D-012. 결정의 이행 진행은 상태로 두지 않고 파생 작업항목에서 계산한다 — 대체됨 (D-094)
- **무엇을**: 결정 상태는 `제안 → 확정 → 대체됨` 그대로. 화면에는 "이행 2/3"(파생 작업항목 종료 수 / 전체 수)을 표시한다.
  작업항목을 다시 열면 숫자도 따라 돌아간다. 파생 작업항목이 없는 결정은 "해당 없음".
- **왜**: 상태값을 따로 두면 작업항목을 다시 열었을 때 결정만 "이행됨"으로 남는 식으로 어긋난다. 계산값은 어긋날 수 없다.
- **감수하는 것**: 작업항목 없이 지키기만 하는 결정(예: "이 라이브러리는 쓰지 않는다")은 이행 여부를 표시할 수 없다.
- **기각한 대안**
  - "이행됨" 상태 추가(사람·에이전트가 직접 변경): 작업항목 상태와 어긋날 수 있다.
  - 계산 + 모두 끝나면 상태 변경 제안: 상태값과 계산값을 둘 다 만들어야 해서 가장 무겁다.

## D-013. 산출물 초안은 한 칸에 덮어쓰고, 버전 번호는 확정할 때 붙인다 — 대체됨 (D-093, 관리 문서는 미정)
- **무엇을**: 산출물마다 초안은 최대 1개. 다시 올리면 덮어쓴다. 확정할 때 번호를 붙인다
  (기본 작은 개정 v1.0 → v1.1, 확정하는 사람이 큰 개정 v2.0 선택 가능). diff는 직전 확정본 ↔ 현재 초안.
- **왜**: 개인 프로젝트의 주 경로는 에이전트가 같은 문서를 여러 번 다듬어 올리는 것이다.
  중간 초안까지 모두 남기면 원본 파일과 행이 빠르게 쌓이는데, 나중에 필요한 것은 확정본끼리의 이력이다.
  확정본 번호에 구멍이 없어 개정이력표가 깔끔하다.
- **감수하는 것**: 중간 초안으로는 되돌릴 수 없다.
- **기각한 대안**
  - 업로드마다 리비전(r1, r2 …)을 쌓고 확정본에만 공식 번호: 되돌리기는 되지만 저장 공간·정리 규칙·두 종류 번호가 생긴다.
  - 올릴 때마다 공식 번호 소비(v1.1, v1.2 …): 확정 이력에 번호 구멍(v1.0 다음 v1.3)이 생긴다.
- **번호 규칙**(작은/큰 개정 선택)은 관례에 따라 정했고 따로 묻지 않았다.
- **적용 시점**: 관리 문서(이후, D-019)에 적용되는 설계다.

## D-014. 소속 관계는 FK, 왜·근거 관계는 범용 Link 테이블 하나에 둔다 — 확정
- **무엇을**: 프로젝트의 작업항목, 산출물의 버전 같은 소속 관계는 각 테이블에 FK로 둔다.
  출처(세션→결정), 파생(결정→작업항목), 개정(작업항목→산출물 버전), 구현(커밋→작업항목), 대체(결정→결정),
  작업항목끼리의 관계(Kaneo의 blocks/related/subtask)는 모두 Link 하나에 `relation` 이름과 함께 둔다.
- **왜**: 역추적(흐름 D)과 연결 타임라인, MCP 맥락 묶음은 Link 표 하나만 따라가면 된다.
  새 엔티티나 관계 종류가 생겨도 표를 늘리지 않는다. 기본 목록 화면은 FK로 빠르고 DB 무결성이 지켜진다.
- **감수하는 것**: Link는 대상 종류가 여럿이라 DB가 대상 존재를 검사하지 못한다. 생성 시 검사와 삭제 시 처리를 애플리케이션이 맡는다.
- **기각한 대안**
  - 관계마다 전용 표: DB가 무결성을 지켜 주지만 관계 종류마다 표가 늘고(예시 하나에서만 4개), 역추적이 모든 표를 합쳐야 한다.
  - 소속까지 전부 Link: 구조는 균일하지만 기본 조회마다 Link를 거치고, 핵심 관계의 DB 무결성을 잃는다.

## D-015. 문서함은 워크스페이스에 하나, 프로젝트는 라벨로 연결한다 — 대체됨 (D-093)
- **무엇을**: 워크스페이스마다 문서함 하나. 파일 탐색기처럼 폴더를 자유롭게 만들고 산출물을 넣는다.
  산출물에 프로젝트 라벨을 0개 이상 붙이고, 프로젝트 화면의 산출물 목록은 라벨로 거른다. 문서 ID는 워크스페이스 안에서 고유.
- **왜**: 문서 관리가 프로젝트와 별도로 돌아가는 경우가 많다(회사 프로젝트에 한정하지 않음).
  폴더는 사용자의 정리 구조이고 프로젝트 소속과 묶이지 않아야 한다. 공통 문서도 라벨을 여러 개 붙이면 된다.
- **감수하는 것**: 라벨을 빠뜨린 문서는 프로젝트 화면에 안 보인다. 팀 모드에서 프로젝트별 접근 제한을 문서마다 라벨로 계산해야 한다.
- **기각한 대안**
  - 프로젝트마다 문서함: 공통 문서를 둘 곳이 없다.
  - 프로젝트마다 문서함 + 워크스페이스 공통 문서함: 폴더 하나에 여러 프로젝트 문서를 섞을 수 없다.
- **이후**: 문서함별 관리가 필요해지면 프로젝트별 문서함을 추가한다.
- D-014의 FK 목록에서 Artifact의 소속을 Project → Workspace(문서함)로 바꾼다.

## D-016. 산출물은 정본 하나 + 플랫폼이 만드는 파생본으로 관리한다 — 대체됨 (D-093, Git md 참조는 미정)
- **무엇을**: 산출물마다 정본은 하나. 정본 종류는 업로드 파일 / 플랫폼 Markdown / Git 저장소 Markdown.
  - 업로드 파일(docx·xlsx 등): 업로드 후 텍스트 사본을 자동 변환. 사람이 직접 올려도 에이전트를 거치지 않아도 된다.
    변환 도구가 지원하는 형식만 변환하고, 이미지·zip 등은 원본만 둔다.
  - Git 저장소 Markdown(아키텍처 문서, 에이전트 스킬 등): 플랫폼은 복사하지 않고 경로 + 커밋을 참조한다. 제출용 PDF는 요청할 때 만든다.
  - 파생본은 사람이 고치지 않고 언제든 다시 만들 수 있는 캐시다.
  - 화면에는 산출물 한 줄만 보이고 정본 종류는 배지, 파생본은 버튼으로 노출한다.
- **왜**: 원본이 docx면 Markdown은 사본이고, 개발 환경에 md가 있으면 반대로 md가 정본이다.
  어느 쪽이든 "정본 하나에서 파생"으로 보면 한 모델로 다룰 수 있고, 원본과 사본이 목록을 어지럽히지 않는다.
  Git 문서를 복사하지 않는 것은 D-003(Git은 참조)과 같은 원칙.
- **감수하는 것**: 1차 범위에 Git 저장소 파일 읽기와 PDF 생성이 추가된다(웹훅 연동만으로는 파일 내용을 받지 못함).
- **기각한 대안**
  - 모든 문서를 Markdown으로 관리: docx·xlsx 원본을 제출용으로 유지해야 해서 불가능.
  - Git 문서도 플랫폼에 복사해 보관: 저장소와 플랫폼 두 곳에서 내용이 갈라진다.
  - 원본과 텍스트 사본을 별개 파일로 목록에 노출: 화면이 지저분하고 어느 쪽이 정본인지 헷갈린다.

## D-017. 에이전트 진입 문서는 AGENTS.md 하나만 둔다 — 확정
- **무엇을**: 프로젝트 규칙은 `AGENTS.md`에만 쓰고, `CLAUDE.md`·`CLAUDE.local.md`는 두지 않는다.
- **왜**: 코드 작업은 Codex에게 맡기고, 기획·검토는 Claude Code와도 한다. Codex는 `AGENTS.md`를 읽는다.
  Claude Code도 v2.1.277부터 `CLAUDE.md`가 없으면 `AGENTS.md`를 직접 읽는다 (공식 문서 code.claude.com/docs/en/memory, 2026-10-22 확인. 설치 버전 2.1.296).
- **주의**: 작업 디렉터리나 상위에 `CLAUDE.md` 또는 `CLAUDE.local.md`가 하나라도 생기면 Claude Code는 `AGENTS.md` 대신 그것만 읽는다.
  사용자 전역 `~/.claude/CLAUDE.md`는 이 판정에 들어가지 않고 함께 로드된다.
- **기각한 대안**
  - `CLAUDE.md`에 `@AGENTS.md` 한 줄 두기(SandboxHr 방식): 동작하지만 이제 필요 없는 파일이다. 처음엔 Claude Code가 `AGENTS.md`를 못 읽는다고 잘못 알고 이렇게 했다가 되돌렸다.
  - 두 파일에 같은 내용 쓰기: 한쪽만 고쳐져 갈라진다.

## D-018. 문서함 파일은 일반 파일과 관리 문서로 나누고, 문서마다 정하며 기본은 일반 파일이다 — 대체됨 (D-093)
- **무엇을**: 일반 파일은 덮어쓰기만 하는 보관용. 관리 문서는 문서 ID·버전·개정 사유·변경 요약·버전 비교가 붙는다.
  올리면 일반 파일이고, 필요한 문서만 관리 문서로 전환한다(전환 순간의 파일이 v1.0). 에이전트는 처음부터 관리 문서로 등록할 수 있다.
- **왜**: 회의 자료·참고 PDF·스크린샷까지 버전과 사유를 요구하면 무겁다("가벼움 유지"). 문서함이 워크스페이스에 하나라서 성격이 다른 파일이 섞인다.
- **감수하는 것**: 사람이 전환을 잊으면 중요한 문서도 이력이 남지 않는다. 목록에 두 종류가 섞여 배지로 구분해야 한다.
- **기각한 대안**
  - 폴더마다 설정: 관리 문서를 설정이 꺼진 폴더로 옮길 때의 규칙이 더 필요하다.
  - 문서마다, 기본 관리 문서: 가볍게 쓰려는 사용자가 매번 끄거나 사유·요약을 요구받는다.

## D-019. 1차에는 일반 파일만 만들고, 관리 문서는 이후로 미룬다. 스키마와 링크는 나중을 대비해 둔다 — 대체됨 (D-093)
- **무엇을**
  - 1차: 문서함·폴더·프로젝트 라벨, 업로드 + 텍스트 자동 변환, Git md 정본 참조 + PDF, 작업항목·결정과의 링크.
  - 이후: 관리 문서 전환, 초안/확정과 버전 번호(D-013), 개정 사유·변경 요약 필수, 버전 비교, 개정이력표, 개인 모드 변경 통제.
  - 관리 문서의 추적 단위는 **버전 + 위치 메모**(예: v1.3, "3.2항"). 문서 안 항목 단위 추적은 하지 않는다.
  - 대비: Artifact/ArtifactVersion 테이블을 1차부터 나눠 둔다(산출물당 버전 1행, 덮어씀). Link에 `artifact_version_id`, `anchor` 칸을 비워 둔다.
- **왜**: 1차 목표(개인 프로젝트)의 자주 쓰는 흐름 A·B·D·E는 버전 없이 동작한다. 주 문서인 Git md는 이력을 Git이 남긴다.
  docx·xlsx의 diff는 변환 텍스트 기준이라 정확하지 않아, 버전 관리를 붙일 때는 변경 요약이 그 기록을 대신한다.
  스키마와 링크 칸을 미리 두면 나중에 테이블을 쪼개는 마이그레이션 없이 붙일 수 있다.
- **감수하는 것**: 1차 기간에 덮어쓴 업로드 파일의 예전 내용은 남지 않는다. 1차에 만든 링크는 버전이 비어 있어 영향 알림 대상에서 빠진다.
  흐름 C(요구 변경 → 문서 개정)는 관리 문서가 생겨야 완성된다.
- **기각한 대안**
  - 1차부터 모든 문서 버전 관리: 1차 범위가 크고, 버전이 필요 없는 파일까지 무겁게 만든다.
  - md 정본만 버전 관리: 회사 업무의 산출물은 대부분 docx·xlsx라서 정작 필요한 쪽이 빠진다.
  - 버전 관리를 영영 빼기: "어느 버전이 어떤 코드의 기준이었나"를 추적한다는 출발 문제(01-vision)가 남는다.
  - 항목 단위 추적: docx·xlsx 변환으로는 항목을 안정적으로 나눌 수 없어 작성 규칙(제목 스타일, 행 ID)을 강제해야 한다.

## D-020. 활동 기록과 댓글은 작업항목에 묶지 않고 대상 종류를 일반화한다 — 확정
- **무엇을**: `activity`와 `comment`에 `target_type`, `target_id`를 두어 작업항목·결정·세션·산출물 어디에나 붙인다.
- **왜**: 연결 타임라인과 역추적에 결정·산출물의 이력도 나와야 한다. Kaneo의 `activity`·`comment`는 작업에만 묶여 있어 그대로는 담을 수 없다.
  Link를 일반화한 D-014와 같은 판단이다.
- **감수하는 것**: 대상 존재를 DB FK로 검사하지 못한다(애플리케이션이 검사).
- **기각한 대안**: 엔티티마다 활동·댓글 테이블(`decision_comment` 등) → 테이블이 엔티티 수만큼 늘고 타임라인이 그것을 모두 합쳐야 한다.

## D-021. 에이전트는 별도 계정이 아니라 사람의 API 키로 움직이고, 키에 에이전트 이름을 남긴다 — 확정
- **무엇을**: `iam_api_key.agent_name`(예: `codex`, `claude-code`). 에이전트가 만든 기록은 키 주인을 `created_by`/`actor_id`로,
  에이전트 이름을 `*_agent` 열로 남긴다. 화면에는 "홍길동 (codex)".
- **왜**: 에이전트가 한 일의 책임은 그 에이전트를 돌린 사람에게 있다. 권한도 그 사람의 워크스페이스 역할을 그대로 쓰면 되어 권한 모델이 늘지 않는다.
  그래도 "누가 직접 했나 / 어느 에이전트가 했나"는 구분되어야 기록을 믿을 수 있다.
- **감수하는 것**: 에이전트별로 권한을 따로 좁힐 수 없다(키 단위 범위 제한은 나중에 키에 붙일 수 있음).
- **기각한 대안**: 에이전트를 봇 사용자 계정으로 만들기 → 멤버·역할·초대를 에이전트마다 관리해야 하고, 누가 시킨 일인지가 흐려진다.

## D-022. MCP는 인스턴스 내장 HTTP 하나로, 사람이 읽는 참조와 맥락 묶음 중심의 도구 24개로 시작한다 — 확정
- **무엇을** (`07-mcp.md`)
  - `/api/mcp` Streamable HTTP + API 키 Bearer 인증(D-021). stdio 패키지는 만들지 않는다.
  - 도구는 UUID 대신 `BIT-42`, `D-007`, `S-003` 같은 참조를 받는다(별칭 키도 받음).
  - `get_work_item_context`(작업항목 + 결정·기각 대안 + 근거 문서 + 커밋), `record_session`(세션과 결정을 한 번에), `trace`(역추적)를 중심에 둔다.
  - 1차 MCP에는 삭제 도구가 없다(보관·해제만). 바이너리 업로드는 MCP가 아니라 웹·REST.
- **왜**: 출발 동기가 "사람이 맥락 배달부가 된다"였다. 에이전트가 도구를 여러 번 조합해야 맥락이 모이면 빠뜨리기 쉽다.
  도구 수가 많을수록 에이전트가 고르기 어려워져, Kaneo의 비슷한 도구들(상태·담당자·마감일 각각, 관계 도구들)을 합쳤다.
  Spring Boot 서버 안에서 Facade를 바로 부르면 별도 클라이언트 배포가 필요 없다.
- **감수하는 것**: stdio만 지원하는 MCP 클라이언트는 붙이지 못한다. 잘못된 기록을 에이전트가 직접 지울 수 없어 사람이 웹에서 정리해야 한다.
- **기각한 대안**
  - Kaneo처럼 stdio 패키지 + 내장 HTTP 두 형태: Java 서버 옆에 Node 패키지를 따로 배포·관리해야 한다.
  - Kaneo 도구 구성을 그대로 따르기(약 40개, 작업 중심): 결정·세션·산출물·추적 도구가 없고, 비슷한 도구가 많다.
  - UUID로만 가리키기: 에이전트가 사람의 말("BIT-42")을 매번 조회로 바꿔야 한다.

## D-023. 명세와 결정 기록은 docs/ Markdown에 두고, 플랫폼이 동작하면 BIT 자신으로 옮긴다 — 확정
- **무엇을**: Gitifact를 쓰지 않는다. 결정은 `docs/decisions.md`, 명세는 `docs/0N-*.md`에 계속 쓴다.
  플랫폼이 동작하면 결정은 BIT의 결정 엔티티로 옮기고, 문서는 Git md 정본(D-016)으로 참조한다.
- **왜**: BIT 자체가 "결정과 문서가 사는 집"이라 Gitifact와 역할이 겹친다. 겹친 채로 두면 결정을 어디에 쓸지 계속 갈리고,
  BIT의 결정 기능을 자기 프로젝트에 쓰지 못한다(도그푸딩 불가). 옮기는 일은 한 번이면 된다.
- **감수하는 것**: CLI 검사·ID 발급이 없어 Codex는 AGENTS.md의 글 규칙만 따른다. 형식이 흐트러져도 기계가 잡아 주지 않는다.
- **기각한 대안**
  - Gitifact 도입 후 계속 사용: 결정 기록처가 둘이 된다.
  - Gitifact를 지금 쓰고 나중에 BIT로 옮기기: 옮기는 일이 두 번이다.

## D-024. 제품 가칭은 better-issue-tracker, 줄여서 BIT — 확정 (D-008 대체)
- **무엇을**: 문서·코드의 제품 이름은 BIT. 코드 식별자(스킬 이름 `bit-*`, 이미지·볼륨·쿠키·API 키 접두사 등)도 `bit` 계열로 쓴다.

## D-025. Java 루트 패키지는 io.github.goraebap.bit — 확정
- **왜**: 개인 프로젝트가 1차 목표라 개인 계정 기준으로 한다. GitHub 계정을 뒤집은 이름은 오픈소스로 낼 때의 관례다.
  패키지는 나중에 바꾸면 모든 파일을 옮겨야 해서 저장소 초기화 전에 정했다.
- **기각한 대안**
  - `dev.goraebap.bit`: 실제로 가진 도메인이 아니면 관례상 이름일 뿐이다.
  - `store.hohoco.bit`(SandboxHr와 같은 회사 도메인): 개인 프로젝트인데 회사 소유처럼 보인다. 회사 허락은 연동까지만 받았다.

## D-026. 저장소는 개인 GitHub, CI는 GitHub Actions. Git 웹훅도 GitHub부터 붙인다 — 확정
- **왜**: 개인 프로젝트이고 패키지 이름(D-025)도 GitHub 계정 기준이다. BIT를 만드는 저장소가 첫 도그푸딩 대상이므로,
  그 저장소의 호스팅이 웹훅 첫 연동 대상이 된다. GitLab·Gitea는 그다음.
- **감수하는 것**: SandboxHr의 `.gitlab-ci.yml`을 그대로 못 쓰고 Actions로 다시 쓴다. 비공개 저장소면 Actions 무료 시간에 한도가 있다.
- **기각한 대안**
  - 사내 GitLab + GitLab CI: 개인 프로젝트 코드가 회사 서버에 올라간다.
  - GitHub만 쓰고 CI는 나중에: Codex가 올린 변경을 기계가 검사하지 않아, 검사를 빠뜨린 커밋이 쌓일 수 있다.

## D-027. 로그인은 이메일 + 비밀번호가 기본이고, 메일 서버가 있으면 이메일 OTP를 켠다 — 확정
- **무엇을**: 비밀번호는 bcrypt 해시(Spring Security 기본), 연속 5회 실패 시 15분 잠금. SMTP를 설정하면 OTP 로그인과 비밀번호 재설정 메일이 켜진다.
  SMTP가 없으면 인스턴스 관리자가 임시 비밀번호를 발급한다. 에이전트는 API 키(D-021). 테이블은 `06-schema.md` 1절.
- **왜**: 개인 셀프호스팅에서 메일 서버 없이 도커만 띄워도 바로 써야 한다. 회사 환경처럼 메일이 있으면 SandboxHr의 OTP 방식도 쓸 수 있다.
- **감수하는 것**: SandboxHr에 없던 비밀번호 저장·잠금을 새로 만든다. 메일 서버가 없으면 비밀번호 분실 시 관리자가 직접 처리한다.
- **기각한 대안**
  - 이메일 OTP만(SandboxHr 그대로): 설치마다 메일 서버가 필수이고, 메일이 막히면 아무도 로그인하지 못한다.
  - GitHub 로그인만: 설치마다 OAuth 앱 등록과 외부에서 접근되는 콜백 주소가 필요하고, 회사 사용자에게 또 다른 방식이 필요하다.

## D-028. Git 정본은 저장소마다 넣은 읽기 전용 토큰으로 호스팅 API에서 읽는다 — 확정
- **무엇을**: 저장소를 연결할 때 읽기 전용 토큰(GitHub fine-grained 등)을 받아 암호화해 저장한다.
  커밋 웹훅이 오면 바뀐 md만 API로 받아 산출물의 현재 내용을 갱신한다. GitHub부터, GitLab·Gitea는 같은 방식의 어댑터를 더한다.
- **왜**: 가장 단순하고 컨테이너에 git이 필요 없다. 세 호스팅 모두 "토큰 + 자기 API"로 같은 모양이라 어댑터만 바꾸면 된다.
  Kaneo 연동은 브랜치·PR만 잇고 파일은 읽지 않아 참고할 구현이 없다.
- **감수하는 것**: 토큰 만료 시 사람이 바꿔 넣어야 한다(만료 전 알림). 토큰 암호화 저장이 필요하다. 호스팅마다 어댑터를 쓴다.
- **기각한 대안**
  - GitHub App: 셀프호스팅 인스턴스마다 사용자가 App을 만들어야 하고, GitLab·Gitea는 어차피 토큰 방식이 따로 필요하다.
  - 서버에 clone: 컨테이너에 git과 디스크 공간이 필요하고, 비공개 저장소는 여전히 인증 정보가 필요하다.

## D-029. 파일 저장소는 로컬이 기본 어댑터이고, S3 호환 저장소는 설정으로 바꾼다 — 확정
- **무엇을**: SandboxHr `file` 모듈 구조(저장소 인터페이스 + 어댑터)를 그대로 쓴다. 기본은 데이터 볼륨(로컬).
  S3 호환 어댑터 하나로 AWS S3·Cloudflare R2·MinIO를 모두 지원한다(접속 주소·지역 등 설정만 다름. R2는 region `auto`).
- **왜**: 문서함이 1차 핵심이라 도커만 띄워도 업로드가 되어야 한다. 사용자는 실제로 R2를 쓰는데, R2는 S3 API라 어댑터를 따로 만들 필요가 없다.
- **감수하는 것**: 로컬이면 볼륨 백업을 사용자가 챙긴다. 두 어댑터를 모두 테스트한다.
- **기각한 대안**
  - Kaneo처럼 저장소 설정 전에는 업로드 꺼짐: 설정 전에는 문서함에 파일을 올릴 수 없고, 개인 설치에도 저장소를 따로 띄워야 한다.
  - 로컬도 설정해야 켜짐: 처음 띄울 때 환경변수를 빠뜨리면 업로드가 꺼진 채로 시작한다.
  - S3와 R2 어댑터를 따로: 같은 API라 중복이다.

## D-030. 외부에 기대는 기능은 인터페이스 + 어댑터로 나누고, 설정이 없으면 그 기능만 꺼진다 — 확정
- **무엇을**: 메일(D-027), Git 연동(D-028), 파일 저장소(D-029), 문서 텍스트 변환, PDF 생성.
  설정이 없거나 연결이 안 되면 해당 기능만 꺼지고 서버는 정상 실행된다. 서버는 켜진 기능 목록을 API로 알려 주고(Kaneo `hasImageUploads`와 같은 방식),
  화면은 그 값을 보고 버튼을 숨긴다. MCP 도구도 꺼진 기능이면 그 이유를 오류로 돌려준다.
- **왜**: 사용자 요청("기능이 연결되지 않더라도 실행에 문제 없는 게 좋다"). 셀프호스팅 설치마다 갖춘 것이 다르고, 인터페이스를 분리하면 어댑터를 바꾸거나 늘리기 쉽다.
- **예외**: 파일 저장소는 로컬 어댑터가 내장되어 있어 기본으로 켜져 있다(D-029).
- **기각한 대안**: 필요한 외부 설정이 모두 있어야 시작 → 개인 설치가 무거워지고, 메일 하나 때문에 앱 전체가 못 뜬다.

## D-031. 문서 텍스트 변환의 1차 어댑터는 서버 안의 Apache POI + PDFBox — 보류 (D-093, 첨부의 텍스트 변환으로 다시 정함)

  변환은 트랜잭션 밖 작업으로 돌고, `artifact_rendition.converter`에 어댑터와 버전을 남긴다 (D-016, `06-schema.md`).
- **왜**: 이미지에 런타임을 더하지 않고 항상 켜져 있다. 어댑터라(D-030) 품질이 부족하면 나중에 외부 도구로 바꿀 수 있다.
  사용자가 선호를 밝히지 않아 권장안으로 정했다.
- **감수하는 것**: 제목 스타일 → `#`, 표 → Markdown 표 같은 내보내기 코드를 직접 쓴다. 변환 품질은 그 코드만큼이다.
- **기각한 대안**
  - markitdown(외부 Python 프로세스): 품질은 좋지만 이미지에 Python이 들어가고 변환마다 프로세스를 띄운다.
  - pandoc(외부 프로세스): docx 품질은 가장 좋지만 xlsx·pptx를 읽지 못해 도구가 하나 더 필요하다.

## D-032. Markdown → PDF 생성의 1차 어댑터는 서버 안의 HTML 렌더링(openhtmltopdf 계열) — 보류 (D-093, 1차에서 빠짐)

- **왜**: D-031과 같은 이유(런타임 추가 없음, 어댑터라 교체 가능). 사용자가 선호를 밝히지 않아 권장안으로 정했다.

- **기각한 대안**
  - 헤드리스 Chromium: 렌더링은 가장 정확하지만 이미지가 수백 MB 커진다.
  - pandoc + LaTeX: 한글 설정이 까다롭고 이미지가 커진다.

## D-033. 기반(스킬·지시서)은 Claude Code가, 코드는 Codex가 맡고, 작업은 docs/tasks/의 지시서로 넘긴다 — 확정
- **무엇을**: git 저장소, `.gitignore`, 스킬 이관(SandboxHr → `bit-*`), 스킬 동기화(`scripts/sync-skills.mjs` + `.claude/settings.json` SessionStart 훅)는 기획 세션에서 했다.

- **왜**: 사용자가 코드 작업을 Codex에게 맡긴다. 스킬이 먼저 있어야 Codex가 규칙대로 짠다. 스킬 이관은 SandboxHr 내용을 판단해 거르는 일이라 기획 맥락이 있는 쪽이 했다.

## D-034. 첫 워크스페이스 모바일 하단 바는 홈·Inbox·My Tasks·더보기로 구성한다 — 확정

## D-035. 첫 실행 비밀값은 DB 옆에 보관하고 인증용·Git 암호화용 키를 나눈다 — 확정
- **무엇을**: `GeneratedSecrets`가 비어 있는 `app.auth.secret`, `app.git.encryption-key`에 각각 독립된 32바이트 난수를 생성해 DB 옆 `secrets.properties`에 보관한다. 환경 변수 `AUTH_SECRET`, `GIT_ENCRYPTION_KEY`가 우선하며 재시작해도 자동 생성값을 유지한다. POSIX에서는 파일 생성 시 소유자 읽기·쓰기 권한만 준다.
- **왜**: Docker나 별도 비밀값 설정 없이 실행하되 재시작마다 키가 바뀌지 않게 한다. 인증과 저장소 토큰 암호화가 같은 키에 묶이지 않으며, DB와 한 볼륨으로 백업할 수 있다.
- **기각한 대안**: 기동마다 새 키를 만들면 세션과 암호화된 토큰을 유지할 수 없다. 공용 기본 키는 설치 사이에 공유되므로 쓰지 않는다. 이번 범위에 없는 푸시 알림 키는 만들지 않는다.

## D-036. 최초 관리자만 직접 가입하고 이후 계정은 초대로 참여한다 — 확정
- **무엇을**: T-002의 추천안 1을 사용자가 채택했다. 사용자 행이 하나라도 있으면(소프트 삭제 포함) 초기 가입을 닫는다. 첫 가입을 쓰기 트랜잭션에서 직렬화한다. 초대 링크는 후속 워크스페이스 기능에서 구현하며 SMTP 없이 전달할 수 있게 한다.
- **왜**: 개인 설치의 시작을 간단하게 유지하면서 공개 주소를 아는 누구나 계정을 만드는 것을 막는다. 관리자가 없어진 상황과 새 설치를 구분한다.
- **기각한 대안**: 계속 공개 가입은 계정 남용 정책이 필요하다. 관리자 직접 계정 생성은 임시 비밀번호 전달을 기본 가입 흐름으로 만든다.

## D-037. 인스턴스 운영 권한과 워크스페이스 업무 권한을 분리한다 — 확정
- **무엇을**: 사용자가 T-002의 추천안 2 권한 표를 채택했다. 인스턴스 관리자는 계정 복구·설치 운영만 맡고 업무 내용은 멤버십으로 판정한다. owner·admin은 관리, member는 업무 내용 생성·수정·보관, viewer는 조회를 한다. admin 관리·소유권 이전·워크스페이스 삭제는 owner만 한다. 세부 표는 인증 계약에 유지한다.
- **왜**: 설치 운영자가 모든 업무를 자동 열람하지 않으면서 가벼운 고정 역할로 협업한다. 마지막 owner는 원자적 소유권 이전 없이 제거할 수 없다.
- **기각한 대안**: member의 자기 작성물만 수정은 협업을 방해한다. 사용자 정의 역할·프로젝트별 멤버 제한은 MVP 관리 비용을 늘린다.

## D-038. API 키는 업무 읽기·쓰기를 허용하고 계정 보안 작업은 세션으로 제한한다 — 확정
- **무엇을**: 사용자가 T-002의 추천안 3을 채택했다. 업무 REST·MCP는 키 주인의 현재 역할로 판정한다. 키 관리·비밀번호·세션 관리·인스턴스 관리자·멤버/소유권 변경·연동 비밀값 관리는 세션 전용이다. 유효한 Bearer만 CSRF에서 제외하며 잘못된 Bearer는 쿠키로 대체 인증하지 않는다.
- **왜**: 에이전트가 업무를 수행하면서도 업무용 키로 추가 자격 증명을 만들거나 계정을 장악하지 못하게 한다.
- **기각한 대안**: GET 전용 키는 기록·상태 변경을 막는다. 모든 인증 API를 키에 허용하면 자격 증명의 영향 범위가 커진다. 키별 scope는 이후로 둔다.

## D-039. 인증 수명·입력·재인증은 T-002 기준으로 시작한다 — 확정
- **무엇을**: 사용자가 T-002 기본값을 채택했다. 비밀번호는 15~64 코드 포인트·UTF-8 최대 72바이트, bcrypt. 세션 유휴 7일·절대 30일·갱신 간격 5분, 키 기본 만료 30일·마지막 사용 갱신 1분이다. 키 생성·관리자 임시 비밀번호 발급은 현재 비밀번호를 다시 확인한다. 로그인·초기 가입은 IP별 분당 10회로 제한한다.
- **왜**: 메일·MFA 없이 시작하는 설치에서 긴 암호문을 지원하고, 무차별 대입·과도한 SQLite 쓰기·자격 증명 재발급을 제한한다. 비밀번호 비교는 잠금 밖에서 하고 검증 결과를 트랜잭션 안에서 재확인한다.
- **기각한 대안**: 비밀번호 잘라 쓰기, 매 요청 만료 연장, 재인증 없는 키 발급은 각각 입력 충돌·불필요한 쓰기·세션 탈취 영향을 늘린다. Argon2id 전환은 기존 D-027과 별도 검토한다.

## D-040. 워크스페이스는 단일 owner와 고정 slug를 갖는다 — 확정
- **무엇을**: 사용자가 T-003 추천안을 채택했다. 활성 공간의 owner는 정확히 한 명이며 소유권 이전은 현재 비밀번호 확인 후 기존 owner→admin, 기존 활성 멤버→owner를 원자 처리한다. UUID가 API/화면 식별자이며 slug는 정규화한 2~64자 영문·숫자·하이픈, 양끝 영문/숫자, 생성 후 고정·삭제 후에도 재사용하지 않는다.
- **왜**: 책임과 참조의 의미를 단순하게 유지하고 과거 주소가 다른 공간을 가리키지 않게 한다.
- **기각한 대안**: 복수 owner, slug 변경/별칭은 MVP 관리 경우의 수를 늘린다.

## D-050. 보드 순서와 집계는 서버가 검증한 전체 조건으로 계산한다 (2026-10-23)
- **무엇을**: 작업 이동은 같은 프로젝트·목적 컬럼의 before/after 이웃을 검증한 뒤 서버가 정수 순서를 다시 매긴다. SQLite REAL의 jOOQ 표현은 Double로 지정한다. 컬럼 삭제는 살아 있는 작업(보관 포함)을 목적지로 이관하고, 이미 삭제된 작업의 원 컬럼 참조는 남긴다. 그 컬럼이 사라진 뒤 복원하는 작업은 백로그로 돌아간다.
- **집계**: 작업 목록과 컬럼별 건수는 같은 SQL 필터를 공유한다. 건수는 별도 counts API로 전체 일치 행을 집계하며, 페이지에서 읽은 카드 수를 전체 건수로 표시하지 않는다. 삭제 목록에는 보관 후 삭제한 작업도 포함한다. from/to 필터는 마감일 범위다.
- **왜**: 분수 위치값 누적·다른 프로젝트 이웃 혼입·페이지마다 달라지는 건수를 피하고, 작업의 보관/삭제 상태를 복원 과정에서 잃지 않는다. REAL을 Java Float로 다루면 큰 위치값에 정밀도 손실이 생겨 Double로 읽고 쓴다.
- **기각**: 클라이언트가 임의 위치를 저장, 로드한 첫 페이지 개수를 전체 건수로 사용, 컬럼 삭제 때 삭제한 작업을 묵시적으로 새 상태에 복원.

## D-055. 결정 대체와 세션 일괄 기록은 명시적 원자성 예외다 (2026-10-23, 결정 대체는 D-094로 없어짐)
- **무엇을**: 결정은 proposed→accepted→superseded. 동일 프로젝트의 accepted 대체자와 옛 결정 상태·supersedes 링크를 원자 변경하고 일반 unlink로 이 관계를 없애지 않는다. accepted까지 본문 정정은 version과 활동 before/after를 남기며 superseded는 읽기 전용, 소프트 삭제는 proposed만 허용한다. 이행은 살아 있는 파생 작업의 closedAt에서 계산하며 보관 작업도 포함한다.

## D-056. 긴 결정 정정 이력은 같은 변경의 조각으로 보존한다 (2026-10-23)
- **무엇을**: 결정의 정정 이력은 필드별 before/after를 기록한다. 각 값은 최대4000 UTF-16 코드 단위로 나누되 서로게이트 쌍을 자르지 않는다. 같은 업무 이벤트의 changeId·version·발생 시각·주체를 공유하고 field·part(0부터)·parts·beforeLength/afterLength를 함께 남긴다. null 길이는 -1이며 빈 문자열과 구분한다. 조각은 업무 변경과 같은 트랜잭션에서 모두 저장된다. 활동의 128KiB UTF-8 행 상한은 유지한다.

- **기각**: 긴 본문 자르기, 이력 없이 정정 성공, 행 상한을 없애기, 이스케이프를 고려하지 않은 글자 수만의 크기 판정. 세션 요약·댓글은 D-055대로 본문 복제가 아니라 변경 메타데이터만 남긴다.

- **기각**: 각진 B 모노그램 유지, BIT를 두 줄로 쌓기, 배경 질감이 있는 생성 이미지를 그대로 확대/축소, 아이콘마다 수동으로 다른 로고 사용.

## D-059. 메뉴 머리는 제품 로고 대신 워크스페이스의 로고와 이름이다 (2026-10-23)
- **무엇을**: 사이드바 맨 위에는 BIT 표시 대신 지금 워크스페이스의 로고(없으면 이름 첫 글자를 색 바탕에)와 이름을 둔다. 누르면 Kaneo처럼 팝오버로 내 워크스페이스 목록(지금 것에 체크)과 그 아래 '워크스페이스 추가'가 열리고, 추가는 짧은 창에서 로고 이미지·이름(필수)·설명을 받아 만든 뒤 그 홈으로 간다. 로고는 정사각형 PNG·JPG·WebP·SVG, 1MB 이하. 메뉴의 '공간 선택 · 전환' 항목은 이 팝오버로 대신한다(휴대폰은 더보기에 남김). 모든 구성원은 온보딩에서 워크스페이스를 하나 반드시 만들므로 메뉴 머리가 빈 채로 보이는 일은 없다. 새 워크스페이스의 홈은 빈 요약 대신 '첫 프로젝트를 만들어 보세요'를 보인다.
- **왜**: 사용자는 제품보다 자기 팀 공간 안에서 일한다. 제품 표시는 로그인·온보딩 화면에서 충분하고, 업무 화면의 맨 위는 지금 어느 공간인지와 공간 전환을 맡는 편이 Kaneo·Linear와 같은 흐름이다.
- **기각**: 제품 로고와 공간 이름을 함께 두기(머리가 붐비고 전환 버튼이 작아짐), 공간 전환을 별도 페이지(/workspaces)로만 두기(한 번 더 이동해야 함).
- **알림**: Inbox는 '알림'으로 부르고 메뉴 항목에서 뺀다. 메뉴 머리에서 워크스페이스 이름과 양끝 정렬로 알림 종(shared/ui NotificationBell, SandboxHr의 것)을 두고, 읽지 않은 알림이 있으면 개수 배지와 함께 종의 선이 회전하는 그라디언트·빛·가끔 흔들림으로 빛난다(동작 줄이기에서는 색만). 휴대폰은 머리 줄 끝에 같은 종을 둔다. 주소는 실제 앱과 같이 `/inbox`를 유지한다.
- **상태 그림**: PageState는 SandboxHr의 풍경 그림 12장(빈 목록·검색 없음·404·500 각 3장)과 StateLandscape를 그대로 쓴다.
- **메뉴 구성 (2026-10-23 정정)**: 워크스페이스 메뉴는 홈·구성원(Members를 이렇게 부른다)·문서함이다. My Tasks는 없앤다(내 작업은 프로젝트 목록의 담당자 필터로 본다). 워크스페이스 설정은 메뉴 맨 아래(바닥)에 둔다. 홈은 SandboxHr 팀 캘린더의 월·주·업무 주 보기를 그대로 쓰고(widgets/demo-calendar, `view`·`date`를 주소에), 요약·내 작업·최근 결정은 넓은 화면에서 오른쪽, 좁으면 캘린더 아래에 둔다. 휴대폰 전용 캘린더(MobileCalendar)는 아직 옮기지 않았다.
- **내 설정**: 메뉴의 프로필 카드 오른쪽 톱니바퀴(접힌 메뉴에서는 사진)를 누르면 메뉴가 설정 구조로 바뀐다. 맨 위는 '‹ 돌아가기'와 Esc 키 표시(Esc도 같은 동작, 바로 앞 작업 화면이면 히스토리로 되돌아감), 그 아래 '계정' 묶음에 프로필·디스플레이·알림·API 키·시큐리티. 주소는 워크스페이스 밖의 `/settings/…`(데모는 `/demo/settings/…`). 설정 페이지는 Kaneo처럼 섹션마다 테두리 카드에 줄 단위 항목을 두는 shared/ui SettingsCard·SettingsRow를 쓴다.
- **설정 페이지 머리와 디스플레이**: 계정 설정 페이지는 카네오처럼 위에 큰 제목과 한 줄 설명만 둔다(shared/ui SettingsHead). '바로 적용됩니다', '변경 사항이 자동으로 저장됩니다'처럼 조작이 스스로 보여 주는 것을 말로 되풀이하는 안내, 목록 위에 그 목록을 풀어 쓰는 설명 줄은 두지 않는다(사용자 경고, 2026-10-23). 페이지 제목 아래 설명을 두지 않는다는 bit-frontend 04 규칙의 예외다. 디스플레이의 '화면 모드' 줄은 없애고 '색상 테마'를 디스코드처럼 견본 타일로 둔다. 순서는 시스템, 라이트, 다크, 그다음 눈이 편하도록 글자와 바탕의 대비를 부드럽게 맞춘 BIT 테마 — 밝은 살구(미색→살구빛)·새싹(민트→레몬)·솜사탕(분홍→복숭아빛)·새벽안개(푸른 회색→아주 옅은 라일락), 밝은 넷은 창 배경에 위에서 아래로 두 색이 번지는 그라데이션을 깔아, 창 높이를 다 쓰는 메뉴에서 그 변화가 온전히 보이게 한다. 어두운 밤바다(깊은 남색)·모닥불(숯빛·호박색). 색 테마는 각자의 모드 위에 배경·면·테두리·글자·강조색만 바꾼다(app/styles/color-themes.css, `<html data-color-theme>`). 웹 조사로 Solarized·Nord·Catppuccin·GitHub도 넣어 봤으나 사용자가 빼기로 했고, 디스코드식 색 테마(민트애플 등)는 업무 도구에 장식이 강해 기각했다. 고르지 않으면(none) 기존 스톤 테마와 같다. 필수 입력(프로필 이름)을 비우면 그 칸 아래에 바로 오류를 보인다.
- **지금 상태**: `/demo`에만 목데이터로 구현했다(features/demo-workspace-switcher). 실제 앱은 워크스페이스 로고 저장(파일 어댑터, D-030)과 온보딩의 첫 워크스페이스 생성 강제가 필요하며 아직 구현하지 않았다.

## D-060. 페이지 동작 버튼은 초타원 모서리와 강조색 빛 그림자, 홈은 캘린더 하나와 '만들기' (2026-10-23, 버튼 부분은 D-067로 대체됨)
- **무엇을**: 페이지가 가진 이름 붙은 동작 버튼(`data-page-action` 안의 새 작업·만들기 등)은 SandboxHr처럼 글자를 굵게 하고 모서리를 초타원(`border-radius: 24px; corner-shape: superellipse(1.6)`)으로 깎는다. 주 버튼은 강조색으로 은은하게 빛나는 그림자를 단다(app/styles/index.css). `corner-shape`를 모르는 브라우저(Firefox·Safari)에서는 알약 모양이 되지 않게 기존의 작은 모서리를 유지한다. 아이콘만 있는 버튼은 그대로 둔다. 헤더 줄의 동작도 같은 모양이다(SandboxHr는 헤더에서 초타원을 빼지만 사용자가 특별한 버튼에 이 모양을 요청했다).
- **홈 (D-059 정정)**: 오른쪽의 요약·내 작업·최근 결정·화면 패턴 칸을 없애고 캘린더 하나만 둔다. 헤더 줄의 동작은 '새 작업' 대신 '만들기' 메뉴다. '일정'은 짧은 창(이름 필수·프로젝트 선택 사항·날짜·종일·시작/끝)으로 워크스페이스 일정을 만들어 캘린더에 올리고, '작업'은 프로젝트 하위 메뉴에서 고른 프로젝트의 새 작업 양식으로 간다. 휴대폰은 떠 있는 +가 같은 선택지를 시트로 연다.
- **일정**: 워크스페이스에 속하고, 프로젝트에 이을 수도 있고 잇지 않을 수도 있다. 프로젝트에 이은 일정은 캘린더에서 제목 앞에 프로젝트 키를 붙인다. `/demo`에서만 메모리에 두며(entities/demo-sample schedules), 실제 앱의 일정 엔티티·API는 아직 정하지 않았다.
- **왜**: SandboxHr의 팀 캘린더가 같은 구성(캘린더 + 새로 만들기 메뉴)이라 홈이 한 가지 일에 집중한다. 작업은 반드시 프로젝트에 속하므로 홈에서 만들 때 프로젝트를 먼저 고르게 한다.
- **기각**: 홈 오른쪽 요약 칸 유지(사용자가 필요 없다고 함), 홈의 동작을 '새 작업' 하나로 두기(일정을 만들 곳이 없음), 작업 양식 안에서 프로젝트 고르기(지금 양식 주소가 프로젝트 아래라 바꾸는 범위가 큼).
- **날짜 미정 서랍 (2026-10-23)**: 홈은 캘린더로 유지하고, 날짜 없이 만든 작업은 캘린더 오른쪽 '날짜 미정' 서랍에 둔다. 대상은 워크스페이스의 진행 중 프로젝트에서 끝나지 않고 마감일이 없는 작업 전체다(캘린더가 워크스페이스 전체를 보이므로 '내 작업'으로 좁히지 않는다. 데모에서 내 담당은 0개였다). 우선순위 순으로 보이고, 데스크톱은 서랍에 하나라도 있으면 열린 채로, 없으면 접힌 채로 시작한다. 탭 줄 끝의 '날짜 미정 N' 토글로 이번 방문 동안 바꿀 수 있다. 서랍의 작업을 월·주 보기의 날짜로 끌어 놓으면 그날이 마감일이 되고, 꽉 찬 날에는 '+N개 더'에 가려질 수 있어 토스트로 어디에 놓였는지 알리고 되돌리기를 준다. 휴대폰은 끌기가 없어 캘린더 줄 끝의 '미정 N'이 시트를 열고, 행을 누르면 작업으로 간다. 데모에서 정한 날짜는 메모리에만 둔다(entities/demo-sample work-dates).
- **카네오 비교**: 카네오의 홈은 캘린더가 아니라 오늘 앞뒤 7일 띠와 '다음 할 일'(내 담당, 날짜 무관)이고, 캘린더는 프로젝트 보기이며 날짜 없는 작업은 거기에 뜨지 않는다. 백로그는 날짜가 아니라 상태(planned) 기준이다(카네오 2847dbd 소스로 확인). BIT는 워크스페이스 일정이 있어 캘린더 홈을 지키고, 날짜 없는 작업은 서랍이 맡는다.
- **기각 (서랍 배치)**: 달력 위 한 줄(늘 높이를 차지하고 몇 개만 보임), 오늘 칸에 '미정 N' 묶음(오늘 할 일로 오해됨), 카네오식 홈으로 바꾸기(사용자가 캘린더 유지를 골랐음).

## D-061. 워크스페이스 설정은 메뉴를 설정 구조로 바꾸고 프로젝트·인스턴스 설정까지 모은다 (2026-10-23)
- **무엇을**: 메뉴 바닥의 '워크스페이스 설정'을 누르면 내 설정(톱니바퀴)처럼 메뉴가 설정 구조로 바뀐다. 맨 위는 '‹ 돌아가기'와 Esc(같은 동작), 그 아래 워크스페이스 이름 묶음(일반·역할·라벨·연동), '프로젝트' 묶음(진행 중 프로젝트마다 접히는 항목, 펼치면 일반·보드 칸·통제·저장소, 보고 있는 프로젝트는 펼친 채), '인스턴스 관리' 묶음(사용자·워크스페이스·서버 기능, 인스턴스 관리자에게만)을 둔다. 카네오의 설정 메뉴 구성(계정·워크스페이스·프로젝트별·관리)을 따르되, 내 정보(계정)는 지금처럼 프로필 카드의 톱니바퀴로 따로 연다.
- **주소**: 워크스페이스 `/w/$workspaceId/settings/{general|roles|labels|integrations}`(`/settings`는 general로), 프로젝트 `/w/$workspaceId/settings/projects/$projectId/{general|board|control|repository}`(프로젝트 메뉴의 '설정'과 옛 `/p/$projectId/settings`도 여기로), 인스턴스 `/admin/{users|workspaces|features}`(워크스페이스 밖, 메뉴는 마지막 워크스페이스의 설정을 함께 보인다). 데모는 `/demo` 아래 같은 주소다.
- **페이지 내용**: 일반(로고·이름·설명, 소유권 이전, 워크스페이스 삭제), 역할(네 역할이 할 수 있는 일의 표, D-048·D-049), 라벨(워크스페이스 공통 라벨의 색·이름·쓰는 작업 수), 연동(Git 서버 연결과 웹훅 주소, D-030), 프로젝트 일반(이름·키·설명, 보관·삭제, D-011), 보드 칸(순서·완료 칸, D-049), 통제(개인/팀 모드와 팀 모드 규칙, 원칙 5), 저장소(프로젝트별 Git 저장소 여러 개와 마지막 웹훅), 서버 기능(켜짐·꺼짐 읽기 전용, 원칙 6). 휴대폰은 지금 묶음의 앞 세 항목이 탭이고 나머지와 다른 묶음·돌아가기는 더보기에 둔다.
- **왜**: 설정이 워크스페이스 한 페이지와 프로젝트 한 페이지에 흩어져 있어 늘어날 항목을 둘 곳이 없었다. 메뉴가 설정 구조로 바뀌면 내 설정과 같은 동작으로 익히고, 프로젝트가 많아도 한 메뉴에서 찾는다.
- **기각**: 내 설정과 워크스페이스 설정을 한 설정 메뉴로 합치기(사용자가 내 정보는 빼기로 함), 프로젝트 설정을 프로젝트 메뉴 안에 두기(설정 진입점이 둘로 갈림), 설정을 한 페이지의 섹션으로 길게 잇기(항목이 늘면 찾기 어려움).
- **지금 상태**: `/demo`에만 목데이터로 구현했다(pages/demo/settings/workspace·project·admin). 실제 앱의 설정 페이지와 라벨·통제·저장소·인스턴스 관리 API는 아직 없다.

## D-062. 작업·일정·노트·결정기록을 '이슈' 하나에 유형으로 담는다 (2026-10-24, 유형 부분은 D-066으로 대체됨)
- **무엇을**: 레드마인 일감처럼 추적하는 모든 것을 '이슈(Issue)' 하나로 부르고 유형으로 나눈다. 유형은 작업·일정·노트·결정기록 네 가지로 고정한다(결정 유형은 '결정기록'이라 부른다). 모든 이슈는 번호·제목·본문·작성자·라벨·댓글·연결·변경 기록을 공통으로 갖고, 유형마다 따로 갖는 칸이 있다(작업: 상태·담당자·우선순위·시작/마감일·트리거, 일정: 시작/끝 시각·종일·반복·참석자, 노트: 일시·참석자(선택), 결정: 제안/확정/대체 상태·기각한 대안). 보드는 작업만, 캘린더는 일정과 마감일 있는 작업만 걸러 보인다.
- **유형과 라벨**: 유형은 화면과 동작(보드·캘린더·결정 목록·진행률·MCP 도구)을 바꾸므로 고정하고 사용자가 추가하지 않는다. 동작은 같고 이름만 다른 분류(회의록·주간회의·고객 미팅·세션 요약·아이디어 등)는 사용자가 만드는 라벨로 둔다(레드마인의 유형과 범주). 그래서 회의록은 따로 두지 않고 '회의록' 라벨을 단 노트로 표현한다. 카네오도 작업 유형은 없고 라벨·보드 칸·프로젝트별 사용자 정의 필드만 사용자가 추가한다(카네오 2847dbd 스키마로 확인). 대가: 회의록 전용 필수 칸은 강제하지 못하고, 동작이 다른 유형이 더 필요하면 코드로 추가한다.
- **결정**: 결정은 별도 대상이 아니라 '결정' 유형 이슈다. 회의록·노트·작업 화면에서 댓글을 달듯 적으면 댓글 줄 사이에 결정 카드로 보이고, 실제로는 그 이슈에서 나온(`derives_from`) 결정 이슈로 저장된다. 결정만 따로 모아 보는 목록을 둔다. 댓글 자체는 이슈가 아니다(번호·상태 없이 한 이슈 안에 붙는 기록).
- **왜**: 일정·회의록·노트·작업의 데이터가 비슷해(제목·본문·사람·날짜·연결) 그릇 하나와 유형이 단순하다(사용자 판단, 회사 레드마인에서 회의록을 일감 유형으로 쓴 경험). 결정은 다른 곳에서 가리키고(작업의 근거, 대체 관계, 에이전트 맥락의 기각 대안) 회의록뿐 아니라 노트·작업에서도 나오므로, 번호·상태를 가진 이슈 유형이어야 한다.
- **SDLC 점검**: 요구는 작업(트리거: 요구)과 문서함의 요구사항 문서, 버그·장애는 작업(트리거: 발견)과 라벨, 설계 판단·변경 요청·미결 질문은 결정기록(제안 상태), 회의·세션·리뷰는 노트와 라벨, 배포·리뷰 날짜는 일정, 에픽은 작업 간 상위·하위 연결, 커밋·MR은 코드 참조, 설계서는 문서함이 맡는다. 마일스톤·릴리스는 이슈 유형으로 만들지 않고 나중에 이슈를 묶는 단위로 둔다(02-domain-model의 Baseline). 카네오에도 마일스톤·스프린트·이터레이션은 없다(카네오 사이트의 Jira·Shortcut 비교 문구로 확인). 테스트 케이스·위험 관리는 범위 밖이다.
- **이름**: '작업 항목(work item)'은 회의록·일정을 담기에 어색해 '이슈'로 정했다. Jira가 2025년 3월 통칭을 issue에서 work로 바꾼 사례를 검토했으나, Jira가 담는 것은 모두 할 일이라 BIT와 다르다.
- **기각**: 지금처럼 결정·세션·작업을 각각 따로 두기(02-domain-model의 분리 원칙. 목록·번호·검색이 갈라짐), 결정을 표시 붙은 댓글로 두기(번호가 없어 작업에서 가리키거나 대체·기각 대안을 담기 어려움).
- **뒤집는 것**: `docs/02-domain-model.md`의 "Redmine은 이슈 하나에 뭉쳐서… BIT는 분리한다"와 결정·세션 독립 엔티티 설계를 이 결정으로 바꾼다. '왜'의 추적은 엔티티를 나누는 대신 유형과 이슈 간 연결로 지킨다.
- **아직 정할 것**: 프로젝트 없는 이슈(워크스페이스 단위)의 번호, 일정→노트를 한 이슈의 유형 변경으로 할지 연결로 할지, 서버 `workitem`·`decision`·`session` 모듈과 표·MCP 도구 이름을 언제 어떻게 바꿀지(T-005 진행 중, `workitem` 쪽은 D-084에서 바꿈). 메뉴 구성은 D-063. 정해지면 이 항목과 02-domain-model·06-schema·07-mcp를 함께 고친다.

## D-063. 메뉴는 이슈 유형 넷을 한 번만 두고, 프로젝트는 메뉴 맨 위의 범위 선택기로 고른다 (2026-10-24, D-064로 대체됨)
- **무엇을**: 사이드바의 '이슈' 묶음에 작업·일정·결정기록·노트를 한 번만 둔다. 각 메뉴는 워크스페이스 전체가 기본 범위이고, 메뉴 맨 위(워크스페이스 이름 바로 아래, 이슈 묶음 위)의 범위 콤보박스(전체 또는 프로젝트 마크와 이름, 펼치면 전체·진행 중 프로젝트·'프로젝트 관리')에서 하나를 고르면 지금 보던 메뉴는 그대로 두고 범위만 그 프로젝트로 바뀐다. 네 메뉴는 선택기 바로 아래 다른 메뉴와 같은 평평한 줄로 둔다(세로선으로 묶었다가 사용자 판단으로 뺐다). 접힌 메뉴에서는 선택기가 마크 하나로 줄어든다. 사이드바의 프로젝트 선택과 화면 위의 '프로젝트' 필터 칩은 같은 상태이고 주소에 담긴다(`?project=…`). 구성원·문서함도 전체나 한 프로젝트에 속할 수 있어 '협업' 묶음으로 두고 같은 범위를 따른다(데모의 두 화면은 아직 범위에 따라 내용을 거르지 않는다). 데모 전용 'UI 패턴' 메뉴는 실제 앱에 없는 메뉴라 사이드바에서 뺐다(상태·대화상자 페이지 주소는 남아 있다).
- **메뉴마다 기본 보기**: 작업은 칸반(목록·표·간트로 바꿈), 일정은 캘린더(일정 + 마감일 있는 작업, 날짜 없는 작업은 '날짜 미정' 서랍), 결정기록은 위에서 아래로 흐르는 타임라인, 노트는 목록. 유형을 섞는 '전체' 보기는 두지 않는다(사용자 판단). 칸반은 상태가 있는 유형(작업, 결정기록)에만 쓴다. 작업의 사용자 정의 저장 보기(Plane·Linear의 Views)는 나중에 연다.
- **순서와 숨김**: '이슈' 묶음 머리의 조절 아이콘을 누르면 짧은 창이 뜨고, 줄마다 손잡이를 끌어(또는 손잡이에서 위아래 화살표로) 순서를 바꾸며 작업을 뺀 셋은 스위치로 숨긴다. '처음 순서로'가 기본으로 되돌린다. 사람마다, 워크스페이스마다 따로 저장한다(다른 구성원의 메뉴를 바꾸지 않게).
- **왜**: 프로젝트마다 같은 네 메뉴를 펼치면 프로젝트 수만큼 메뉴가 길어지고, 같은 페이지가 두 번 나온다. 범위로 고르면 메뉴가 늘 같고, 결정기록을 보다가 프로젝트만 바꿔 볼 수 있으며, 필터와 하나라 익힐 것이 적다.
- **기각**: 프로젝트마다 같은 메뉴를 펼치기(지금까지의 데모 구조), 이슈 메뉴 아래 별도 '프로젝트' 목록 묶음(메뉴와 범위가 떨어져 있어 그 목록이 위 메뉴의 범위라는 게 안 보임, 2026-10-24 사용자 피드백), 사이드바 맨 위의 큰 범위 막대(워크스페이스 전환기와 헷갈림), 유형을 섞는 전체 보기, 순서·숨김을 워크스페이스 전체에 강제하기, 순서를 위아래 버튼으로 옮기기(번거로움).
- **지금 상태 (2026-10-24)**: `/demo`에 구현했다. 주소는 `/w/$workspaceId/{work|schedule|decisions|notes}?project=…`, 워크스페이스 첫 화면은 그 사람의 첫 이슈 메뉴로 간다. 홈 캘린더는 '일정'이 이어받고(날짜 없는 작업은 일정에 보이지 않고 작업 메뉴에서 본다), '모든 프로젝트' 관리는 범위 선택기의 '프로젝트 관리'로 연다. 옛 `/p/$projectId`·`/decisions`·`/sessions`·`/artifacts`는 범위를 단 새 메뉴(산출물은 문서함)로 넘긴다. 작업 상세·새 작업 양식 주소는 아직 프로젝트 아래다. 결정기록 타임라인은 검토 중을 맨 위에, 확정된 것은 월별 최신순으로 둔다. 휴대폰은 보이는 이슈 메뉴 앞 셋이 탭이고, 나머지·구성원·문서함·범위 선택은 더보기에 있다. 실제 앱은 아직 옛 구조다.

## D-064. 메뉴는 워크스페이스(홈·구성원·문서함)와 프로젝트 목록, 프로젝트의 부분은 탭이다 (2026-10-24, 홈·보기 전환은 D-065로, 프로젝트 탭은 D-066으로, 문서함과 프로젝트 하위 메뉴는 D-093으로 바뀜)
- **무엇을 (D-063 대체)**: 사이드바는 '워크스페이스' 묶음(홈·구성원·문서함), '프로젝트' 묶음(머리의 + 버튼으로 바로 만들기, 진행 중 프로젝트 목록), 바닥의 워크스페이스 설정·프로필 카드다. 범위 선택기와 워크스페이스 전체의 작업·일정·결정기록·노트 메뉴는 없앤다. 프로젝트를 누르면 아래에 하위 메뉴가 펼쳐지지 않고 프로젝트 페이지가 열리며, 그 탭 줄의 탭이 작업·백로그·노트·결정기록이다(주소 `/w/$workspaceId/p/$projectId?tab=backlog|notes|decisions`, 작업은 생략).
- **리스트와 표**: 리스트와 테이블을 같은 것으로 본다. '표 보기'는 따로 없고, 리스트가 데스크톱에서는 표, 휴대폰에서는 카드로 그려진다.
- **탭마다 보기**: 작업은 리스트·캘린더(마감일 있는 작업과 일정)·칸반·타임라인(만든 날부터 마감일까지 막대, 오늘에 맞춰 열림)을 툴바 맨 앞의 전환으로 고른다(`?view=calendar|board|timeline`, 리스트는 생략, 캘린더 자체 위치는 `cal`·`date`). 백로그는 리스트만 있고, 카네오의 백로그처럼 표가 아닌 행 목록이다(유일하게 표가 아닌 목록). 노트는 구글 Keep처럼 크기대로 쌓이는 카드(라벨별 색), 결정기록은 위에서 아래로 흐르는 히스토리 타임라인이다.
- **홈**: 기본으로 활동 잔디(깃허브 기여 그래프처럼 1년치 일별 활동), 최근 활동, 내 작업을 보인다. '홈 구성' 창에서 위젯(활동 잔디·최근 활동·내 작업·다가오는 마감·최근 결정기록)을 손잡이로 끌어 순서를 바꾸고 켜고 끈다. 사람마다, 워크스페이스마다 따로 저장한다.
- **구성원**: 리스트(데스크톱은 표)로 사진·이름·이메일, 역할(선택), 참여 중인 프로젝트, 참여(작업·결정기록·노트 수), 최근 활동을 보인다. 휴대폰은 사진·이름·이메일과 역할·프로젝트 수를 카드로 보인다. 초대 탭은 그대로다.
- **왜**: 사용자가 메뉴를 다시 생각해 정했다. 프로젝트의 부분을 사이드바 하위 메뉴가 아니라 탭으로 두면 사이드바가 프로젝트 수만큼만 길어지고, 프로젝트 안에서 탭으로 오가는 흐름이 카네오·Plane과 같다. 워크스페이스 수준의 이슈 메뉴와 범위 선택기는 '지금 어느 범위인지'를 매번 의식하게 해 직관적이지 않았다.
- **기각**: 범위 선택기 + 이슈 메뉴 하나(D-063), 프로젝트 아래 하위 메뉴 펼치기, 리스트와 표를 다른 보기로 두기.
- **열린 것**: '일정' 유형 이슈(D-062)를 만드는 곳은 작업 캘린더 보기에 보이기만 하고 만들기 화면은 아직 없다. 프로젝트 없는 워크스페이스 일정의 자리도 정하지 않았다. 구성원·문서함은 워크스페이스 전체만 보인다.
- **지금 상태**: `/demo`에 구현했다(pages/demo/home·project, 캘린더는 프로젝트 페이지 안으로 옮김). 옛 `/p/$projectId/decisions`·`/sessions`는 해당 탭으로, `/artifacts`는 문서함으로 넘긴다. 실제 앱은 아직 옛 구조다.

## D-065. 홈은 '전체' 범위의 프로젝트 화면이고, 범위는 브레드크럼에서, 보기는 '표시' 팝오버에서 고른다 (2026-10-24)
- **무엇을 (D-064 일부 대체)**: 브레드크럼은 '워크스페이스 › 범위' 두 단계다. 탭 이름이던 세 번째 단계는 없앤다(작업 상세처럼 다른 페이지는 항목 이름이 뒤에 붙는다). 두 번째 단계는 카네오처럼 위아래 꺾쇠가 붙은 선택기로, 전체·프로젝트 목록·'프로젝트 만들기'를 연다. 데스크톱은 팝오버, 휴대폰은 바텀시트다. 범위를 바꿔도 탭과 보기(`tab`·`view`·`cal`·`date`)는 유지하고, 전체에는 결정기록이 없어 그 탭은 작업으로 돌아간다.
- **홈 = 전체**: 홈(`/w/$workspaceId`)은 프로젝트 화면과 같은 페이지를 진행 중인 모든 프로젝트에 대해 보인다. 탭은 작업·백로그·노트이고, 결정기록 탭은 프로젝트를 골랐을 때만 나온다. 전체에서는 백로그 행과 노트 카드에 프로젝트 이름이 붙는다. D-064의 홈 위젯(활동 잔디·최근 활동·홈 구성)은 없앤다.
- **보기는 표시 팝오버**: 툴바 끝의 아이콘은 리니어처럼 둥근 필터(ListFilter)와 표시(SlidersHorizontal)다. 작업의 보기(리스트·캘린더·칸반·타임라인)는 탭 줄의 전환이 아니라 표시 팝오버 맨 위의 타일로 고르고, 그 아래가 정렬이다. 첫 보기나 기본 정렬에서 벗어나면 표시 아이콘에, 필터가 걸리면 필터 아이콘에 점이 붙는다. 휴대폰은 같은 내용을 표시 시트로 연다. 공용 ListToolbar의 `views`로 만들었으므로 실제 앱의 다른 목록도 같은 아이콘을 쓴다.
- **왜**: 사용자가 정했다. 홈과 프로젝트가 같은 화면이면 범위만 바꿔 같은 탭·보기로 오갈 수 있고, 카네오·리니어와 같은 흐름이다. 보기 전환을 탭 줄에서 빼면 툴바가 가벼워지고 정렬과 한곳에 모인다.
- **기각**: 홈 위젯 유지(D-064), 브레드크럼 세 단계(워크스페이스 › 프로젝트 › 탭), 보기를 세그먼트 탭으로 툴바 앞에 두기.
- **열린 것**: 전체에서 '새 작업'은 첫 프로젝트의 작성 화면으로 간다. 작성 화면에서 프로젝트를 고르는 칸은 아직 없다.
- **지금 상태**: `/demo`에 구현했다(pages/demo/home 삭제, 프로젝트 페이지가 두 주소를 맡음, app/layout/ScopeSwitcher). 실제 앱은 아직 옛 구조다.

## D-066. 이슈는 유형으로 나누지 않고 라벨과 뷰로 구분한다. 결정기록만 시스템 라벨로 남긴다 (2026-10-24, 유형 없음은 D-092로, 노트·회의록은 D-093으로, 결정기록 라벨은 D-094로 바뀜)
- **무엇을 (D-062의 유형, D-064·D-065의 프로젝트 탭 대체)**: 홈(전체)이든 프로젝트든 화면은 이슈를 보인다. 작업·일정·노트·백로그를 고정 범주나 탭으로 나누지 않고, 카네오·리니어처럼 워크스페이스 라벨과 뷰로 구분한다. 이슈가 어느 뷰에 보이는지는 유형이 아니라 속성이 있는지로 정한다.
- **뷰**: 처음 주는 뷰는 모든 이슈를 담는 '전체 이슈' 리스트 뷰다. 사용자는 리스트·캘린더·칸반·타임라인 중 하나를 골라 이름을 붙이고 필터·정렬·표시 컬럼을 미리 조합한 뷰를 추가한다(예: 라벨이 회의록인 리스트, 상태가 백로그인 리스트). 뷰는 워크스페이스에 정의하고 전체와 각 프로젝트에 같은 목록으로 보이며, 프로젝트에서는 그 프로젝트로 걸러진다.
  - 리스트: 모든 이슈.
  - 캘린더: 시작일이나 마감일이 있는 이슈.
  - 칸반: 워크플로우 상태가 있는 이슈. 프로젝트 안에서는 그 프로젝트의 칸(카네오처럼), 전체에서는 상태 분류(할 일·진행 중·완료)로 묶는다(권장안, 구현 때 확정).
  - 타임라인: 날짜가 있는 이슈. 시작~마감은 막대, 마감만 있으면 점.
- **상세**: 모든 이슈의 상세는 같은 모양이고, 쓰인 속성만 보인다.
- **결정기록**: 사용자가 지울 수 없는 시스템 라벨이다. 이 라벨을 단 이슈에만 결정 상태(제안·확정·대체)와 기각한 대안 칸이 생기고, 서버에 구현한 결정 동작(대체 원자 변경, 진행률 계산, D-053~D-057)을 그대로 쓴다.
- **왜**: 사용자가 정했다. 범주를 고정하면 탭·메뉴·만들기 화면이 범주 수만큼 늘고, 회의록처럼 팀마다 다른 분류를 담지 못한다. 결정기록은 다른 이슈가 가리키고(근거, 대체, 기각 대안) 에이전트 맥락의 핵심이라 동작을 잃으면 안 된다.
- **기각**: 결정기록도 일반 라벨로 두기(결정 수명주기와 기각 대안 형식을 잃음), 유형 넷을 데이터에 남기고 화면에서만 뷰로 풀기(만들 때마다 유형을 골라야 해 방향과 어긋남).
- **열린 것**: 공유 뷰와 개인 취향은 D-068로 정했다. 반복 일정과 시각·종일·참석자는 D-071에서 본체가 다루지 않기로 했다('일정' 라벨도 두지 않음).
- **지금 상태**: 결정만 기록했다. 데모와 서버는 아직 D-064·D-065 구조다.

## D-067. 화면은 리니어의 디자인 언어를 따른다: 누르는 것은 알약, 칸은 8px, 사진은 원 (2026-10-24)
- **무엇을 (D-058의 모서리 규칙과 D-060의 버튼 부분 대체)**: `docs/08-design-language.md`의 리니어 측정값을 BIT의 기본 디자인 언어로 삼는다. 누르는 것(버튼·칩·아이콘 버튼·토글)은 알약 모양이고, 칸을 차지하는 것(사이드바 항목·선택 상자·카드·메뉴 행)은 8px, 떠 있는 것(팝오버·메뉴)은 12px 모서리다. 사람 사진은 원이다. 페이지 동작 버튼의 초타원 모서리와 강조색 빛 그림자(D-060)는 없애고, 주 버튼은 인디고 알약에 옅은 그림자만 둔다.
- **토큰**: 글자 12·13·15·24px, 보통 굵기 450, 컨트롤 높이 24·28·32px(목록 행 44px, 그룹 머리 36px), 기본 색은 리니어의 중립 회색이다. 프라이머리는 스톤처럼 라이트 모드에서 검정, 다크 모드에서 흰색이다(2026-10-24 정정, 처음엔 인디고 `#5e6ad2`). 인디고는 상태 표시처럼 색이 뜻을 가질 때만 쓴다.
- **색 테마**: 색 테마(살구·밤바다 등)는 바탕·표면·글자·선·강조만 정한다. 카드·팝오버·칩·세부 선·호버는 그 값에서 `color-mix`로 계산되어(`app/styles/index.css`) 테마마다 제 색을 띤다. 처음엔 이 토큰들이 리니어 회색으로 고정돼 있어서 테마 위에 회색 면이 떴다.
- **모바일**: 리니어에는 없는 부분이므로 08 문서 4절 표대로 바꾼다. 팝오버는 바텀시트로 열고, 터치 영역은 44px 이상으로 한다.
- **왜**: 사용자가 리니어 UI를 기준으로 삼기로 했다. 리니어처럼 보이는 핵심이 알약 칩·원형 아이콘 버튼과 적은 수의 크기 단계라서, 모서리 규칙(D-058)을 남기면 같은 인상이 나지 않는다.
- **기각**: 버튼 모서리는 D-058대로 두고 색·크기·메뉴만 리니어로 바꾸기, 칩과 아이콘 버튼만 알약으로 하고 글자 버튼은 지금 모서리로 두기(규칙 두 가지가 섞임).
- **적용 순서**: 토큰 → 떠 있는 면(팝오버·메뉴·다이얼로그·토스트·시트) → 툴바(뷰 칩·필터·표시) → 목록·칸반·타임라인·상세 → 새 이슈 창과 속성 선택 → 모바일.
- **지금 상태**: 1~4단계를 적용했다. 토큰(`app/styles/index.css`), 떠 있는 면, 툴바(뷰 칩·필터·표시), 목록·칸반·타임라인·상세가 해당하고, 상태 표시·우선순위 막대·라벨 알약도 리니어식으로 바꿨다. 5단계(새 이슈 창과 속성 선택)도 적용했다. 새 작업은 별도 페이지가 아니라 화면 위쪽에 뜨는 다이얼로그다. 제목·설명은 테두리 없이 두고, 속성 알약(상태·우선순위·담당자·라벨·기한)마다 검색 메뉴와 숫자 단축키가 있다. 기한은 '내일'·'3일'·'10월 30일'처럼 말로 적고, 계속 만들기와 Ctrl+Enter를 지원한다. C 키나 칸반 열의 +로 연다(+는 그 열의 상태로 시작). 전체에서는 다이얼로그 안에서 프로젝트를 고른다. 만든 뒤에는 오른쪽 아래 토스트가 뜬다. 공용 부품은 `shared/ui/property-picker`다. 6단계(모바일)도 적용했다. 휴대폰 탭은 가로로 스크롤되는 32px 칩 줄이고, 버튼은 32·40·44px(입력 칸은 48px)이다. 상세 속성은 제목 아래 알약 줄로 놓고, 팝오버와 속성 메뉴는 바텀시트로, 새 작업은 높은 시트로 연다. 단축키 표시는 휴대폰에서 숨긴다. 우클릭 메뉴는 아직 BIT에 없어 '길게 눌러 여는 시트'는 만들 때 따른다.

## D-068. 뷰는 기본이 워크스페이스 공용이고, '나만 보기' 개인 뷰와 사람별 조정을 둔다 (2026-10-24)
- **무엇을 (D-066의 열린 것)**: 리니어처럼 뷰는 세 겹이다. ① 공용 뷰: 워크스페이스 모두에게 보이는 정의(이름·아이콘·색·보기 방식·필터·정렬·표시 컬럼). ② 개인 뷰: 만들 때 '나만 보기'를 켜면 만든 사람에게만 보인다. ③ 사람별 조정: 공용 뷰에서 각자 바꾼 보기 방식·정렬·표시 컬럼은 그 사람에게만 남는다. 표시 메뉴의 '초기화'로 뷰의 정의로 돌아가고, 고칠 권한이 있는 사람은 '모두의 기본값으로 저장'으로 정의를 바꾼다.
- **필터**: 뷰에서 필터를 바꾸면 필터 줄 끝에 '되돌리기'와 '저장'이 생긴다. 저장은 고칠 수 있는 뷰면 그 뷰의 필터를 바꾸고, '전체 이슈'처럼 기본 뷰나 고칠 수 없는 뷰면 새 뷰를 만든다. 바꾼 필터는 주소에 남아 새로 고침·공유해도 같게 보인다.
- **권한**: 뷰를 만든 사람과 워크스페이스 소유자·관리자가 공용 뷰를 고치고 지운다. '전체 이슈'는 지우거나 이름을 바꿀 수 없다.
- **왜**: 사용자가 리니어 방식(A)을 골랐다. 팀이 함께 보는 뷰는 한 사람의 정렬 변경으로 흔들리면 안 되고, 개인만 쓰는 필터 조합도 저장할 곳이 있어야 한다.
- **기각**: 공용 뷰만 두기(한 사람의 변경이 모두에게 번짐), 공용 뷰와 개인 조정만 두기(개인 필터 조합을 저장할 곳이 없음).
- **지금 상태**: `/demo`에 구현했다. 작업·노트·결정기록·일정 목데이터를 이슈 하나로 합쳤다(`entities/demo-sample/model/issues.ts`). 프로젝트 탭(작업·백로그·노트·결정기록)은 뷰 칩 줄로 바꿨다. 기본 뷰는 전체 이슈·백로그·진행 보드·일정·회의록·결정기록이고, 홈(전체)과 프로젝트가 같은 뷰를 쓴다. 뷰 만들기·고치기·복제·지우기, 필터의 되돌리기·저장, 표시의 보기 방식·정렬·표시할 속성, 초기화·모두의 기본값으로 저장이 동작한다. 상세는 모든 이슈가 같고 가진 속성만 보인다. 데모는 뷰와 조정을 이 브라우저에만 저장한다(localStorage). 실제 앱은 공용·개인 뷰를 서버에, 조정은 사람별 설정으로 저장한다.
- **보기 방식 추가 (2026-10-24)**: D-064의 노트 Keep 카드와 결정기록 히스토리 타임라인을 보기 방식 '카드'·'히스토리'로 되살렸다. 보기 방식은 리스트·캘린더·칸반·타임라인·카드·히스토리 여섯이고 어느 뷰든 고를 수 있다. 카드는 모든 이슈를 첫 라벨 색으로 물든 Keep 카드로 보인다. 히스토리는 카드 가운데 놓인 칼럼에 끊기지 않는 선 하나를 두고, 묶음(검토 중, 달별 최신순)을 선 위의 빈 고리로, 각 이슈를 상태 색 점과 카드로 보인다. 기본 뷰의 회의록은 카드로, 결정기록은 히스토리로 시작한다. 상세 주소는 아직 `/work-items/$id`다.

## D-069. 이슈 상세는 목록 위 모달로 열되 주소는 이슈 자신의 것(마스크 라우트), '크게 보기'로 페이지 (2026-10-24)
- **무엇을**: SandboxHr처럼 목록에서 이슈를 누르면 목록을 그대로 둔 채 가운데 모달로 연다. 주소창에는 이슈 자신의 주소(`/p/$projectId/work-items/$id`)가 보이고(TanStack Router의 `mask`), 목록의 주소는 `panel`·`depth`로 그 밑에 남는다. 모달 머리는 제목, 이슈의 동작(편집·메뉴), '크게 보기'(이슈 페이지로), 닫기 순이다. Esc, 바깥 누르기, 뒤로 가기가 모달만 닫는다. 새로 고침하거나 링크로 열거나 휴대폰에서 열면 같은 주소가 이슈 페이지다(`unmaskOnReload`). Ctrl·⌘을 누른 클릭은 페이지를 새 탭으로 연다.
- **어떻게**: SandboxHr의 `shared/lib/routed-panel`(useScreenPanel·useGo·PANEL_PAGES)과 `shared/ui/side-panel`(RoutedPanel·PanelDialog·ContentModal·Surface)을 같은 이름·역할로 옮겼다. 다른 점은 셋이다. 저장 안 한 작업을 묻는 확인은 아직 BIT에 그런 화면이 없어 뺐다. 옆 패널(side peek)은 옮기지 않았다. 모서리·그림자·흐림 없는 배경은 D-067을 따른다. 상세는 위젯(`widgets/demo-issue-detail`의 IssueDetail) 하나가 Surface로 페이지와 모달 둘 다 그린다.
- **왜**: 사용자가 HR처럼 모달과 페이지를 같은 주소로 두기를 원했다. 목록의 위치(뷰·필터·스크롤)를 잃지 않고 여러 이슈를 훑을 수 있고, 주소를 공유하면 받는 사람은 이슈 페이지를 본다.
- **기각**: 상태로만 여는 모달(주소가 없어 공유·새로 고침·뒤로 가기가 안 됨), 항상 페이지로 이동(목록 위치를 잃음).
- **남은 것**: 새 이슈 창은 D-070에서 주소를 갖게 했다.

## D-070. 새 이슈도 자기 주소를 갖는 마스크 라우트 모달이다 (2026-10-24)
- **무엇을 (D-069의 남은 것)**: 새 이슈는 프로젝트에서 `/p/$projectId/work-items/new`, 전체에서 `/w/$workspaceId/issues/new`(창 안에서 프로젝트를 고른다)라는 자기 주소를 가진다. 칸반 열의 +는 `?status=`로 시작 상태를 넘긴다. 이슈 화면에서는 SandboxHr의 새 작업 항목처럼 목록을 둔 채 모달로 열리고 주소창은 새 이슈 주소를 보인다. 새로 고침·링크·휴대폰·'크게 보기'로는 같은 주소가 새 이슈 페이지다. 페이지는 카드나 대화상자 머리를 가져오지 않고 페이지답게 그린다: 페이지 제목 '새 이슈'와 돌아가기, 본문에 제목·설명과 속성 알약(프로젝트가 첫 알약), 페이지 아래 줄에 취소 · 계속 만들기 · 이슈 만들기.
- **모양**: 모달은 D-067의 리니어식 새 이슈 그대로다. 화면 가운데가 아니라 위쪽(12dvh)에 뜨는 720px 창으로 내용만큼 높다(side-panel의 크기 `form`). 머리는 프로젝트 › 새 이슈 다음에 크게 보기·닫기가 온다. 만들면 모달은 닫히고 토스트가 남는다(계속 만들기를 켜면 남는다). 페이지에서 만들면 만든 이슈 페이지로 간다.
- **편집 분리**: `/work-items/new`가 새 이슈가 되었으므로 예전 작성 양식 페이지는 편집 주소 `/work-items/$id/edit`로 옮기고 그 이슈 값으로 채운다.
- **왜**: 사용자가 HR처럼 새 이슈도 주소를 갖기를 원했다. 주소가 있으면 링크로 바로 '새 이슈'를 열 수 있고, 뒤로 가기가 창만 닫는다.
- **기각**: 상태로만 여는 다이얼로그(D-067 5단계 방식), 가운데 큰 모달(content 크기: 짧은 양식에 비해 비어 보임), 페이지에 모달 양식을 카드째 옮겨 놓기(사용자 반려: 페이지가 대화상자처럼 보임).
- **닫힘**: 닫히는 사본도 열려 있던 자리(위쪽 12dvh)에서 사라진다. 사본을 가운데 정렬 상자에 넣던 탓에 닫는 순간 가운데로 튀던 것을 고쳤다.

## D-071. 호호 HR은 비공개 오피스 확장으로 같은 워크스페이스 메뉴에 들어오고, 진짜 일정은 본체가 다루지 않는다 (2026-10-24, 일정은 D-092로, 회의록은 D-093으로 바뀜)
- **무엇을**: 호호컴퍼니의 HR(결재·휴가·주간보고·공지·조직도)을 BIT 위에 옮긴다. 본체는 GitHub에 공개하고, HR은 회사 GitLab의 비공개 저장소가 본체를 upstream으로 받아 오피스 모듈만 얹는다(서버 `module/office/*`, 화면 `pages/office/*`, 별도 마이그레이션 폴더). 본체에는 비공개 쪽이 본체 파일을 고치지 않고 끼울 자리(메뉴·라우트 등록 목록, 마이그레이션 버전 대역, 권한·알림·캘린더 출처 등록)를 먼저 만든다.
- **메뉴**: 오피스를 따로 된 공간으로 나누지 않고 한 워크스페이스 사이드바에 함께 둔다. HR이 켜지면 홈, 결재함, 주간보고, 문서함, 근태·휴가, 구성원, 공지사항 순이고, 꺼지면 홈, 문서함, 구성원이다. 켜진 메뉴만 생기므로 빈자리가 없다. 받은함(알림)은 메뉴가 아니라 위쪽 알림 아이콘이다. 워크스페이스 로고는 워크스페이스 설정으로 바꾼다(호호컴퍼니는 HR 로고).
- **화면을 늘리지 않는다**: 팀 캘린더는 홈의 기본 뷰(캘린더 레이아웃, D-068의 모두의 기본값)이고, 조직도는 구성원 화면이 품는다(HR이 켜지면 부서·직급과 조직도 탭). 회의록은 '회의록' 라벨 이슈다(D-066). HR 관리(사원·조직·휴가 정책·결재선)는 워크스페이스 설정 안에 HR 관리자에게만 보인다. 공지사항은 읽음 확인·상단 고정이 있어 라벨로 대신하지 않고 HR 메뉴로 둔다.
- **일정**: 반복·한 회차 예외·참석자·참석자별 알림·회의실·공개 범위·ICS 가져오기가 있는 진짜 일정은 본체가 다루지 않는다. 본체의 이슈는 날짜(시작일·마감일)만 갖고, 캘린더 뷰는 날짜 있는 이슈(마감, 릴리스 주간)를 보인다. 그래서 '일정' 라벨과 이슈의 시각·종일·참석자 속성은 두지 않는다. HR 확장은 SandboxHr의 일정(`calendar_event`와 반복·예외·알림)을 옮기고, 휴가·연장근무·공휴일과 함께 캘린더 뷰의 출처로 끼운다(SandboxHr `CalendarSourceSpi` 방식). 회의 일정과 회의록 이슈는 범용 링크로 잇는다.
- **범위**: HR은 호호컴퍼니 한 워크스페이스에만 켠다. 운영에서 더 생기는 워크스페이스는 개인용으로 보고 HR 데이터(사원·휴가)는 그 한 곳에 속한다.
- **왜**: 사용자가 정했다. HR 코드는 비공개여야 하고 본체는 공개한다. SandboxHr은 공간(Office·Projects)을 나누고 화면을 잘게 쪼개 복잡했는데, 사원들은 팀 캘린더와 결재를 자연스럽게 쓰고 있어 그 둘을 첫 화면과 맨 위에 둔다. 일정을 이슈에 섞으면 반복 이슈의 상태·담당자 의미가 꼬이고 오픈소스 본체가 무거워진다.
- **기각**: 한 저장소에 HR까지 두기(HR 코드가 공개됨), 본체를 jar·npm으로 내보내 가져다 쓰기(패키지 배포 절차가 지금 규모에 무거움), 오피스를 공간 전환 안의 별도 공간으로 두기(사용자 반려: 한 워크스페이스에서 함께 보이길 원함), 이슈에 일정 속성 붙이기(A), 일정을 본체의 별도 기능으로 두기(B, D-066을 되돌림).
- **지금 상태**: 결정만 기록했다. 데모에는 아직 '일정' 라벨, 시각·종일·참석자가 있는 샘플 이슈, '일정'이라는 이름의 기본 캘린더 뷰가 남아 있고, 데모를 실제 앱으로 옮길 때 정리한다.

## D-072. 이슈 목록의 from/to는 기간 겹침이고, 완료 컬럼의 분류는 언제나 완료다 (2026-10-25)
- **무엇을 (T-004의 "from/to는 마감일 범위" 대체)**: 프로젝트·내 작업·전체 이슈 목록의 `from`/`to`는 이슈의 시작일~마감일 기간이 그 범위와 겹치는지로 거른다. 날짜가 하나만 있으면 그날 하루로 본다. 날짜가 없는 이슈는 범위를 주면 빠지고, `hasDates`로 따로 고른다. 컬럼 분류(todo·doing·done, D-066)는 완료 컬럼이면 done만 허용하고 다른 값은 400으로 거절한다. 생략하면 서버가 완료 여부에 맞춰 채운다.
- **왜**: 캘린더·타임라인(D-064·D-071)은 보이는 기간에 걸친 이슈를 모두 그려야 한다. 마감일 범위로는 이번 주에 시작해 다음 주에 끝나는 이슈가 이번 주 화면에서 빠진다. 전체 칸반은 분류로 묶으므로, 완료(`closed_at`)와 분류가 어긋나면 같은 이슈가 완료됐는데 진행 중 칸에 보인다.
- **기각**: 마감일 범위 유지(캘린더가 기간 막대를 못 그림), 시작일·마감일 필터를 따로 두기(화면이 겹침 조건을 매번 조합해야 함), 완료 컬럼의 다른 분류를 조용히 done으로 바꾸기(보낸 값과 저장된 값이 달라 원인을 찾기 어려움).
- **지금 상태**: T-006 1단계 서버에 구현했다. 옛 화면의 '마감일 이후/이전' 필터 이름은 3·4단계에서 화면을 옮기며 정리한다.

## D-073. 짧은 창도 새 이슈와 같은 창이고, 프로젝트는 뷰처럼 표시(아이콘·색)를 가진다 (2026-10-25)
- **무엇을**: 데스크톱의 짧은 창(CompactDialog: 확인, 초대, 새 워크스페이스, 칸·라벨 고치기 등)을 Astryx 대화상자 대신 새 이슈의 창(side-panel의 `form`, D-070)에 그린다. 위쪽 12dvh에 뜨고, 머리·몸·발 사이에 줄이나 다른 바탕이 없는 한 면이며, 너비만 내용에 따라 다르다(520·560·580·600px). 24px 안쪽 여백과 20px 제목으로 큼직하게 둔다. 휴대폰은 그대로 아래 시트다. 새 프로젝트는 리니어의 새 프로젝트 배치를 따른다: 표시, 상자 없는 큰 이름, 키를 담은 알약, 가는 줄 아래 설명.
- **프로젝트 표시**: 프로젝트는 뷰와 같은 아이콘 목록(`MARK_ICONS`)과 팔레트에서 아이콘과 색을 고른다(V7이 `color`를 더했고 `icon`은 V3부터 있었다). 사이드바·범위 전환·새 이슈의 칩·프로젝트 목록에 보이고, 표시가 없는 프로젝트(에이전트가 만든 것 등)는 키 첫 글자를 보인다. 프로젝트 설정 일반에서 바꾼다.
- **왜**: 사용자가 새 이슈와 나머지 창의 생김새·뜨는 높이를 맞추길 원했고, Astryx 대화상자는 몸 부분만 바탕이 달라 띠처럼 보였다. 프로젝트를 이름만으로 구별하기 어려워 뷰처럼 표시를 원했다.
- **기각**: Astryx 대화상자의 몸 바탕만 덮어쓰기(뜨는 높이·모양이 새 이슈와 계속 다름), 모든 창을 720px로 맞추기(확인 질문처럼 짧은 창이 비어 보임), 아이콘만 두고 색은 빼기(사용자가 뷰와 같은 선택을 원함).
- **함께 고친 것**: 창이 떠오르는 애니메이션(0.98배)이 걸린 채로 높이를 재서 몇 px 낮게 잡히고 스크롤바가 생기던 것, 빈 화면을 채우는 상자가 반올림으로 1px 넘쳐 페이지에 스크롤바가 생기던 것.

## D-074. 테두리 있는 입력칸은 모두 리니어 규격 하나다 (2026-10-25)
- **무엇을**: 앱의 테두리 있는 입력칸(Astryx TextInput·TextArea·선택 상자·날짜 등, 이메일 칸, 툴바 검색, 휴대폰 선택 창의 검색)을 리니어에서 잰 규격 하나로 그린다(`docs/08-design-language.md` 3절). 데스크톱에서 높이 36px, 좌우 12px, 모서리 8px, 13px 글자이고, 바탕은 칠하지 않아 놓인 면(카드·창·페이지)을 따르며, 테두리는 `--color-border-emphasized` 헤어라인이다. 마우스를 올려도 그대로이고, 초점은 테두리를 강조색 선으로 바꾼다(고리·번짐 없음). 라벨은 13px/500, 칸 위 7px이다. 인증 화면과 온보딩도 예외 없이 같다. 규격은 `app/styles/index.css`의 `--bit-field-*` 토큰 한 곳에 있고, Astryx 칸은 자기 토큰으로, BIT가 직접 그린 칸은 이 토큰으로 받는다.
- **예외로 둔 것**: 툴바 검색은 툴바 줄 높이(28px)를 지킨다(리니어도 툴바 검색은 작다). 휴대폰은 엄지용 48px와 16px 글자를 지킨다(iOS가 16px보다 작은 칸에서 화면을 확대함). 테두리 없는 칸(새 이슈·새 프로젝트 제목, 뷰 이름)과 메뉴 맨 위 검색 줄은 원래 테두리가 없다.
- **초점 색**: 처음에는 리니어처럼 초점에서 테두리를 강조색으로 바꿨으나, 사용자가 진하게 바뀌는 색이 예쁘지 않다고 해(PinProof #006) 초점에서도 테두리를 그대로 둔다. 커서가 어디에 입력되는지 보여 준다.
- **왜**: 사용자가 리니어처럼 깔끔하게, 예외 없이 똑같이 맞추길 원했다. 지금까지는 칸마다 바탕을 한 단계 밝게 칠하고 테두리가 거의 보이지 않았고, 인증 화면만 50px로 따로 컸다.
- **기각**: Astryx 칸을 감싸는 BIT 입력 부품 새로 만들기(26개 화면을 다 바꿔야 함), 화면마다 덮어쓰기(같은 규격이 여러 곳에 흩어짐).
- **덧붙임**: Astryx는 포인터가 거친 기기(터치 노트북 포함)에서 칸 글자를 16px로 올린다. 사용자의 노트북이 그 경우라 데스크톱 폭에서는 13px로 고정했다.

## D-075. 프로젝트 참여는 소속 표시이고 권한이 아니다 (2026-10-25)
- **무엇을**: 프로젝트에 구성원을 넣고 빼는 '참여'를 둔다(`project_member`, V8). 구성원 화면의 '참여 프로젝트' 열에 각 구성원이 속한 프로젝트가 표시(아이콘·이름)로 보이고, 누르면 그 사람의 참여 프로젝트 창이 열린다. 구성원을 관리하는 사람(관리자 이상)은 거기서 프로젝트마다 스위치로 넣고 빼며 바로 저장된다. 다른 사람은 읽기만 한다. 프로젝트를 만든 사람은 그 프로젝트에 자동으로 참여하고, V8은 기존 프로젝트에 만든 사람을 넣어 두었다. 워크스페이스를 떠난 사람의 참여는 목록에서 빠진다.
- **권한은 그대로**: 참여는 아무 권한도 주지 않는다. 워크스페이스 구성원이면 참여와 상관없이 모든 프로젝트를 읽고, 쓰기는 지금처럼 역할(D-040)로 정한다.
- **API**: `GET /workspaces/{w}/project-members`(워크스페이스 전체를 한 번에), `POST /workspaces/{w}/projects/{p}/members`(`userId`), `DELETE /workspaces/{w}/projects/{p}/members/{userId}`. 넣기와 빼기는 구성원 관리 권한과 프로젝트 설정 권한이 함께 필요하고, 보관한 프로젝트에서는 바꿀 수 없다.
- **왜**: 사용자가 구성원 화면에서 사람마다 참여 프로젝트를 보고 넣고 빼기를 원했고, 세 안 가운데 '소속 표시'를 골랐다.
- **기각**: 참여를 접근 권한으로 두기(비공개 프로젝트, 모든 조회 API에 권한 검사가 필요한 큰 작업), 담당 이슈가 있는 프로젝트를 읽기 전용으로 보여 주기(넣고 빼기를 할 수 없음).
- **남은 것**: 담당자 고르기에서 참여한 사람을 먼저 보이는 일 같은 활용은 아직 하지 않았다.

API 키로도 쓸 수 있어 에이전트가 같은 자리에 의견을 남긴다(D-021).

- **함께 고친 것**: 마크다운 습관대로 `- [ ] `를 치면 글머리 안에 `[ ]`가 글자로 남던 것을 할 일로 바꾼다(`[x] `는 체크).

## D-081. MCP는 세션 없는(stateless) Streamable HTTP이고, 도구는 각 모듈이 등록하며, 1차는 이슈 중심 10개다 (2026-10-25)
- **무엇을**: `/api/mcp`에 공식 MCP Java SDK(`mcp-core`·`mcp-json-jackson3` 2.1.0)의 `HttpServletStatelessServerTransport`를 서블릿으로 붙였다. 요청마다 API 키(Bearer)를 받아 키 주인으로 도구를 돌리고, 기록에 키의 에이전트 이름을 남긴다(D-021). 브라우저 세션은 거절한다. 도구는 `whoami`, `list_members`, `list_projects`, `list_labels`, `get_work_item_context`, `list_work_items`, `create_work_item`, `update_work_item`, `move_work_item`, `add_comment` 10개다(`docs/07-mcp.md`).
- **모듈 구조**: mcp 모듈은 등록 계약(`McpToolProvider`, `McpTool`, `McpArguments`)과 서버 설정만 갖는다. 각 모듈이 자기 application 계층에서 도구를 등록하므로(컨트롤러를 각 모듈이 갖는 것과 같다) 도구가 그 모듈의 Service를 직접 부르고 HTTP와 같은 권한·검증·기록을 탄다(D-022의 "Facade 호출" 취지). 다른 모듈 것이 필요하면 공개 Facade로만 부른다: 워크스페이스 고르기·구성원(`WorkspaceFacade.resolve`·`members`·`mine`), 라벨 목록(`LabelFacade.findAll`), 보드 칸(`ProjectFacade.boardColumns`), 타임라인(`TimelineFacade`). mcp 모듈은 아무 모듈에도 기대지 않아 순환이 없다.
- **왜 stateless**: 도구가 모두 묻고 답하는 한 번의 요청이고 서버가 먼저 보낼 것(진행 알림·되묻기)이 없다. 권한은 요청마다 키로 판정한다. 세션을 메모리에 두면 서버를 다시 띄울 때 연결된 에이전트가 끊기고, 서버를 늘릴 때 세션 고정이 필요하다. 사용자도 stateless를 원했다.
- **왜 10개**: 결정·세션·산출물 화면과 모듈이 아직 없거나(산출물 모듈은 빈 패키지) D-066 이후 결정기록이 라벨 이슈가 되어 D-022의 결정 도구와 모델이 어긋난다. 지금 있는 이슈·댓글·타임라인 위에서 "이슈 맥락 읽기 → 작업 → 댓글로 결과 → 상태 옮기기"가 끝나는 범위로 잡았다. 결정은 결정기록 라벨과 템플릿(D-077)으로 남긴다.
- **기각**: stateful Streamable HTTP(재시작에 약하고 쓸 기능이 없음), MCP를 직접 JSON-RPC로 구현(스펙 변화를 따라가야 함), Spring AI의 MCP 스타터(Spring Boot 4와 맞는 정식판을 확인하지 못했고 우리가 쓰는 건 전송 하나뿐), mcp 모듈이 각 모듈 Facade를 부르기(Facade마다 화면용 조회를 다시 만들어야 하고 Facade가 비대해짐), D-022의 24개 전부(서버부터 새로 만들 것이 많아 쓸 때까지 오래 걸림).
- **확인한 것**: 통합 테스트가 HTTP로 initialize → tools/list → 만들기·댓글·옮기기·맥락 읽기를 거치고, 세션 쿠키 요청이 거절되는지 본다. MCP Inspector CLI로 8092의 오름랩 데이터에서 whoami·맥락·목록을 확인했다.

## D-082. 배포는 태그를 푸시하면 Actions가 이미지를 만들어 GHCR에 올리고, 버전은 태그가 원본이다 (2026-10-25)
- **무엇을**: `v*` 태그를 푸시하면 `.github/workflows/release.yml`이 루트 `Dockerfile`로 이미지를 만들어 `ghcr.io/dev-goraebap/better-issue-tracker`에 올린다. 후보 `v0.8.0-rc.1`은 `0.8.0-rc.1`로만, 정식 `v0.8.0`은 `0.8.0`·`0.8`·`latest`로 올린다. 저장소 기본 토큰(`GITHUB_TOKEN`, `packages: write`)만 쓰고 linux/amd64만 만든다. 절차는 `bit-release` 스킬(검사 → 버전 맞추기 → 후보 태그 → 이미지 확인 → 같은 커밋에 정식 태그 → GitHub Release)이다.

- **감수하는 것**: 저장소가 비공개라 이미지도 비공개다. 다른 서버에서 받으려면 `read:packages` 권한으로 `docker login ghcr.io`가 필요하다. 비공개 저장소의 Actions 무료 시간(월 2,000분)을 쓴다.

## D-083. 모든 ID는 UUID 대신 첫 글자가 영문인 10자(`A-Za-z0-9`)이고, V9가 옛 ID를 한 번에 바꾼다 (2026-10-26)
- **BIT 결정기록**: BIT-8
- **무엇을**: DB 기본 키·외래 키·다형 참조, API, 화면 주소의 ID가 모두 `[A-Za-z][A-Za-z0-9]{9}` 하나다(BIT-1). 서버의 `shared/domain/Ids`가 `SecureRandom`으로 만들고(`newId`), 경로·커서의 값은 `Ids.parse`로 검사한다. Java 타입은 값 타입 없이 `String`이고, jOOQ는 `uuid` 열을 forcedType으로 `VARCHAR`로 만든다. ID는 대소문자를 구분한다(UUID는 소문자로 맞춰 받던 것과 다르다).
- **마이그레이션(V9)**: 옛 UUID마다 새 ID 하나를 정한 대응표(임시 표)를 만들고, 그 표로 97개 열(23개 표)과 글 안의 ID(활동 payload의 changeId·commentId·칸·담당자·대체 결정·라벨 목록, 뷰 필터, 트윅의 뷰 키)를 같은 값으로 바꾼다. Flyway의 트랜잭션 안에서는 `PRAGMA foreign_keys`를 바꿀 수 없어 `PRAGMA defer_foreign_keys=ON`으로 외래 키 검사를 커밋 때로 미루고 UPDATE만 쓴다(표 다시 만들기 없음). relates_to 링크는 양 끝을 글자 순으로 두므로(`ck_link_symmetric_order`) 새 ID로 순서가 뒤집히면 양 끝을 바꾼다. 어디서든 실패하면(새 ID 두 개가 겹치는 것 포함) 전체가 되돌려지고 다음 기동에서 다시 시도한다.
- **왜 첫 글자가 영문인가**: V1~V8은 열을 `uuid`로 선언했고 SQLite에서 이 타입은 NUMERIC 친화도라, `0123456789`처럼 숫자로 읽히는 글자는 정수로 바뀌어 저장된다(앞의 0이 사라진다). 열 타입을 바꾸려면 23개 표를 모두 다시 만들어야 하므로, 첫 글자를 영문으로 두어 숫자로 읽힐 수 없게 했다. 경우의 수는 52·62⁹ ≈ 7.0×10¹⁷이다.
- **왜 재시도를 두지 않는가**: 충돌은 기본 키 고유 제약이 막아 덮어쓰기는 일어나지 않고 그 요청만 실패한다. 한 표에 100만 행이 쌓여도 한 번이라도 겹칠 확률이 약 7×10⁻⁷이라, 모든 저장 지점에 재시도를 넣는 비용이 크다.
- **왜 String인가**: 코드 규칙상 값 객체는 검증·정규화가 꼭 필요한 값에만 둔다. `Id` 타입을 두면 Spring 변환기·Jackson·jOOQ 변환기·OpenAPI 매핑을 모두 새로 붙여야 하는데, UUID 때도 ID끼리 타입으로 구분하지 않았으므로 얻는 안전이 없다.
- **기각**: 주소만 슬러그·키로 바꾸기(내부에 UUID가 남는다, BIT-1의 A), 내부 UUID와 공개 ID 두 열(어디서 무엇을 쓸지 계속 가려야 한다, C), 표를 모두 다시 만들어 열 타입을 `varchar(10)`으로 바꾸기(외래 키를 끌 수 없는 트랜잭션 안에서 23개 표를 다시 만들어야 하고 실패 위험이 크다), Java 마이그레이션으로 `SecureRandom` 쓰기(마이그레이션이 SQL이라는 규칙과 jOOQ 생성이 SQL만 읽는 것과 어긋난다. 한 번 쓰는 대응표는 SQLite `random()`으로 충분하다).
- **감수하는 것**: 옛 주소(북마크, 붙여 넣은 링크, 본문 속 `/w/<UUID>/…`)는 깨진다. 옛 주소는 모두 `/w/<UUID>`로 시작해 워크스페이스 선택 화면으로 돌아간다. 그림 프로필(D-045, 사용자 ID로 고름)이 사람마다 바뀐다. API 키와 로그인 세션 토큰은 ID를 품지 않아 그대로 쓴다. CSRF 쿠키는 세션 ID에 묶여 있어 배포 뒤 첫 쓰기에서 한 번 거절되지만, 화면이 새 토큰을 받아 다시 보낸다(`command`의 재시도).

## D-084. 작업항목은 어디서나 '이슈'이고, 화면 주소는 풀어 쓴 복수형이다 (2026-10-26, 이름은 D-091로 대체됨)
- **BIT 결정기록**: BIT-4
- **무엇을**: D-062에서 이름을 '이슈'로 정하고 미뤄 둔 코드 쪽 이름을 모두 바꾼다. 서버 모듈 `workitem` → `issue`(`IssueFacade`·`IssueService`…), 표 `work_item`·`work_item_label` → `issue`·`issue_label`, 열 `project.last_work_item_number` → `last_issue_number`, 다형 대상 종류 `work_item` → `issue`(link·activity·comment), API `/projects/{p}/work-items` → `/projects/{p}/issues`(`/work-items/by-ref` → `/issues/by-ref`), 오류 코드 `WORKITEM_*` → `ISSUE_*`, MCP 도구 `get_work_item_context`·`list_work_items`·`create_work_item`·`update_work_item`·`move_work_item` → `get_issue_context`·`list_issues`·`create_issue`·`update_issue`·`move_issue`, 화면 `entities/work-item` → `entities/issue`.
- **주소**: 화면 주소를 API와 같은 풀어 쓴 복수형으로 맞춘다. `/w/$w` → `/workspaces/$w`, `/w/$w/p/$p` → `/workspaces/$w/projects/$p`, 이슈 `/workspaces/$w/projects/$p/issues/$id`(편집 `/edit`, 새 이슈 `/issues/new`), 키로 찾기 `/w/$w/r/BIT-42` → `/workspaces/$w/issues/BIT-42`. 옛 짧은 주소(`/w/…`, `/p/…`, `/work-items/…`, `/r/…`)는 같은 화면의 새 주소로 넘긴다.
- **마이그레이션(V10)**: `issue`·`issue_label`은 이름 바꾸기가 아니라 다시 만든다(SQLite는 제약 이름을 저장된 정의에 두고 바꾸지 못해, 이름을 바꾸면 `work_item_pkey`·`ck_work_item_*`가 남는다). link·activity·comment는 CHECK가 대상 종류를 나열하므로 다시 만든다. relates_to 링크는 양 끝을 글자 순으로 두는데(`ck_link_symmetric_order`, `Link.Edge`) `issue`는 `session_record`보다 앞이고 `work_item`은 뒤였으므로 세션-이슈 링크의 양 끝을 바꾼다. 외래 키 검사는 V9처럼 `defer_foreign_keys`로 커밋 때 한다. ID 열의 선언 타입은 다른 표와 같이 `uuid`로 둔다.
- **왜**: 화면은 '이슈'가 93번, '작업항목'이 2번이었고 제품 이름과 MCP 안내문도 이슈다. 코드·API·MCP만 work item이라 사람과 에이전트가 같은 것을 두 이름으로 불렀다. 주소는 `/w/…/p/…/work-items/…`처럼 한 주소 안에서 줄임과 풀어 쓰기가 섞여 있었고, API는 처음부터 풀어 쓴 복수형이었다(사용자 결정).
- **기각**: 모두 줄이기(`/w/$w/p/$p/i/$id`, 주소는 짧지만 API와 규칙이 갈리고 읽히지 않는다), 작업항목(work item)으로 통일(D-062에서 회의록·노트를 담기에 어색하다고 기각, 화면 문구 93곳을 바꿔야 한다), 표 이름만 바꾸고 제약 이름은 두기(이름 규칙과 어긋난 채 남는다), 옛 MCP 도구 이름을 별칭으로 남기기(쓰는 에이전트가 사용자 한 명뿐이라 지침 두 곳을 고치는 편이 단순하다).
- **감수하는 것**: 배포 전에 쓰던 MCP 도구 이름이 사라진다. 에이전트 지침(이 저장소 `AGENTS.md`, 안전관리솔루션의 `CLAUDE.local.md`)의 도구 이름을 배포와 함께 바꿔야 한다. 이슈 상세 주소는 ID가 10자라 약 45자에서 약 70자로 길어진다. 지난 결정 기록과 작업 지시서(T-00x)의 옛 이름은 기록이라 그대로 둔다.

## D-085. 결정기록은 앞으로 다른 작업이 따라야 할 선택만 담고, 그 선택이 나온 작업 이슈와 따로 만든다 (2026-10-26, 결정기록의 자리는 D-094로 바뀜)
- **BIT 결정기록**: BIT-7
- **무엇을**: 결정기록은 여전히 `결정기록` 시스템 라벨을 단 이슈(D-066)지만, 담는 것과 만드는 때를 좁힌다. 기존 결정이나 지켜 오던 동작을 바꿀 때, 여러 안 중 하나를 골라 이후 작업이 그것을 따라야 할 때만 쓴다. 한 번 하고 끝나는 선택, 새 기능 추가 자체, 딸려 바뀐 것, 오타는 작업 이슈의 댓글로 남긴다. 작업 이슈(끝나면 닫힘)와 결정기록(대체될 때까지 유효)은 따로 만들고 서로의 참조를 적는다. 본문은 맥락 / 결정 / 검토한 대안(실제로 따져 본 안이 있을 때만)이고 맥락과 결정은 각 2~5문장이다. 결정한 순간에 쓰고, 확정한 결정은 고치지 않고 새 결정기록으로 대체한다. MCP 안내문·도구 설명, 내장 결정기록 템플릿(D-077), 배포용 스킬 `skills/better-issue-tracker/`가 이 기준을 쓴다.
- **왜**: BIT-1(ID 형식 바꾸기)은 할 일인데 결정기록 라벨이 붙었다. "의미 있는 판단은 결정기록"이라는 안내가 모호해 선택지를 비교한 작업이 모두 결정기록처럼 보였고, 6섹션 양식이 그런 작업 정리에도 맞았으며, 작업과 결정을 잇는 MCP 도구가 없어 하나로 몰아넣었다. 사용자가 만든 Gitifact의 결정기록 규칙(쓰는 때 표, 설명 대상 연결, 고치지 않고 새 기록, 섹션 길이)이 같은 문제를 이미 풀고 있어 이슈 트래커에 맞게 옮겼다(사용자 결정).
- **기각**: 6섹션 양식에 쓰는 때 기준만 더하기(선택지와 기각한 대안이 겹치고, 후속 작업은 글이 아니라 파생 이슈여야 이행률 D-012가 계산된다), 작업 이슈 하나에 결정까지 담기(대체·이행률·근거 찾기가 작업 단위로 섞인다), 결정을 BIT 밖 문서로만 두기(에이전트가 작업 맥락에서 찾지 못한다).
- **아직 없는 것**: 이슈끼리 잇는 MCP 도구와 결정 상태(제안·확정·대체)를 바꾸는 MCP 도구. 그때까지 참조는 본문과 댓글에 적고, 확정은 완료 칸으로 옮겨 나타낸다. `docs/decisions.md`의 지난 결정은 6섹션에 가까운 옛 형식 그대로 둔다.

## D-086. 마크의 아이콘은 lucide 전체에서 고르고 값은 컴포넌트 이름이며, 고르기와 그리기는 공용 컴포넌트 하나씩이다 (2026-10-26)
- **BIT 결정기록**: BIT-13
- **무엇을**: 프로젝트·뷰 마크의 아이콘 값은 lucide 컴포넌트 이름(`LayoutList`, `Telescope`)이다. 전에 쓰던 18개 이름(`list`, `board`, `decision`…)은 그대로 읽어 앱의 NavIcon으로 그리고, 선택기에서는 대응하는 lucide 아이콘이 골라진 것으로 보인다(`LEGACY_MARKS`). 고르기는 `shared/ui/icon-picker`의 `IconPicker` 하나다(데스크톱은 팝오버, 휴대폰은 바텀시트, 검색·16색·자주 쓰는 아이콘·전체 1,903개). 프로젝트 설정, 새 프로젝트, 뷰 편집이 쓴다. 그리기는 `MarkIcon` 하나로 `ProjectMark`와 뷰 탭이 쓴다. 팔레트는 16색으로 늘렸고(기존 8색 값은 그대로, 새 뷰·라벨의 기본은 `DEFAULT_MARK_COLOR`), 라벨 색 고르기도 같은 팔레트다.
- **불러오기**: lucide 전체(`lucide-react/dist/esm/icons/index.mjs`)는 선택기를 열거나 전체 세트의 아이콘이 처음 필요할 때 한 덩어리(약 613kB, gzip 162kB)로 늦게 받는다. 첫 화면 번들에는 앱이 이름으로 쓰는 아이콘만 남는다. 검색은 아이콘의 영어 이름과 자주 찾는 한국어 낱말(달력, 사람, 로켓…)의 대응표다.
- **왜**: 18개로는 프로젝트를 구분하기 어려웠다(사용자 요청). 서버는 아이콘을 32자 글자로만 받으므로 값의 형식을 바꿔도 서버·DB가 바뀌지 않는다.
- **기각**: 이모지도 제공하기(만들었다가 사용자가 아이콘만 원해 뺐다), 아이콘마다 따로 늦게 받기(`DynamicIcon`, 빌드 파일 1,900개와 그리드를 열 때 요청 수백 개), 옛 이름을 마이그레이션으로 바꾸기(읽을 때 대응표로 충분하다), 케밥 이름(`layout-list`)으로 저장하기(숫자가 든 이름의 변환이 모호하다).

## D-087. 저장소 연동은 카네오와 같은 범위를 토큰 하나로 하고, 바뀐 것은 웹훅과 커밋 뒤 동기화로 양쪽에 반영한다 (2026-10-26)
- **BIT 결정기록**: BIT-16
- **무엇을**: 프로젝트마다 GitHub·GitLab·Gitea 저장소를 호스트별로 하나씩 잇는다(`repository_integration`). 인증은 세 호스트 모두 저장소 토큰이다(D-028, GitHub App 없이). 토큰과 웹훅 비밀값은 AES-GCM으로 암호화해 둔다. 연결할 때 호스트에 먼저 물어 틀린 토큰·이름은 호스트가 거절한 이유와 함께 막고, 웹훅은 토큰 권한이 되면 BIT가 등록하고 안 되면 주소와 비밀값을 보여 사람이 등록한다. 웹훅(`/api/v1/hooks/{id}`, 서명만 확인)은 이슈 키(`BIT-42`)를 단 브랜치·PR·커밋을 이슈에 잇고(`code_link`), 이벤트별 규칙(`integration_rule`, 없으면 칸 분류로 정한 기본 칸)으로 앞쪽 칸으로만 옮긴다. 저장소 이슈의 열기·닫기·고치기·댓글은 미러된 BIT 이슈에, BIT 이슈의 만들기·제목·설명·우선순위·라벨·칸·댓글은 저장소 이슈에 반영한다(라벨 `priority:x`, `status:<칸>`). 열린 이슈 가져오기, 이슈 상세의 연결된 코드, 브랜치 이름 복사, 목록·보드의 PR 배지가 화면이다. 카네오와 달리 커밋 메시지의 이슈 키도 읽는다.
- **행위자**: 웹훅이 바꾼 것은 연결한 사람이 `INTEGRATION` 방식(`CurrentUser.Method`)으로, 에이전트 이름 `GitHub · 계정`으로 남는다. 이 방식은 서버가 서명을 확인한 뒤에만 만들고 요청에서는 만들 수 없다. `CurrentUser.agent()`가 기록할 에이전트를 정한다(D-021).
- **메아리 막기**: BIT가 저장소에 쓴 이슈 본문·댓글에는 숨은 표시(`<!-- bit:… -->`)를 넣어, 그 웹훅이 돌아오면 건너뛴다. 저장소 이슈에서 온 변경(에이전트가 호스트 이름)은 저장소로 다시 보내지 않는다. 다만 저장소의 코드(브랜치 push·PR 열기·병합)가 옮긴 칸은 그 이슈가 모르는 소식이라 상태 라벨과 열림/닫힘을 저장소 이슈에 반영한다(BIT-18). 저장소 이슈 웹훅의 수정 시각(`updated_at`)이 BIT가 그 이슈에 마지막으로 쓴 시각보다 이르면, 늦게 도착한 앞선 쓰기의 메아리로 보고 적용하지 않는다. 그러지 않으면 이슈가 앞 칸으로 되돌아간다. 미러 반영은 같은 값이면 바꾸지 않아 반복되지 않는다.
- **트랜잭션 밖**: 호스트 호출은 트랜잭션 안에서 하지 않는다. 연결·가져오기는 호스트를 부른 뒤 짧은 트랜잭션으로 쓰고(`TransactionTemplate`), BIT에서 저장소로 가는 동기화는 커밋 뒤 이벤트를 한 줄짜리 실행기(`repositorySyncExecutor`)가 하나씩 보낸다. 실패는 연동의 `last_error`에 남아 설정 화면에 보인다. 암호화 키가 없으면 이 기능만 꺼진다(D-030, `capabilities.gitIntegration`).
- **왜**: 사용자가 카네오 기능 전부를 한 번에 원했다(BIT-9). 토큰 방식은 D-028에서 이미 정했고(셀프호스팅마다 GitHub App을 만들 필요가 없다), 세 호스트가 같은 모양이라 어댑터(`GitHost`)만 다르다.
- **기각**: GitHub App(D-028에서 기각), 저장소 이슈만 잇고 양방향 반영은 빼기(사용자가 전부를 원함), 웹훅을 받은 요청 안에서 호스트로 되돌려 쓰기(요청과 트랜잭션이 호스트 속도에 묶인다), 계정 이름으로 메아리 거르기(토큰 주인이 직접 쓴 저장소 댓글까지 버린다), `git_repository`·`code_ref`·`link implements` 설계 그대로(06-schema 7절, 브랜치·PR·커밋 모두 이슈 하나의 표시라 `code_link` 하나가 단순하다).
- **아직 없는 것**: 한 저장소를 여러 프로젝트가 공유하는 연결(카네오 GitHub만 됨), 브랜치 이름 패턴 설정, 가져오기 이어하기, 동기화 범위 라벨 필터, MCP `get_issue_context`에 연결된 코드 넣기.

## D-088. 뷰 순서는 홈과 프로젝트마다 따로 두고 첫 뷰가 그 범위의 기본 뷰이며, 브레드크럼은 선택기 대신 그 기본 뷰로 가는 링크다 (2026-10-26)
- **무엇을 (D-065 일부 대체)**: 뷰 정의는 지금처럼 워크스페이스 공용이고 홈과 모든 프로젝트가 같은 뷰를 쓴다(D-068). 순서만 범위마다 따로 둔다. 홈과 각 프로젝트는 자기 순서를 갖고, 맨 앞 뷰가 그 범위의 기본 뷰다. 주소에 뷰(`v`)가 없으면 기본 뷰가 열리고, 기본 뷰를 고르면 주소에서 `v`가 빠진다. 순서는 탭 줄의 '뷰 순서' 창에서 보드 칸처럼 끌어 옮기거나 Alt+↑/↓로 바꾸고, 워크스페이스 소유자·관리자만 바꾼다(프로젝트 설정과 같은 권한). 브레드크럼의 두 번째 단계는 범위 선택기(전체·프로젝트 목록·프로젝트 만들기)가 아니라 링크 글자다. 홈은 '홈'(전체 X), 프로젝트는 그 이름이고, 누르면 그 범위의 기본 뷰로 간다. 다른 프로젝트로는 사이드바에서 간다.
- **어떻게**: `issue_view_order`(워크스페이스, 범위, 뷰 키 JSON 배열) 한 행이 범위 하나의 순서다(V12). 배열에 없는 뷰(새로 만든 뷰 등)는 워크스페이스 순서로 뒤에 붙고, 지운 뷰는 조회에서 빠진다. API는 `GET /workspaces/{w}/view-orders`(범위별 순서 전부), `PUT /workspaces/{w}/view-orders/{home|프로젝트 ID}`. 화면의 끌어 옮기기는 보드 칸 설정의 것을 `shared/lib/row-reorder`(useRowReorder)로 옮겨 함께 쓴다.
- **왜**: 사용자가 정했다(BIT-21). 선택기는 링크 하나로 갈 곳을 메뉴로 한 번 더 고르게 했고, 이름이 '전체'라 홈이라는 걸 알기 어려웠다. 범위마다 순서를 두면 프로젝트마다 시작 화면(예: 홈은 전체 이슈, 프로젝트는 진행 보드)을 다르게 할 수 있고, 순서의 첫 뷰를 기본으로 삼으면 '기본 뷰 지정'을 따로 만들지 않아도 된다.
- **기각**: 워크스페이스에 순서 하나(기존 `position`만, 홈과 모든 프로젝트가 같은 기본 뷰), 사람마다 순서(같은 링크가 사람마다 다른 뷰로 열려 팀이 정한 시작 화면이 없어짐), '기본 뷰' 표시를 따로 두기(순서와 기본이 따로 놀아 둘을 맞춰야 함), 범위 선택기 유지(D-065).
- **기록**: BIT 결정기록 BIT-23.

## D-089. 이슈 상세는 읽기 전용이고, 제목·설명·속성은 수정 페이지에서 한 번에 저장한다 (2026-10-26)
- **BIT 결정기록**: BIT-27 (작업 이슈 BIT-22)
- **무엇을**: 이슈 상세(페이지와 모달, D-069)는 읽기만 하고, 열고 닫아도 서버에 쓰지 않는다. 상세에 남는 쓰기는 댓글, 보관, 삭제뿐이다. 설명은 `MarkdownView`로 보이고 속성은 표시만 한다. 제목·설명·상태·우선순위·담당자·시작일·기한·라벨은 수정 페이지(`…/issues/$issueId/edit`)에서 고친다. 이 페이지는 새 이슈 페이지(D-070)와 같은 모양(테두리 없는 제목·본문, 아래 속성 알약 줄)이다. 저장은 바뀐 값만 연 버전으로 보내고, 상태가 바뀌었으면 그 뒤에 이동 요청을 따로 보낸다. D-076의 '설명은 그 자리에서 쓰고 저절로 저장'과 D-067의 '상세 속성 알약은 즉시 저장'을 대체한다.
- **왜**: 편집기는 표처럼 다루지 못하는 블록을 지운 마크다운을 입력 없이 내보낸다. 그래서 상세를 열기만 해도 자동 저장이 돌아 PATCH가 2번 나가고, 활동에 '설명을 고쳤습니다'가 남고, 표가 사라졌다. 사용자는 상세에서는 아무것도 고칠 수 없기를 원했다(사용자 결정).
- **기각**: 속성 알약은 상세에 두고 제목·설명만 읽기 전용(리니어 방식이지만 요청과 어긋난다), 상태(칸 이동)만 상세에 남기기(상태를 바꾸는 곳이 두 군데가 된다).
- **감수하는 것**: 담당자 하나를 바꾸려 해도 편집 → 저장을 거쳐 클릭이 2번 는다. 편집기가 표를 지우는 문제는 수정 페이지에 그대로 남는다(BIT-24).

## D-090. 파일 저장소는 환경변수로 정하고, 사진 대표색은 브라우저가 뽑으며, 1차는 설명·댓글·아바타·로고에 파일 하나 20MB다 (2026-10-26)
- **BIT 결정기록**: BIT-26. 구현은 BIT-28(서버), BIT-29(설명·댓글), BIT-30(아바타·로고).
- **무엇을**: D-029·`bit-api-contract` 04의 hohohr 구조를 그대로 두고 남은 선택을 정한다.
  - **설정**: 환경변수 `STORAGE_ENDPOINT`·`STORAGE_PUBLIC_ENDPOINT`·`STORAGE_REGION`·`STORAGE_BUCKET`·`STORAGE_ACCESS_KEY`·`STORAGE_SECRET_KEY`·`STORAGE_KEY_PREFIX`. 주소가 없으면 데이터 볼륨(`STORAGE_LOCAL_ROOT`)에 둔다. 관리자 화면에서는 입력하지 않는다. 서버 기능 화면(D-061)에 어댑터·버킷과 시작할 때 한 연결 점검 결과만 읽기 전용으로 보인다. S3 호환을 설정했는데 연결이 안 되면 로컬로 바꾸지 않고 파일 기능만 끈다(D-030). 로컬로 바꾸면 파일이 두 저장소에 갈라지기 때문이다.
  - **대표색**: 브라우저가 올리기 전에 사진을 96px로 줄여 colorthief로 대표색을 뽑고, 가로·세로와 함께 업로드에 싣는다(hohohr `image-traits`). 서버는 `#RRGGBB` 형식과 크기 범위만 검사한다. 화면은 저장된 가로·세로로 자리를 잡아 대표색으로 칠하고, 사진이 오면 페이드인한다. 이미 캐시에 있는 사진은 바로 보인다. REST로 직접 올려 값이 없으면 중립색을 쓴다.
  - **1차 위치**: 이슈 설명·댓글(MarkdownEditor 붙여넣기·끌어 놓기·/사진·/파일, 본문은 `attachment:<id>`, 이슈 아래 파일 모음)과 내 아바타·워크스페이스 로고. 아바타·로고는 브라우저에서 정사각 JPEG(1MB 이하)로 잘라 올리고, 서버가 사진 id가 들어간 고정 주소로 바이트를 직접 내려 줘 오래 캐시한다(hohohr `AvatarService`). 문서함 정본은 같은 `blob`을 쓰고, 화면·흐름은 문서함 설계에서 정한다.
  - **제한**: 파일 하나 기본 20MB(`STORAGE_MAX_FILE_MB`), 이슈 합계 없음. 형식은 hohohr `FileFormat`에서 녹음을 뺀 PDF·HWP/HWPX·DOC/DOCX·XLS/XLSX·PPT/PPTX·JPEG/PNG/WebP/GIF·ZIP·MD/TXT/CSV이고, SVG는 1차에서 뺀다(새니타이징이 따로 필요하다).
- **왜**: 사용자가 정했다. 서버 설정이 모두 환경변수라 저장소도 같은 자리에서 바꾸는 것이 자연스럽고, hohohr 코드를 거의 그대로 옮길 수 있다. 대표색은 브라우저가 이미 디코딩한 사진에서 뽑으면 서버에 라이브러리와 디코딩 시간이 늘지 않는다.
- **감수하는 것**: 저장소를 바꾸려면 compose를 고치고 재시작해야 하고, 옛 저장소의 파일을 옮기는 도구는 없다. 에이전트가 REST로 올린 사진에는 대표색이 없다. 한 이슈에 파일이 쌓이는 만큼 저장소가 커진다.
- **기각**: 관리자 화면 입력(또는 환경변수와 둘 다, 저장소를 바꾸면 파일별 저장소 기록·옮기기가 필요하다), 서버가 대표색 추출(또는 브라우저 값이 없을 때 보충, JDK가 WebP를 못 읽고 확정이 디코딩만큼 느려진다), 설명·댓글만 또는 모듈·API만 먼저(사용자가 아바타·로고까지 원함), hohohr의 한 글 합계 10MB(스크린샷 몇 장과 로그로 금방 찬다), 파일당 + 이슈 합계(댓글마다 합계를 세고 넘쳤을 때 보여 줄 화면이 더 필요하다).
- **아직 없는 것**: 로컬 → S3 옮기기 도구, SVG·녹음, 문서함 업로드 화면.

## D-091. 일감은 화면에서 '업무', 그 밖의 모든 곳에서 work item이다 (2026-10-26)
- **BIT 결정기록**: BIT-32. 논의는 BIT-31.
- **무엇을 (D-084의 이름 대체)**: 한국어 화면과 문서에서만 '업무'라고 쓰고, 나머지는 모두 work item이다. DB `work_item`, Java `WorkItem`, 화면 주소·API `/work-items`, JSON `workItem`·`workItemId`, MCP `create_work_item`·`list_work_items` 같은 도구 이름, 스킬과 MCP 안내문이 해당한다. 업무 키(`BIT-25`)와 주소를 풀어 쓴 복수형으로 두는 규칙(D-084)은 그대로다. 업무 안의 코드와 잇는 모양은 화면에서 '작업'이라 부른다(D-092).
- **왜**: 사용자가 정했다. 한국 정서에 '이슈'는 문제나 사건으로 읽혀 어색하다. 영어 이름은 한 줄로 맞추기를 원했다. work item은 Azure DevOps가 처음부터 쓰고 Jira·Plane이 최근 issue에서 바꾼 이름이며, D-084 전에 BIT가 쓰던 이름이다.
- **감수하는 것**: V10(이름을 `issue`로 바꿈)에 이어 또 이름 바꾸기 마이그레이션이 필요하다. 운영 MCP 도구 이름이 바뀌어 연결된 에이전트와 배포한 스킬(`better-issue-tracker`)을 다시 맞춘다. GitHub·GitLab 이슈 동기화(D-087)에서는 바깥의 issue와 안의 work item을 대응시킨다.
- **기각**: 화면만 '업무'로 두고 코드·API·MCP는 `issue` 그대로(권장안이었지만 코드와 화면 이름이 갈린다), `works`(영어로 작품·공장으로 읽히고 선례가 없다).

## D-092. 업무는 종류 둘(작업·일정)과 선택 속성이고, 일정·반복·알림은 본체가 맡는다 (2026-10-26)
- **BIT 결정기록**: BIT-33. 논의는 BIT-31.
- **무엇을 (D-066의 유형 없음, D-071의 일정 부분 대체)**: 업무는 프로젝트에 속한 제목과 마크다운 본문(D-076)에 선택 속성(상태·우선순위·사람 여럿·라벨·기간·반복)을 붙인 것이고, 모두 필수가 아니다. 플랫폼이 종류 칸 둘을 고정 제공한다.
  - **작업**: 담당자, 날짜 기간·마감, 상태(보드 칸), 하위 작업(`subtask_of`), Git 브랜치·PR·커밋(D-087).
  - **일정**: 참석자, 시각 단위 시작·끝과 종일, 반복, 시작 전 알림.
  - 화면의 '새 이슈' 버튼은 '만들기 ▾'(작업·일정)이다. 종류가 양식, 상세, 사람 칸의 뜻을 정한다. 사람 칸은 데이터로는 하나이고 작업에서는 담당자, 일정에서는 참석자로 부른다. 에픽·스토리·버그, 회의·면담 같은 세부 분류는 라벨이다(D-066). 종류를 바꿀 때 버리는 값(일정 → 작업이면 시각·반복)은 구현 때 정한다.
- **반복**: 회차마다 서로 다른 업무다. 규칙(일정, 템플릿 D-077, 프로젝트)이 때가 되면 템플릿을 복제해 새 업무를 만들고, 복제본에는 나온 규칙과 회차를 남긴다. 편집은 셋이다. '이번 회차만'은 평소 편집이다. '이 회차부터 이후 모두'는 바꾼 속성만 이 회차와 뒤 복제본에 적용하고 규칙도 고친다. 본문은 덮어쓰지 않고 템플릿만 바꾼다. '이후 회차 취소'는 뒤 복제본을 지우고 규칙을 끝낸다. 언제 복제할지(다음 하나, 몇 주치)는 구현 때 정한다.
- **HR과 알림**: 일정은 본체 업무 하나로 통일한다. HR 확장은 SandboxHr `calendar_event`를 옮기지 않고, 휴가·연장근무·공휴일처럼 업무가 아닌 것만 캘린더 출처로 끼운다. 알림은 HR과 상관없이 본체 기능으로 만든다. 회의실은 나중에 HR 쪽에서, 공개 범위는 뺀다. ICS 가져오기는 나중이다.
- **왜**: 사용자가 정했다. 작업과 일정은 사람·시간·흐름의 뜻이 달라, 속성이 있는지로 짐작하면 시각이 있는 작업이 일정처럼 보이고 뷰가 간접 조건으로 걸러야 한다. 메뉴가 '업무' 하나로 고정되고 세부 분류는 라벨이라, D-066이 유형을 뺀 이유(범주마다 탭·메뉴가 늘고 팀마다 다른 분류를 담지 못함)는 해당하지 않는다. 회차를 복제하면 회차마다 내용·댓글·연결이 깔끔하다. 일정을 두 곳에서 만들면 같은 회의가 둘 생긴다.
- **구현 (BIT-37, V16)**: 사람은 `work_item_person`(20명 이하), 일정 시각은 `starts_at`·`ends_at`, 종일은 `all_day`와 날짜다. 일정은 칸이 없고 백로그·보드 개수에서 빠진다. 종류를 바꿀 때: 작업 → 일정은 칸을 떠나고(그 칸은 순서를 다시 맞춤) 날짜가 있으면 그 날들의 종일 일정이 된다. 일정 → 작업은 시각을 버리고 날짜는 둔다. 화면의 시각은 그 사람의 시간대이고 서버는 순간(UTC)으로 둔다. 목록의 from/to는 시각 일정을 앞뒤 하루 여유로 거르고, 화면이 자기 날짜에 놓는다.
- **반복 구현 (BIT-38, V17)**: 규칙(`recurrence`)이 처음 업무를 본보기로 복사하고, 회차는 따로 만든 업무다(`recurrence_id`, `occurrence_on`). 일정은 8주 앞까지 미리 만들어 캘린더에 보이고, 작업은 마지막 회차의 날이 오면 다음 하나만 만들어 보드에 하나씩 있다. 매시간 도는 작업이 회차를 만들고, 서버가 멈췄던 사이 지난 날은 늦게 만들지 않는다. 회차를 만드는 사람은 규칙을 마지막으로 정한 구성원이고 에이전트 이름은 '반복'이다. 고치기는 '이 회차만'(기본)과 '이 회차부터 이후 모두'다. 이후 모두는 요청이 바꾼 값만 규칙과 이미 만든 이후 회차에 옮기고, 설명은 규칙에만 옮긴다(각 회차의 메모는 그 회차 것). 시각은 하루 안의 시각과 길이로 옮기고 회차의 날은 그대로다. 규칙 자체(매주 → 격주 등)를 바꾸면 그 회차부터 새 규칙이 되고, 옛 규칙은 전날로 끝나며 이후 회차는 지운다. '이후 회차 취소'는 이후 회차를 지우고 규칙을 그 회차의 날로 끝낸다. 지운 회차는 관리자가 되살릴 수 있다.
- **알림 구현 (BIT-39, V18)**: 알림은 받은함(위쪽 종)에 쌓이고, 메일이 설정돼 있으면(`SPRING_MAIL_HOST` 등, D-030) 메일로도 간다. 받는 경우: 작업의 담당자로 넣어짐, 일정에 초대됨, 내가 맡거나 만든 업무에 댓글, 내가 참석하는 일정의 시각이 바뀜, 작업의 기한 당일(9~21시 정각마다 보고 한 번만), 일정 시작 전(일정마다 '알림 N분 전', 새 시각 일정은 10분 전). 자기 변경은 알리지 않고, 반복 규칙이 만든 회차는 사람을 다시 알리지 않으며, '이후 모두'로 여러 회차가 바뀌어도 한 사람에게 한 번이다. 알림은 변경과 같은 트랜잭션에서 만들고, 메일은 1분마다 도는 작업이 트랜잭션 밖에서 보낸다(D-028). 메일이 켜지기 전 한 시간보다 오래된 알림은 늦게 보내지 않는다. 문장(본문)은 만들 때 정해 받은함과 메일이 같은 말을 한다. 알림 설정(끄기·방식 고르기)은 아직 없다.
- **감수하는 것**: D-066의 "유형 없음"이 둘로 되돌아가고, 사용자가 세 번째 종류를 만들 수 없다. 미리 만든 범위 밖의 회차는 캘린더에 보이지 않는다. 참석자별 알림을 본체에 새로 만들고, HR의 기존 일정 데이터를 업무로 옮긴다. 담당자가 하나(`assignee_id`)이고 기간이 날짜뿐(`start_date`·`due_date`)인 스키마를 바꾼다.
- **기각**: 만들기 메뉴만 나누고 데이터는 하나(만든 뒤 구분할 수 없고 사람 칸의 뜻이 남는다), 담당자와 참석자를 다른 칸으로(고르는 칸이 둘), 업무에 RRULE을 넣고 회차를 펼쳐 그리기(예외 회차·시간대·편집 범위를 본체가 모두 만든다), HR `calendar_event`와 본체 일정을 둘 다(만드는 곳이 둘), 일정은 본체 밖(D-071 원안).

## D-093. 문서는 프로젝트마다 폴더에 두는 마크다운 글이고, 워크스페이스 문서함이 프로젝트 폴더와 공통 폴더를 함께 보인다 (2026-10-26)
- **BIT 결정기록**: BIT-34. 논의는 BIT-31.
- **무엇을 (D-015·D-016·D-018·D-019와 D-064의 하위 메뉴 기각 대체)**: 문서는 제목과 Tiptap 마크다운 본문(D-076)이고 폴더 안에 놓인다. 폴더(이름만 있는 그릇)와 문서는 나뉜 엔티티이고, 문서 아래 하위 문서는 없다. 사람은 화면에서, 에이전트는 MCP로 같은 문서를 쓰고 읽는다.
  - **메뉴**: 사이드바에서 프로젝트를 펼치면 하위 메뉴는 '업무'·'문서' 두 개로 고정이다. 워크스페이스 메뉴의 '문서함'은 맨 위에 프로젝트 폴더를 프로젝트 순서(D-080)대로 보이고, 그 아래 워크스페이스 공통 폴더와 문서를 보인다. 프로젝트 폴더는 지울 수 없고 Git 서브모듈처럼 특별한 모양이다. 프로젝트의 '문서'는 문서함의 그 프로젝트 폴더를 바로 연 화면이다.
  - **문서가 갖는 것**: 워크스페이스 라벨(업무와 같은 목록), 업무와의 연결, 댓글·활동(D-078의 타임라인), 첨부(D-090의 파일 모듈, 첨부 주인에 문서를 더함)를 갖는다. 폴더에 파일을 끌어 놓으면 그 파일을 감싼 문서를 만든다. 커밋은 직접 붙이지 않고 연결된 업무의 커밋을 모아 보인다.
  - **가리키기**: 10자 ID(D-083)와 제목으로 가리킨다. 주소는 `/documents/<제목>-<id>`이고, 본문에서는 `@`로 골라 넣는 링크다. 에이전트는 제목·폴더로 찾고 ID로 읽는다.
  - **담는 글**: 요구사항·설계·기획·회의록·메모 같은 SDLC 문서와 결정기록(D-094)이다. 노트·회의록 라벨 업무(D-066·D-071)는 문서로 옮기고, 업무의 '카드' 보기도 문서로 옮긴다. 문서 뷰 구성(폴더·리스트·카드 후보)은 화면 설계 때 정한다.
  - **원칙 3**: 문서 편집과 일정(D-092)은 범위 안이다. 실시간 공동 편집, 결재, 공개 위키는 밖이다. 동시에 고치면 버전 검사(D-049 방식)로 충돌만 알린다.
- **왜**: 사용자가 정했다. 쓰는 글과 올린 파일은 생기는 방식, 정본, 에이전트가 읽는 법이 다르다(마크다운 원문은 바로 읽는다). 업로드 파일 중심의 문서함은 BIT 안에서 쓰는 흐름에 맞지 않았다. 사용자는 폴더를 만들고 위치를 옮기며 정리하길 원했다. 업무와 문서가 대등해져 프로젝트 하위 메뉴가 필요해졌다(D-064 때는 이슈뿐이었다). '페이지'는 화면 코드의 FSD `pages` 층과 이름이 겹쳐 '문서'로 정했다.
- **감수하는 것**: 원칙 3을 일부 고친다. 펼친 프로젝트마다 사이드바가 두 줄 길어진다. 문서에는 외워 칠 수 있는 짧은 키가 없다. 파일 하나를 보관해도 문서가 하나 생긴다. Git md 참조(D-016), 첨부 텍스트 변환(D-031), PDF(D-032), 관리 문서(버전·확정, D-013·D-018)가 1차에서 빠진다.
- **기각**: 워크스페이스 문서함 + 프로젝트 라벨(D-015 원안), md도 문서함의 파일로(D-016), 노트 라벨 업무로 대신(상태가 있는 목록에 참고 문서가 섞이고 계층이 없다), 페이지 안 페이지(Notion·Plane)나 폴더와 중첩 둘 다, 프로젝트 화면의 탭(D-066에서 없앤 탭과 뷰 칩이 두 겹), 사이드바에 폴더 트리(메뉴와 내용이 섞인다), 사용자가 메뉴를 만드는 메뉴 › 뷰 두 단계(리니어도 메뉴는 고정하고 숨기기·즐겨찾기만 준다), 폴더에 파일도 항목으로(항목 종류가 둘), 업무와 같은 번호열 키(업무 번호에 구멍), 문서 전용 번호(키 모양이 하나 더).
- **화면 (BIT-41, 2026-10-27)**: 사용자가 시안을 보고 정했다. 폴더 안은 **목록 하나**다: 폴더 다음 문서이고 열은 라벨·연결된 업무·고친 때다. 시안의 카드 보기(본문 첫 줄)는 처음에 목록과 함께 두기로 했다가 사용자가 빼기로 했다(같은 날). 그래서 위 '담는 글'의 "업무의 카드 보기도 문서로 옮긴다"는 문서 쪽에는 카드 보기를 두지 않는 것으로 바뀐다. 문서함 맨 위의 프로젝트 폴더는 프로젝트 색의 폴더에 프로젝트 표시와 연결 표시를 붙여 일반 폴더와 다르게 그린다. 사이드바에서 프로젝트를 펼치면 '업무'·'문서'이고, 보고 있는 프로젝트는 펼쳐지며 펼침·접힘은 그 브라우저에 기억한다. 문서 주소는 `/documents/<제목>-<id>`, 새 문서와 편집은 자기 주소의 페이지다. 기각: 목록 기본 + 카드 전환(시안 2·3, 사용자가 카드를 뺐다).
- **아직 없는 것**: 폴더에 외부 항목 연결(SharePoint 같은 연동, Git md 참조)은 미정이다. 첨부 텍스트 변환, 관리 문서도 아직 정하지 않았다.

## D-094. 결정기록은 결정 틀을 넣은 문서다 (2026-10-26)
- **BIT 결정기록**: BIT-35. 논의는 BIT-31.
- **무엇을 (D-012, D-055의 결정 대체, D-066의 결정기록 시스템 라벨, D-085의 자리 대체)**: 결정기록은 본문에 맥락 / 결정 / 검토한 대안 틀(문서 템플릿)을 넣은 일반 문서(D-093)다. 결정 상태(제안·확정·대체), 대체 관계, 파생 업무로 계산하는 이행률은 두지 않는다. '결정기록'은 지울 수 없는 시스템 라벨이 아니라 문서에 다는 평범한 라벨이다. 쓰는 때 기준(앞으로 따라야 할 선택만, 고치지 않고 새 기록으로 대체, D-085)은 스킬의 작성 지침으로 남긴다.
- **옮기기**: 서버의 결정 전용 동작을 걷어 내고, 운영 BIT의 결정기록 업무를 문서로 옮기고, 스킬 4절과 MCP 안내문을 고친다. 문서 기능이 생길 때까지는 지금처럼 이 파일과 BIT 결정기록 업무에 함께 남긴다.
- **왜**: 사용자가 정했다. 결정기록은 말 그대로 기록이다. 결정 기록(ADR)을 문서로 두는 팀이 많고, 이 파일도 문서다.
- **감수하는 것**: "이 결정이 아직 유효한가"를 화면과 에이전트가 상태로 알 수 없고 본문의 '대체됨' 표시로만 안다. 이행률 계산이 사라지고, 이미 만든 결정 동작 코드를 버린다.
- **기각**: 작업에 시스템 라벨 그대로(권장안이었다. 바꿀 것이 없지만 기록을 업무 흐름에 둔다), 세 번째 업무 종류(라벨 기반 동작·MCP·운영 데이터를 종류 기반으로 옮겨야 한다), 문서에 종류 칸(일반·결정기록)을 두고 상태 유지, 시스템 폴더 '결정'(의미가 위치에 숨는다).
