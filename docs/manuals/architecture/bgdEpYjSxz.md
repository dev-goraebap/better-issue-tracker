# 기존 프레임·목록·테마 유지

새 목록 화면이나 기존 목록의 행·도구·액션을 바꿀 때 적용합니다.

## 규칙과 이유

PageFrame·ListToolbar·ItemList/ItemRow와 기존 토큰을 먼저 재사용합니다. 제목 아래 설명, 끝의 더보기, 동일 행 높이, 하단 개수·빈 공간 마감을 함께 유지합니다. 검색·필터·정렬·만들기는 기존 헤더 동작을 따르고 임의의 별도 상단 안내/배너를 추가하지 않습니다.

## BIT 실제 코드

현재 코드 발췌: `client/src/pages/workspace/projects/ui/ProjectsPage.tsx` · 79행부터. 주변 선언·호출부는 원본에서 확인합니다.

```tsx
    <ListToolbar search={{ label: '프로젝트 검색', placeholder: '이름이나 키로 찾기', value: search.q, onChange: q => go({ q }, true) }}
      action={canWrite ? { label: '프로젝트 만들기', icon: 'plus', onClick: () => setCreating(true), isCreate: true } : undefined} />
```

프로젝트 목록은 공용 도구 줄에 검색과 만들기를 선언합니다. 행은 같은 파일의 ItemRow에서 title/description/meta/end를 나눕니다. 제목·설명과 행 액션을 새 표 컬럼으로 임의 변경하지 않습니다.

## 피해야 할 예

아래는 실패 이유를 보여 주는 설명용 반례이며 현재 BIT 구현의 발췌가 아닙니다. 생략된 선언이 있어 그대로 실행하는 완성 코드가 아닙니다.

```tsx
// 화면마다 도구와 행을 새 HTML 구조로 만드는 반례
<table><thead><tr><th>이름</th><th>설명</th></tr></thead></table>
<button style={{ color: "#fff", background: "#111" }}>검색</button>
```

## 예외와 적용 한계

정형 데이터 비교에 표가 필요한 기능까지 금지하는 것은 아닙니다. 해당 화면의 기존 목적과 부품을 확인합니다. 확정 로고·설치 아이콘은 다른 규칙이므로 내부 로고의 테마 색을 PWA 아이콘에 적용하지 않습니다.

## 검증 기준

자동: lint:components·타입/빌드·관련 목록 테스트를 확인합니다.

화면: 설명 유무·긴 제목/ID·더보기 열기·하단 개수/배경·권한별 액션·접힌 사이드바·모바일·스톤 라이트/다크와 색 테마를 확인합니다. JSX 부품 이름 검사로 크기·대비·잘림이 검증되지는 않습니다.

## 1. 반응형 분기 원칙 (CSS vs React)

화면 크기 변화에 대응할 때 스타일 변경과 상호작용 분기를 명확히 구분한다.

| 구분 | 적용 기준 | 구현 방식 |
| :--- | :--- | :--- |
| **CSS 스타일 분기** | 단순 배치, 여백, 너비/높이, Flex 방향 등 시각적 치수만 변경되는 경우 | 미디어 쿼리 및 유틸리티 클래스 적용 |
| **React 컴포넌트 분기** | 내비게이션 구조, 다이얼로그 ↔ 바텀시트 전환 등 사용자 상호작용 흐름이 변경되는 경우 | `useMediaQuery` 훅을 통한 조건부 렌더링 |

- **중단점(Breakpoint) 통일**: 프로젝트 전역에서 공통 상수 `MOBILE_QUERY = '(width < 64rem)'`와 Astryx의 `useMediaQuery` 훅만을 사용한다. 페이지별로 임의의 픽셀 중단점을 추가하는 것을 금지하며, 기준값은 `shared/config/layout`에 고정하여 관리한다.

## 2. 레이아웃 셸(App Shell) 및 내비게이션 구조

화면 골격은 역할별로 레이어를 엄격히 분리하여 조립한다. 셸은 client/src/widgets/workspace-shell의 기존 구현과 공용 PageFrame을 사용한다.

### 레이어별 책임
- **`app`**: 라우트 구조 조립 및 레이아웃 메타데이터 매핑
- **`widgets/app-shell`**: 공통 레이아웃 프레임워크(사이드바, 헤더, 모바일 바) 제공
- **`pages`**: 본문 비즈니스 콘텐츠 및 페이지 단위 인터랙션 소유

### 메뉴 구성

| 영역 | 메뉴 |
| :--- | :--- |
| 사이드바 위 | 워크스페이스 범위는 WorkspaceSwitcher, 프로젝트 범위는 프로젝트 마크·이름의 ProjectSwitcher(D-117) |
| 워크스페이스 메뉴 | 이슈·스케줄·매뉴얼·리소스·멤버·프로젝트(D-116) |
| 프로젝트 메뉴 | 이슈·스케줄·매뉴얼·리소스·멤버. 범위 전환 시 메뉴와 콘텐츠를 함께 바꾼다 |
| 프로젝트 관리 | 일반·워크플로·저장소 연동. 워크스페이스 관리 화면은 기존 설정 탭을 유지한다 |

메뉴 이름·순서는 공간별 서버 설정이며 URL·기능 키·권한은 고정한다. 워크스페이스의 프로젝트 메뉴 아래에는 개인 즐겨찾기 프로젝트 이름만 둔다. 프로젝트 전환 메뉴 안의 워크스페이스 이름을 누르면 전체 이슈로 돌아간다. 프로젝트명 중복 제목이나 별도의 돌아가기 행을 더하지 않는다. 실제 경로·기본 메뉴는 `client/src/shared/config/navigation.ts`와 `entities/navigation`을 확인한다. 매뉴얼은 BIT-144의 서버 저장 기능으로 운영 메뉴·라우트에 포함한다. 기존 브라우저 미리보기 자료를 자동 게시하지 않으며 원본 가져오기를 사용한다.

### 환경별 내비게이션 구성
- **데스크톱 환경**: 좌측 접이식 사이드바를 통해 전체 메뉴를 계층적으로 탐색한다.
- **모바일 환경**: 하단 바는 지금 범위(워크스페이스 또는 프로젝트)의 핵심 메뉴이고, 그 범위의 나머지 메뉴는 '더보기' 시트에 둔다. 내 정보·설정·로그아웃은 '더보기' 시트의 계정 줄과 바닥에서 연다. 만들기 동작은 `FloatingAction`이다(3절).
- **범위별 하단 메뉴(D-116)**: 현재 범위에서 활성화된 메뉴의 앞 세 개와 더보기를 사용한다. 나머지 메뉴와 관리는 더보기에 두며 프로젝트 전환기도 프로젝트 범위의 더보기에서 제공한다. 설정에 따른 이름·순서와 개발/운영 기능 제외를 먼저 적용한다. 실제 조립은 `client/src/app/layout/AppLayout.tsx`를 확인한다.
- **확인할 것 표시**: 확인할 것이 있는 메뉴(읽지 않은 항목이 있는 Inbox 등)는 숫자 없이 강조색 점 하나로 알린다. 데스크톱은 메뉴 이름 끝, 모바일은 하단 탭 아이콘 모서리이고, 더보기 안의 메뉴에 점이 있으면 더보기 아이콘과 시트의 그 블록에도 둔다.
- **켜진 기능**: 꺼진 기능에만 딸린 메뉴는 그리지 않는다([데이터 흐름](BEzXrFTF1X.md) 4절).
- **관리자 고밀도 화면**: 데이터 밀도가 높은 관리 화면은 별도의 전용 레이아웃 셸로 구성할 수 있으나, 사용자 권한 검증은 일반 셸과 동일한 보안 정책을 적용한다.

## 3. 페이지 헤더, 툴바 및 푸터 표준

화면 상단과 하단의 UI 요소는 일관된 시각적 위계를 갖도록 표준 패턴을 강제한다.

### 목록 화면의 층
목록 화면은 위에서부터 같은 층을 둔다. 쓰지 않는 층은 비우고 순서는 바꾸지 않는다.

```
① 제목 ───────────────────────── [주 동작]
② 탭 (없으면 생략)
   ─────────────────────────────────────  ← 탭 유무와 관계없이 긋는 선
③ [검색      ]      [상태 ▾] [담당자 ▾] [필터 +2] [초기화] [정렬 ▾]   ← 데스크톱, 늘 한 줄
   [검색                  ] [필터·정렬]               ← 모바일(만들기는 오른쪽 아래 떠 있는 +)
   걸린 조건 칩 ×   모두 지우기          ← 모바일, 조건이 있을 때만
   목록 …
   [더 보기]
```

| 층 | 규칙 |
| :--- | :--- |
| 제목 줄 | 모바일에서는 상단 경로가 페이지 이름을 보이므로 목록 페이지의 큰 제목과 아이콘을 화면에서 숨기고 스크린 리더에만 남긴다(뒤로가기가 있는 상세 페이지는 제목이 내용이라 둔다). 탭이 없으면 제목 아래 선과 간격도 없애 도구 줄이 상단 바 바로 아래에서 시작한다. 제목 앞에 메뉴 아이콘을 작게(`PageFrame`의 `icon`) 두고, `actions`에 페이지 전체의 동작 하나(새로 만들기·등록)를 둔다. 제목이 길면 한 줄에서 말줄임으로 자르고 동작 버튼은 줄바꿈하거나 줄이지 않는다. 보조 동작은 더보기 메뉴로 모은다 |
| 탭과 선 | 탭은 공통 `PageTabs`로 그려 `PageFrame`의 `tabs`에 넘기고, 페이지 폭 전체에 그은 선 위에 올린다. 탭은 아이콘 없이 글자만 보인다. 페이지 안의 탭은 `hasRule`로 같은 전체 폭 선을 긋는다. 탭이 없는 목록은 `PageFrame`의 `hasRule`로 같은 선만 긋는다 |
| 도구 줄 | 공통 `ListToolbar`를 쓰고 데스크톱·모바일 모두 한 줄이며 줄바꿈하지 않는다. 데스크톱은 검색을 왼쪽에 두고 필터를 오른쪽 끝에 붙여 하나씩 작은 선택 상자로 풀어 두고(아이콘과 이름, 고르면 "상태: 확정"처럼 값이 붙고 강조 바탕색, 고르는 즉시 적용), 사람·라벨처럼 긴 목록은 선택 상자 안에서 검색한다. 한 줄에 다 들어가지 않으면 폭을 재서 뒤쪽 필터부터 "필터 +N"으로 접고(접힌 것 중 걸린 수를 함께 보임), 그 버튼은 접힌 필터만 담은 대화상자(머리·본문·바닥을 선으로 나눔)를 연다. 걸린 필터가 있으면 '초기화'를 둔다. 모바일은 모든 필터를 바닥이 아래에 붙는 바텀시트에서 고른 뒤 '적용'으로 함께 걸고(필터마다 아이콘과 이름을 머리로, 입력은 큰 크기로), 걸린 필터는 아래 줄에 지울 수 있는 칩으로 보인다. 도구 줄이 상단에 붙어 목록이 그 밑으로 지나가면 아래 선이 서서히 나타난다. 모바일에서는 한 줄에 [검색] [필터·정렬]을 둔다. 정렬은 시트 맨 위에서 필터와 함께 고르고, 걸린 조건 수를 버튼에 숫자로 보인다. 페이지의 만들기 동작(새로 만들기·등록·추가)은 `ListToolbar`의 `action`에 `isCreate`를 달아 제목 줄 대신 떠 있는 + 버튼(`FloatingAction`)이 되고, 만들기가 아닌 주 동작(모두 읽음 등)은 줄 끝의 강조색 아이콘 버튼이다 |
| 목록 | 바깥 테두리·둥근 모서리·별도 바탕 없이 페이지 위에 둔다. 행 사이는 옅은 선으로 나누고, 날짜처럼 비교하는 값은 오른쪽 끝에 세로로 맞춘다. 사람이 쓴 항목은 이름 앞에 아바타를 둔다. 읽지 않은 항목은 행 바탕을 강조 바탕색(`--color-accent-muted`)으로 칠해 구분선과 색으로 갈리게 한다. 날짜 앞에는 시계 아이콘을 둔다. 데스크톱에서는 제목 글자만 눌러 열고(마우스를 올리면 밑줄), 모바일에서는 행 전체를 누를 수 있다 |
| 표 보기 | 여러 속성을 나란히 비교하는 목록은 데스크톱에서 여백 넓은 표(Astryx `Table`의 `density="spacious"`)로, 모바일에서는 위 목록 행으로 보인다. 표에서는 정렬을 열 머리에 두고 도구 줄의 정렬은 모바일에만 둔다. 열 머리 정렬은 서버가 인덱스로 받치는 열에만 건다 |
| 끝 | 커서 목록은 공통 `ListMore`('더 보기')로 다음 조각을 읽고, 다음이 없으면 아무것도 두지 않는다 |

검색어·필터·정렬은 URL에 두고 기본값은 생략한다. 검색어는 입력이 300ms 멈추면 히스토리를 덮어쓰며 반영하고, 필터·정렬 변경은 히스토리에 남긴다. 조건에 맞는 결과가 없으면 `search` 상태와 '조건 지우기'를 보인다.

### Plane식 머리 영역 목록 (`chrome="header"`)

`PageFrame`에 `chrome="header"`를 준 목록은 위 층 대신 아래를 따른다. 목록 화면을 이 방식으로 옮길 때는 페이지가 `chrome="header"`만 주고 나머지는 공용 부품에 맡긴다. 페이지마다 머리·도구·칩 줄을 따로 짜지 않는다.

| 화면 | 규칙 |
| :--- | :--- |
| 데스크톱 | 셸의 머리 줄(경로 + 끝의 도구·만들기), 그 아래 탭 줄, 필터 줄(FilterBar 칩), 본문은 카드 끝에서 끝까지. 여러 속성을 비교하는 목록은 `SheetTable`(Plane 표), 제목을 읽는 목록은 `ItemList`·`ItemRow`·`ItemMeta`(Plane 목록). 새로 만들지 않는 동작(모두 읽음)은 `action`에 `isCreate` 없이 주면 보조 버튼이 된다. 검색·필터가 없는 설정 화면도 `ListToolbar`에 `action`만 주어 머리 줄 버튼을 두고, 행이 적어 표가 카드 끝에 닿지 않으면 `SheetTable`이 표 아래 남은 높이에 옅은 점 격자(16px 간격, `--color-icon-secondary` 35%)를 깔고 아래로 흐리게 지운다(누를 수 없고 화면 읽기에서 숨김, 표가 페이지의 마지막 내용일 때만). 손으로 순서를 정하는 표는 `SheetTable`의 `rowProps`와 첫 칸의 공통 손잡이를 연결하며, 표 위 안내는 옅은 한 줄로 둔다 |
| 휴대폰 목록 | 맨 위 막대(MobileBar), 머리 줄(경로 끝 두 단계 + 필터·정렬·검색 아이콘, `MobileTools`), 탭 줄(화면 너비를 나눠 씀), 칩 줄(가로로 넘김), 본문(화면 끝에서 끝까지, 행이 20px 안쪽 여백을 가짐), 하단 탭, 만들기는 떠 있는 +, 다른 동작은 머리 줄 끝의 강조 아이콘 |
| 휴대폰 상세·양식 | 막대·머리 줄·하단 탭 없이 전체 화면. 페이지가 자기 뒤로가기(PageFrame `back`)를 둔다 |
| 휴대폰 검색 | 돋보기는 같은 목록 주소에 `finding=1`을 붙인 검색 화면을 연다(`useSearchScreen`, 목록 주소 해석에 `findingOf`). 셸이 막대·탭·칩·+를 숨기고 머리 줄이 검색 줄(돋보기가 든 전체 폭 검색 칸)이 되며, 바닥에 붙은 줄의 '목록으로'가 검색 화면을 닫는다. 페이지는 검색 화면에서 그 탭을 검색어로만 읽고(필터·정렬 빼고), 검색어가 없으면 아무것도 읽지 않고 `search` 상태로 무엇을 찾을지 안내하며, 결과가 없으면 그 검색어로 없다고 보인다 |

### 헤더 및 설명 문구 정책
- **제목과 툴바의 물리적 분리**: 페이지 제목 영역과 필터/액션 툴바 영역을 하나의 박스에 혼합하지 않고 분리한다.
- **배지 및 부제 지양**:
  - 페이지 제목 옆에 건수 배지를 부착하지 않는다. (전체 건수는 목록 하단이나 테이블 요약에 표시한다.)
  - 페이지 제목 바로 아래에 형식적인 페이지 설명 문구를 배치하지 않는다. 사용자에게 필요한 안내는 해당 기능을 사용하는 입력 폼 옆이나 컨텍스트 영역에 짧고 명확하게 배치한다.
- **토큰 일관성**: 헤더 높이, 타이틀 폰트 크기, 본문 최대 너비는 디자인 시스템의 전역 공통 토큰으로 일치시킨다.
- **페이지 폭**: 페이지는 가운데 정렬하고, `PageFrame`의 `width`로 내용에 맞춘다. 한 건을 읽거나 양식을 채우는 페이지(결정 상세, 산출물 상세)는 `narrow`(48rem), 목록과 섹션 화면은 기본(64rem), 보드와 넓은 표는 `wide`(80rem)다. `chrome="header"` 화면은 `width`를 주지 않으면 본문이 카드 끝에서 끝까지이고, 주면 머리 줄·탭 줄·칩 줄은 다른 화면과 같은 자리·높이로 두고 본문만 그 폭의 가운데 열(양옆 32px·위 24px, 휴대폰 20px)에 둔다. 페이지마다 본문 폭 CSS를 따로 두지 않는다.
- **상세·작성 페이지**: 목록 항목의 상세와 등록·수정은 대화상자가 아니라 자기 URL의 페이지로 둔다. 목록의 검색 조건을 URL에 실어 뒤로가기(`BackLink`)와 상단 경로가 같은 목록으로 돌아가게 한다. 저장·취소 같은 바닥 줄은 모두 공통 `PageFoot`(시작 칸: 뒤로가기·취소, 끝 칸: 동작)으로 그린다. 셸이 카드 맨 아래에 자리를 내주어, 내용이 짧아도 화면 아래에 붙고 길면 그 위로 내용이 스크롤된다. 페이지마다 바닥 줄을 직접 짜거나 `position: sticky`로 붙이지 않는다. `PageFoot`은 셸의 자리로 옮겨 그려져 `<form>` 밖에 놓이므로, 제출 버튼은 폼에 `useId`로 준 id를 `form` 속성으로 가리킨다(`<Button type="submit" form={formId} />`). 건수 안내가 필요하면 시작 칸에 둔다. 채워 넣는 페이지의 라우트는 `staticData: form`(`isFormPage`)을 달아 모바일에서 하단 탭을 숨기고 동작 줄이 키보드 위에 남게 한다.

### 공통 컴포넌트 표준
- **상세 페이지 위치와 뒤로가기**: 메뉴 항목 아래의 상세 페이지는 `usePageCrumb`로 자기 이름을 상단 경로의 마지막 단계로 더하고, 상위 메뉴 단계는 링크로 바뀐다. 뒤로가기는 페이지가 `PageFrame`의 `back`에 공통 `BackLink`로 넘기되, 제목 위에 보이지 않는다(데스크톱은 상단 경로가 길을 보인다). 휴대폰은 상세·양식이 전체 화면이므로 페이지가 자기 바닥 줄을 두지 않으면 `PageFrame`이 `PageFoot` 시작 칸에 '이전으로'를 둔다(페이지의 바닥 줄이 있으면 물러난다). 이 탭에서 앞에 본 앱 화면이 있으면 어디서 왔든 히스토리로 되돌아가고(목록은 불러온 조각과 스크롤을 지키고, Inbox에서 왔으면 그리로), 링크를 새로 열었거나 새로고침해 앞 화면을 모르면 그 페이지의 목록으로 이동한다. 찾는 페이지가 없을 때의 '이전으로 돌아가기' 버튼도 같다. 목록의 검색 조건은 상세 URL에 실어 앞 화면을 모를 때도 같은 목록 상태로 간다. 상단 경로의 목록 링크와 작성 취소·수정 저장·삭제 뒤의 이동은 바로 앞 화면이 그 목적지(경로와 검색 조건)일 때 히스토리로 되돌아가고(`useReturnTo`), 아니면 링크로 이동한다. 새로 만든 항목의 저장은 작성 화면을 상세로 바꿔(`replace`) 뒤로 가면 목록이 나온다.
- **목록 도구 줄 (`ListToolbar`)**: 스크롤하면 제목은 위로 사라지고 도구 줄은 상단 헤더 바로 아래에 붙는다. 색이 든 박스로 감싸지 않는다.
- **날짜 범위 필터**: 날짜 구간으로 거르는 조건은 `ListFilter`의 `kind: 'range'`로 둔다. 데스크톱 도구 줄과 모바일 시트에서 두 달 달력의 날짜 범위 입력이 되고, 값은 `from~to` 한 값이며 페이지가 URL의 `from`·`to`로 나눈다(`rangeOf`, `rangeValue`).
- **전체 건수**: 관리자 목록처럼 전체 수가 판단에 필요한 목록은 `ListMore`의 `count`로 끝에 'N개 중 M개'(다 읽으면 '모두 N개')를 보인다.
- **떠 있는 만들기 버튼 (`FloatingAction`)**: 모바일에서 만들기 동작이 있는 화면은 그 동작을 오른쪽 아래에 떠 있는 강조색 + 버튼 하나로 연다. 버튼은 하단 탭과 홈 표시줄 위에 있고, 하단 탭이 없는 화면에서는 홈 표시줄 바로 위다(셸이 `--workspace-tab-bar-height`를 준다). 버튼이 있는 동안 셸이 본문 끝에 버튼 높이만큼 여백을 두어 마지막 줄을 가리지 않는다. 이 버튼이 대신하는 제목 줄·구역 머리의 만들기 버튼은 모바일에서 숨기고, 빈 상태의 만들기 버튼은 둔다. 양식 화면에는 두지 않는다. 데스크톱은 그리지 않는다.

## 4. 오버레이 및 모달 인터랙션 패턴

사용자 작업의 집중도와 입력 복잡성에 따라 오버레이 형태를 적응형으로 전환한다.

### 창의 두 종류: 짧은 창과 페이지 창
모든 창은 같은 해부도로 그린다. 구분선 있는 머리(제목·부제·닫기, 앞 페이지가 있으면 뒤로), 스크롤되는 몸통, 구분선 있는 바닥(오른쪽 끝에 취소 다음 주 동작, 바닥 배경은 표면색)이다. shared/ui/frame의 `FrameHead`·`FrameBody`·`FrameFoot`이 이 세 부분이며, 창마다 머리·바닥을 직접 짜지 않는다(Astryx `Dialog`·`AlertDialog`·`DialogHeader`를 화면에서 바로 쓰지 않는다). 휴대폰에서 어떻게 뜨는지는 일의 크기로 두 가지만 둔다.

| 종류 | 데스크톱 | 휴대폰 | 주소 | 컴포넌트 | 맞는 일 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| 짧은 창 | 가운데 작은 창 | 바텀시트 | 없음 | `CompactDialog`, 그 위의 `FormDialog`(짧은 입력)·`ConfirmDialog`(확인, `word`로 직접 입력 확인)·`ConfirmDelete` | 이름 하나 입력, 라벨 지정, 삭제 확인, 나가기 확인 |
| 페이지 창 | 보던 화면 위 가운데 패널(마스크 라우팅) | 전체 화면 페이지 | 있음 | `Surface`를 그리는 위젯 + 독립 라우트 + 여는 화면의 `useScreenPanel`·`RoutedPanel` | 사유를 적는 일, 긴 글, 단계가 있는 등록 |

- **휴대폰 전체 화면이면 반드시 페이지 창이다.** 주소가 있어야 뒤로가기·새로고침·링크가 된다.
- **페이지 창을 여는 화면**: 화면이 `useScreenPanel(경로, search, 패널 뺀 search)`로 호스트를 만들고 `PanelHostContext`로 감싼 뒤, search에 `panel`이 있으면 `RoutedPanel`(묻는 것이 적으면 `size="compact"`) 안에 그 주소의 위젯을 그린다. 화면의 search 파서는 `parsePanelPlace`를 더하고, 목록 조건·뒤로 링크·로더에는 `withoutPanel`을 쓴다. 여는 쪽은 `useGo()`(화면 자신은 `useGo(host)`)로 주소를 열고, 그 주소는 `shared/lib/routed-panel`의 `PANEL_PAGES`에 정규식으로 올린다. 같은 위젯이 독립 라우트(`staticData: form`)에서도 그려진다.
- **페이지 창에서 끝낸 일의 결과**: 패널은 주소로 열리므로 연 행에 콜백을 넘길 수 없다. 결과를 행이 받아야 하면 기능 슬라이스의 작은 알림(`use…Heard`)으로 듣는다. 토스트는 페이지 창이 띄운다.

### 폼 입력 및 상세 화면
- **데이터 생성 및 편집**: 데스크톱 환경에서는 중앙 집중식 모달 다이얼로그(Dialog)를 띄우고, 모바일 환경에서는 뷰포트를 가득 채우는 전체 화면 표면(Full-screen Surface)으로 전환한다. 가운데 모달은 창 폭과 관계없이 같은 모양으로 보인다.
- **단계 양식**: 입력 묶음이 여럿인 작성·편집 양식은 화면 크기와 관계없이 같은 단계로 나누고, 휴대폰용 단계와 데스크톱용 한 장 양식을 따로 두지 않는다. shared/ui의 `StepFlow`·`StepActions`·`StepReview`·`useStepFlow`로 그린다. 페이지나 모달의 내용 폭 전체에 그 페이지·모달의 제목과 같은 왼쪽 줄로 단계 표시, 단계 제목(큰 제목 입력처럼 입력이 스스로 무엇인지 말하는 단계는 화면 읽기 프로그램에만), 그 단계의 입력을 두고, 마지막 단계는 저장할 내용을 줄마다 보이는 확인이다. '다음'은 그 단계의 입력만 검사하고, 저장은 모든 단계를 검사해 처음 걸리는 단계를 열며 걸린 단계를 단계 표시에 오류로 표시한다. 새로 만들 때는 단계 표시로 지나온 단계까지만 가고 저장은 마지막 단계에 있다. 고칠 때는 내용이 다 있으므로 어느 단계로든 가고(가는 길에 문제가 있는 단계에서 멈춤) 어느 단계에서나 저장한다. 단계를 옮기면 초점이 단계 제목으로 간다. 입력 초안은 양식에만 있으므로 단계는 주소에 두지 않는다. 바닥 줄은 왼쪽에 취소, 오른쪽에 이전·다음·저장이다. 제목·본문·파일로 된 문서 양식은 한 장으로 둔다.
- **보던 화면 위의 상세**: 보드·타임라인처럼 화면을 떠나지 않고 보는 항목 상세와 그 자리 편집은 shared/ui의 `PanelDialog`·`SidePanel`로 데스크톱 창 가운데의 모달로 연다. 상세·편집은 `content`로 좁은 페이지와 같은 832px(48rem 내용 + 양옆 `--spacing-8`)여서 같은 상세가 페이지와 모달에서 같은 폭으로 보이고, 작은 상세(사람 프로필 등)는 `compact` 560px다. 창이 좁으면 양옆 24px를 남긴 폭이 된다. 높이는 내용만큼이되 `content`는 560px, `compact`는 440px보다 낮아지지 않고 창 높이의 90%를 넘지 않는다(창이 낮으면 최소도 90%로 줄어든다). 내용이 짧으면 본문 위쪽에 붙고 바닥 줄은 모달 아래에 남으며, 머리와 바닥 줄은 두고 본문만 스크롤한다. 내용이 바뀌어 높이가 달라지면(불러오기 끝, 상세와 편집 전환, 펼침, 90% 상한) 높이가 `--duration-fast-max`(230ms)에 `--ease-standard`로 바뀌고, 그동안 본문은 스크롤 막대 대신 잘라 보인다. height: auto는 브라우저마다 전환되지 않으므로 `useModalHeight`가 내용을 ResizeObserver로 재어 픽셀 높이를 준다. 열 때는 아래에서 살짝 떠오르며 나타나고 닫을 때는 잠깐 남은 복사본이 흐려지며 가라앉는다(175ms). 동작 줄이기를 켜면 높이 전환과 여닫기 움직임을 모두 끈다. 너비를 바꾸는 손잡이는 없다. 모바일은 전체 화면이다. 모달에서 연 대화상자는 모달 위에 뜨고 모달은 닫지 않는다. 확인·삭제 같은 작은 대화상자는 짧은 창(`ConfirmDialog`)이다.
- **상세 모달과 붙은 패널**: 상세 모달은 브라우저 모달(`showModal`)로, 붙은 패널이 있든 없든 창 전체의 가운데에 뜬다. 배경은 붙은 패널까지 어둡게 덮고 그 밖은 모두 비활성이 되어 초점이 모달 안에 머문다. 배경을 누르거나 Escape·뒤로가기로 모달을 닫고, 닫히면 초점이 연 자리로 돌아간다.
- **어디서나 여는 작업**: 어느 화면에서든 시작해 끝나면 돌아오는 작업은 페이지 창이다. 보던 화면이 패널 호스트면 그 위 패널로, 아니면 그 주소의 페이지로 열린다.
- **단순 선택 및 필터**: 모바일 환경에서의 단일 선택이나 필터 옵션은 바텀시트(Bottom Sheet)를 기본으로 채택한다. 필터·선택 시트는 내용 높이만큼만 올라오게(`height="hug"`) 해 짧은 필터가 화면 대부분을 가리지 않게 한다. 정렬이 셋을 넘으면 라디오를 세로로 쌓는다.
- **바텀시트의 머리·본문·바닥**: 바텀시트 안은 직접 짜지 않고 `CompactDialog`나 shared/ui frame의 `FrameHead`·`FrameBody`·`FrameFoot`으로 그린다. Astryx 바텀시트는 위 24px에 손잡이 띠를 덮어 그리므로 머리를 직접 만들면 제목이 손잡이에 걸리고, `capped`·`tall` 높이에 직접 만든 바닥은 내용 끝에 떠서 화면 아래에 붙지 않는다. frame은 시트 안에서 머리를 손잡이 띠 아래로 내리고, 머리·바닥을 붙여 두고 본문만 스크롤한다. 두 단계 시트(항목 → 값)는 같은 시트에서 `FrameHead`의 `onBack`으로 돌아간다. 바텀시트에는 닫기 버튼을 두지 않는다(손잡이·바깥 누르기·뒤로가기로 닫힘, 더보기 시트와 같음). frame 머리가 시트 안에서 닫기를 감추므로 `onClose`를 넘겨도 된다. 확인할 때는 휴대폰 크기에서 제목 위치가 손잡이 띠 아래인지, 바닥 줄이 화면 아래 끝에 붙는지 잰다.
- **여러 개 고르는 필터**: 선택지가 많은 필터(담당자·라벨·프로젝트)는 `ListFilter.isMultiple`로 여럿을 고른다. 값은 쉼표로 이은 한 문자열(`a,b`)로 URL과 API에 그대로 싣고, 데스크톱은 도구 줄의 MultiSelector(버튼은 `라벨: 설계 외 2`), 필터 창·시트는 고른 것을 배지로 보이는 MultiSelector다. 상태·기간·읽음처럼 선택지가 두세 개인 필터는 하나만 고른다. 멀티셀렉트는 서버가 여러 값을 받을 때만 둔다.
- **알림 토스트**: 토스트는 화면 위·아래 끝에서 쓰는 조작을 가리지 않는 곳에 뜬다. 데스크톱은 페이지 제목 줄과 도구 줄이 있는 위를 피해 오른쪽 아래, 모바일은 하단 탭을 피해 위쪽 가장자리이며 세 개까지 쌓는다(앱 진입점이 화면 폭에 따라 LayerProvider의 `toast.position`을 고른다). 글은 낱말 사이에서 줄을 바꾼다(`word-break: keep-all`).
- **독립 상세 페이지**: 복합적인 상세 정보는 모달 내부에 억지로 가두지 않고 고유한 라우트(URL)를 가진 독립 페이지로 유지한다.
- **삭제 확인**: 지우는 동작은 모두 짧은 확인 창(shared/ui ConfirmDelete, 휴대폰은 바텀시트)을 거친다. 라벨·댓글처럼 가벼운 것은 삭제 버튼으로 확인하고, 딸린 것이 많거나 되돌릴 수 없는 것(프로젝트, 폴더 등)은 '삭제'를 입력해야 삭제 버튼이 켜진다(`isTyped`). 삭제는 드러난 버튼보다 편집 옆 더보기 메뉴에 둔다.
- **모바일 뒤로가기**: 화면 크기와 관계없이 연 다이얼로그·바텀시트·서랍은 브라우저 뒤로가기(브라우저 뒤로 버튼, 안드로이드 뒤로 버튼, iOS 가장자리 밀기)로 맨 위의 것 하나만 닫고 화면은 떠나지 않는다. 앱 시작 때 한 번 설치하는 shared/lib/back-close가 열린 `<dialog>`를 지켜보며 겹겹이 연 순서대로 쌓고, 열 때마다 표식을 단 기록 항목을 브라우저의 원래 pushState로 더한다. 브라우저는 창의 popstate 리스너를 더한 순서대로 부르므로, 이 장치는 `app/entry.tsx`의 첫 import(`app/back-close.ts`)로 라우터가 이동 기록을 만들기 전에 설치한다. 그래서 뒤로가기를 라우터보다 먼저 받아 맨 위 오버레이에 닫기 요청(`cancel`)을 보내고, 버튼으로 닫히면 그 항목을 `history.back()`으로 거둔다. 라우터는 이 항목을 보지 않으므로 목록의 읽은 조각이 그대로 남는다. 각 화면은 따로 할 일이 없다. 다만 대화상자에서 끝낸 작업이 화면을 옮기면(삭제 뒤 목록으로 가기) 대화상자를 먼저 닫아 그 기록 항목을 거둔 뒤(`afterOverlayClose`) 옮긴다. 먼저 옮기면 뒤로 가는 이동이 대화상자의 항목에서 끝나 대화상자와 화면이 그대로 남는다. 지운 항목의 상세는 다시 읽지 않는다(없다는 응답만 온다).
- **URL 기반 오버레이 주의점**: 작성 폼이나 상세 보기가 URL SearchParams에 바인딩된 경우, 브라우저 직접 링크 진입, 뒤로가기, 새로고침 시 이중 오버레이가 생성되거나 배경이 꼬이지 않도록 라우터 수명주기를 철저히 제어한다.

## 5. 뷰포트 안정성 및 웹 접근성

- **포커스 및 스크롤 잠금**: Astryx 오버레이 컴포넌트가 제공하는 포커스 트랩(Focus Trap)과 배경 스크롤 잠금(Scroll Lock) 계약을 충실히 준수한다.
- **모바일 Safe Area 및 가상 키보드**: 모바일 환경에서 홈 인디케이터나 가상 키보드가 활성화될 때, 폼 제출 및 닫기 버튼이 가려지지 않도록 충분한 안전 패딩(`safe-area-inset-bottom`)을 확보한다. 키보드 위치는 `visualViewport`로 따르고(widgets/app-shell의 model/form-page), 뷰포트 메타의 `interactive-widget`은 쓰지 않는다. 동작 줄은 `position: fixed`로 따로 띄우지 않고 본문 카드 바닥에 붙여(`sticky`) 셸이 보이는 화면에 맞춰 줄어들 때 함께 올라오게 한다.
- **콘텐츠 넘침(Overflow) 처리**: 긴 테이블이나 코드 블록, 칸반 보드의 가로 넘침은 전체 페이지 뷰포트를 흔들지 않고, 콘텐츠 영역 내부에서 자체 스크롤로 안전하게 격리 처리한다. 뷰포트 최상위에 `overflow: hidden`을 무분별하게 적용하여 중요 기능을 화면 밖으로 잘라내는 행위를 금지한다.
- **상대 단위 지원**: 브라우저 확대 및 텍스트 크기 조절 환경에 유연하게 대응할 수 있도록 폰트와 간격에 `rem` 단위와 디자인 토큰을 철저히 적용한다.

## 순서·위치 변경 인터랙션

- 메뉴 구성, 프로젝트 목록, 매뉴얼의 섹션·페이지, 뷰, 라벨·유형·워크플로처럼 사용자가 순서를 지정하는 UI는 손잡이로 드래그 앤 드롭한다. 새 화면을 만들기 전에 `client/src/shared/lib/row-reorder/useRowReorder.ts`와 기존 `ViewOrderDialog.tsx`를 확인하고 재사용한다. 위·아래 버튼이나 메뉴만으로 순서를 바꾸는 구현을 추가하지 않는다.
- 기존 드래그가 있는 보드·리소스·본문 첨부는 동작을 유지한다. 검색·필터·부분 조회로 전체 순서가 안 보이거나 권한이 없으면 순서 변경을 제공하지 않는다. 단순 이름순·최근순 정렬, 날짜/역할 값 선택에 억지로 드래그를 붙이지 않는다.
- 마우스·터치 손잡이, 이동 자리 표시, Esc 취소, Alt+↑/↓ 키보드 이동, 초점 유지·읽기 안내를 함께 제공한다. 매뉴얼처럼 그룹이 있으면 빈 그룹으로의 이동도 다룬다. 키보드용 그룹 선택은 대안으로 유지할 수 있다.
- 초안 대화상자는 드롭 후에도 저장을 눌러 확정하며 취소하면 원본을 유지한다. 즉시 저장 목록은 실패 시 저장된 순서로 되돌린다. 저장 중에는 순서를 다시 바꾸지 못하게 하거나 기존 공통 직렬 저장 처리를 따른다.
- 완료 전 새로 만든 순서 변경 영역 전체를 목록으로 점검하고, 실제 드래그·키보드·취소·저장 후 재진입을 확인한다. 모바일은 손잡이와 페이지 스크롤이 충돌하지 않는지 확인한다. `node scripts/check-reorder-ui.mjs`는 위·아래 버튼만 남기는 회귀를 검사하며, 실제 드래그 동작 검증을 대신하지 않는다.


### 행 리스트의 제목과 설명

프로젝트처럼 항목의 이름과 설명을 함께 읽는 목록은 공통 `ItemList`/`ItemRow`를 사용한다. 설명은 `ItemRow.description`으로 제목 바로 아래에 보조 색상·작은 글자로 배치한다. 설명을 오른쪽 메타 열로 옮기거나 테이블 열 배치를 그대로 복제하지 않는다. 오른쪽 메타에는 키·날짜 등 짧은 속성을 두고 즐겨찾기·더보기는 끝 동작으로 둔다. 설명이 없으면 빈 설명 줄을 만들지 않으며, 긴 설명은 말줄임한다. 드래그 손잡이와 마크는 제목·설명 묶음 옆에 정렬한다. 데스크톱과 모바일에서 제목·설명·메타의 읽는 순서를 확인한다.


리스트로 전환할 때는 행만 교체하지 않는다. 설명이 있는 항목과 없는 항목의 행 높이를 같은 화면 크기에서 통일하고, 길어진 텍스트는 말줄임한다. 공통 `ListSummary` 또는 `ListMore`로 건수·다음 페이지를 표시하고, 목록 아래 남은 공간은 `ListFill`의 공통 점선 배경으로 채운다. API에 전체 건수가 없으면 일부 조회 결과를 전체 건수인 것처럼 표시하지 않는다. 표와 리스트 전환의 완료 기준에는 헤더·도구·행·행 끝 동작·하단 건수·배경·빈 상태·모바일 검증을 모두 포함한다.


### 읽기 화면의 스크롤과 공통 레이아웃

- `PageFrame chrome="header"`는 목록용이다. `isDetail`·`headerContent`·`fillsContent`로 본문 내부 스크롤을 소유하는 읽기 화면에는 같은 모드를 적용하지 않는다. 목록과 읽기를 같은 라우트에서 전환하면 `ManualPreview`처럼 PageFrame 모드도 분리한다.
- 매뉴얼 읽기는 바깥 페이지의 스크롤을 고정하고 본문만 이동한다. 왼쪽 탐색 목록은 독립 스크롤, 오른쪽 목차는 본문을 내리는 동안 상단에 유지한다. 긴 실제 본문에서 바깥 scrollTop, 메뉴 위치, 본문 scrollTop과 목차 클릭 이동을 함께 확인한다.
- `useFillRoom`은 ref가 달린 DOM이 마운트된 뒤 측정한다. RequestBoundary가 자식을 나중에 그리면 `ScheduleCalendar`처럼 측정 훅도 그 자식에 둔다. 로딩 뒤 첫 진입과 새로고침에서 남은 높이를 채우는지 확인한다.
- 멤버처럼 행마다 동작이 있는 목록은 데스크톱 표·모바일 행 모두 같은 더보기를 연결한다. 공용 `features/member-actions`의 권한/확인창을 재사용하고 역할·참여 프로젝트·프로젝트 제외·워크스페이스 내보내기의 범위를 구분한다.
- 공통 필터 콜백은 바뀐 키만 줄 수 있다. 존재하는 키만 URL에 반영해 다른 활성 필터를 지우지 않는다. 복합 필터와 새로고침 유지를 검증한다.

## 1. Astryx CLI 및 개발 워크플로우

화면을 구현하기 전에 프로젝트에 설치된 Astryx CLI(`npm run astryx --prefix client -- <명령>` 또는 `client/`에서 `npx astryx <명령>`)를 활용하여 공식 레이아웃, 템플릿 구조 및 컴포넌트 인터페이스(props)를 확인하고 구현을 시작한다. 에이전트 컨텍스트 절약을 위해 조회 명령에는 `--dense` 플래그를 붙인다.

```sh
# 1. 지정한 화면 설명에 적합한 컴포넌트 조합(page + block + component) 및 플레이북 확인 (인자 없이 실행 시 전체 워크플로우 출력)
npm run astryx --prefix client -- build "구현할 화면"

# 2. 표준 템플릿·블록 목록 및 골격 구조 확인
npm run astryx --prefix client -- template --list
npm run astryx --prefix client -- template <템플릿명> --skeleton

# 3. 특정 컴포넌트의 상세 props 인터페이스 및 예제 확인 (--dense로 토큰 절약 출력)
npm run astryx --prefix client -- component <컴포넌트명> --dense
npm run astryx --prefix client -- component --list

# 4. 컴포넌트·훅·문서·템플릿·블록 통합 검색
npm run astryx --prefix client -- search "<키워드>"

# 5. 공식 레퍼런스 문서 확인 (주요 토픽: layout, styling, tokens, forms, overlays, patterns, principles, data-fetching, routing, theming, accessibility, icons, i18n, testing, typescript, working-with-ai)
npm run astryx --prefix client -- docs layout --dense
npm run astryx --prefix client -- docs tokens --dense
```

- **버전 호환성 확인**: 각 명령어는 독립적으로 실행하며, 프로젝트에 설치된 Astryx 패키지 버전에서 해당 명령어와 옵션이 정상 지원되는지 사전에 확인한다.
- **완료 전 자기 점검(SELF-CHECK)**: 코드 작성을 마친 뒤 파일을 다시 읽고, 레이아웃용 원시 `<div>`/`<span>`, 하드코딩된 색상·크기(`#hex`, `16px`), 추측으로 적은 prop이 남아 있지 않은지 확인한다(`npm run lint:components --prefix client` 통과 필수). 컴포넌트나 prop이 불확실하면 추측하지 말고 `npm run astryx --prefix client -- component <Name> --dense` 또는 `search`로 확인한다.

## 2. 레이아웃 및 디자인 토큰 체계

### 기본 레이아웃 컴포넌트 우선
- 뷰포트 및 내부 배치는 Astryx가 제공하는 `Layout`, `VStack`, `HStack`과 컴포넌트 자체 내장 props(여백, 정렬 등)를 최우선으로 활용한다.
- 임의의 인라인 스타일이나 커스텀 CSS 작성은 지양하며, 커스텀 스타일이 불가피한 경우 색상, 간격, 테두리 반경(radius) 등 시스템 공통 토큰 변수를 참조한다. 색·크기는 하드코딩하지 않는다.

### 전역 스타일 및 프로바이더 조립
- **전역 스타일**: 브라우저 스타일 초기화(CSS Reset), 웹 폰트, `astryx.css`, 테마 변수는 `app/styles/index.css` 한곳에서 통합 로드한다. 기본 테마는 `@astryxdesign/theme-stone`이다.
- **글꼴**: 본문과 제목은 Pretendard Variable(npm `pretendard`의 동적 서브셋, 한글·영문 모두), 고정폭이 필요한 곳(업무 키, 커밋 해시, 코드)은 JetBrains Mono Variable(`@fontsource-variable/jetbrains-mono`)을 앱에 실어 기기마다 같은 모양으로 보인다. 테마가 `--font-family-body`·`--font-family-heading`·`--font-family-code`로 이름을 대고, 테마 밖(body)도 같은 글꼴 목록을 쓴다. 시스템 글꼴은 불러오는 동안의 대체로만 둔다.
- **최상위 프로바이더**: 레이어 중첩을 관리하는 `LayerProvider`와 다국어 처리를 위한 `InternationalizationProvider`는 앱 진입점(`app/entry.tsx`)에서 단 1회 조립한다.

## 3. 데이터 표현 컴포넌트 표준

데이터의 밀도와 성격에 부합하는 적합한 시각적 컴포넌트를 사용한다.

| 데이터 유형 | 권장 컴포넌트 | 표현 목적 |
| :--- | :--- | :--- |
| **고밀도 테이블형 데이터** | `Table` 또는 `List`/`Item` | 다량의 정형화된 레코드 비교 및 정렬 |
| **독립된 맥락 묶음** | `Card` | 특정 엔티티의 정보 요약 및 작업 그룹화 |
| **도메인 상태 표시** | `StatusDot` 또는 `StatusToken`(shared/ui) | 업무 상태, 결정 상태(제안/확정/대체됨) 등 상태 코드의 직관적 인지. 상태는 모서리가 완전히 둥근 알약 모양 `StatusToken`으로 보이고, 라벨·이름표·정본 종류(docx / md / Git)·트리거 유형은 `Token`·`Badge`를 쓴다 |
| **단순 건수 및 카운트** | `Badge` | 미확인 알림 수, 탭별 항목 수 등 정량적 수치 표현 |

- **무분별한 래퍼 생성 금지**: 동일한 props를 단순 전달하기만 하는 껍데기 래퍼 컴포넌트를 기계적으로 양산하지 않는다. 반응형 정책이 결합되거나 프로젝트 공통 규칙이 부여된 경우에 한해서만 `shared/ui`로 승격 추출한다.

### 입력 필드

- 글을 적는 칸(`TextInput`·`TextArea`·`NumberInput`·`DateField`)은 모두 `placeholder`로 적을 내용의 예시(`예: 결제 모듈 개편`)나 무엇을 적을지(`바꾸는 이유를 적어 주세요`)를 보인다. 날짜는 `YYYY-MM-DD`다. 값이 비어 있을 수 있는 `Selector`도 `placeholder`로 고르라고 알린다.
- 정해진 몇 가지에서 고르는 칸은 Astryx `Selector`, 이름처럼 긴 목록에서 찾아 고르는 칸은 `Typeahead`(콤보박스), 날짜 하나는 shared/ui의 `DateField`, 기간은 `DateRangeInput`을 쓴다. 네이티브 `select`와 `input type="date"`는 쓰지 않는다.
- `DateField`는 화면 폭으로 모양을 정한다. 데스크톱(64rem 이상)은 날짜를 적는 칸과 달력 팝오버(오늘·지우기), 모바일은 Astryx `DateInput`(`nativePicker="never"`)의 바텀시트 달력이다. Astryx `DateInput`을 직접 쓰지 않는다. 주 입력이 터치인 노트북에서 데스크톱 폭에도 브라우저 날짜 입력이나 바텀시트가 뜨기 때문이다. 달력을 늘 보여야 하는 양식은 `Calendar`를 화면에 둔다.
- 정해진 간격에서 고르는 시각 하나는 shared/ui의 `TimeField`를 쓰고, `DateField`처럼 화면 폭으로 모양을 정한다. 데스크톱은 칸에 적거나(`1430`·`9시 30분`·`오후 2시`) 칸 아래로 펼친 `step`분 간격 목록에서 고르는 콤보박스다. 모바일은 읽기 전용 칸이라 키보드가 올라오지 않고, 누르거나 Enter·Space·화살표로 바텀시트를 연다. 시트는 칸 이름 아래 48px 줄의 시각 목록이고, 고른 시각(없으면 그다음 시각)을 가운데 두고 초점을 준다. 화살표·Home·End로 옮기고 누르거나 Enter로 고르면 닫히며, Escape·밀어 내리기·바깥 누름은 바꾸지 않고 닫는다. 닫히면 초점이 칸으로 돌아간다. `from`(같은 날 종료 시각의 시작)을 주면 두 모양 모두 시작 뒤 시각부터 각 길이(30분, 1시간…)를 함께 보이고 23:59로 끝난다. 분 단위로 자유롭게 적는 시각은 Astryx `TimeInput`이다.
- 모바일(`MOBILE_QUERY`)에서는 글을 적거나 고르는 칸(`TextInput`·`TextArea`·`NumberInput`·`Selector`·`MultiSelector`·`Typeahead`·`DateInput`·`DateRangeInput`·`TimeInput`·`InputGroup`)과 `SegmentedControl`, 양식의 동작 줄(`data-action-row`) 버튼이 손가락으로 누르는 크기다. 높이는 48px(`SegmentedControl` 항목은 트랙 안쪽 44px), 글자는 16px이고, 16px보다 작으면 iOS가 입력할 때 화면을 확대한다. 크기는 페이지마다 `size`로 주지 않고 `app/styles/index.css`가 Astryx 컨트롤의 고정 클래스(`astryx-text-input` 등)에 `--size-element-*`·`--text-*-size`를 다시 정한다. 데스크톱은 Astryx 크기 그대로다. 공통 `Surface`·`SidePanel`의 바닥 줄과 `ListingFooter`는 `data-action-row`를 이미 달고 있고, 페이지가 직접 그리는 저장·취소 줄은 그 줄에 `data-action-row`를 단다. 목록 도구 줄의 버튼도 모바일에서 48px 검색 칸과 같은 높이다.
- 예외는 로그인의 이메일과 인증 코드(메일이 켜졌을 때의 OTP)다. Astryx `TextInput`에는 자동 완성·숫자 키패드 속성이 없어 네이티브 `input`을 쓰며, 이때도 `placeholder`를 둔다.

### 빈 상태·찾을 수 없음·오류 화면

페이지 안의 구역은 큰 제목(`Heading level={2}`) 대신 shared/ui의 `SectionHeader`로 나눈다. 구역 이름은 작고 옅은 이름표(13px, 600, 보조 글자색)이고 선은 긋지 않으며, 구역 사이는 페이지 간격으로 나누고, 구역의 동작은 같은 줄 끝에 둔다. 동작이 있든 없든 높이가 같아 내용이 같은 거리에서 시작한다. 페이지 제목만이 제목급 글자다. 스크린 리더에는 여전히 2단계 제목이다.

보여 줄 것이 없는 화면과 영역은 shared/ui의 `PageState`로 그린다. Astryx `EmptyState` 위에 상황(`kind`)별 모양을 정한 것이며, 제목은 무엇이 없는지 보통 굵기(500)로 쓴다. 모든 빈 상태는 설명에 다음에 무엇이 일어나는지나 할 일을 쓰고, 그 화면에서 할 수 있는 동작(새로 만들기, 등록, 조건 지우기)이 있으면 `actions`에 둔다. 내용은 영역 가운데가 아니라 위쪽에 두어 짧은 안내 아래로 빈칸이 크게 남지 않게 한다. 상황별 그림은 아직 정하지 않았다(SKILL.md "BIT에서 정할 것"). 그림을 붙이더라도 장식(`aria-hidden`)이며 뜻은 제목·설명이 전한다.

다른 내용 없이 상태만 있는 화면에서는 `PageState`가 스스로 카드까지 올라가며 각 상자 아래에 남은 높이를 재어(`useFillRoom`) 그만큼 늘어나고, 묶음을 그 가운데에 둔다. 페이지가 상태를 몇 겹의 상자로 감싸든 페이지마다 높이를 맞추지 않는다. 다른 내용 아래의 `isCompact`는 그 내용 바로 밑에 둔다. 로딩, 기존 내용이 있을 때의 재조회 실패, 401·403, 아직 만들지 않은 기능 안내에는 오류 상태를 쓰지 않는다.

| 상황 | `kind` | 크기 |
| :--- | :--- | :--- |
| 화면의 목록이 비었다 | `empty` | 기본 |
| 검색어·필터에 맞는 것이 없다 | `search` | 기본 |
| 화면 안의 한 영역이 비었다 | `empty` | `isCompact` |
| 없는 주소나 없는 대상이다(`RequestBoundary`가 받은 404와 경로 값 형식 오류 포함, 페이지의 뒤로 링크를 주 버튼으로) | `not-found` | 기본 |
| 조회가 실패했다(`RequestBoundary`, 라우트 오류) | `error` | 기본 |

홈 카드처럼 좁은 칸 안의 빈 결과는 한 줄 안내로 둔다.

## 4. 리치 콘텐츠 및 파일 업로드 처리

### 마크다운 렌더링
- **데이터 계약**: 마크다운 데이터는 HTML로 변환하여 보관하지 않고, 원문(Markdown Raw Text) 계약을 유지하여 저장하고 송수신한다.
- **편집기**: 마크다운을 적는 칸(업무·결정·세션 본문, 댓글)은 `MarkdownEditor`(`shared/ui/markdown-editor`, Tiptap)를 쓴다(D-076). `TextArea`로 적지 않는다. 값은 마크다운 원문이고 `onChange`로 돌려받는다. 페이지에 그대로 놓는 본문은 `variant="bare"`, 상자에 담는 칸(댓글, 양식의 설명)은 `variant="field"`다. Ctrl(⌘)+Enter로 보내는 칸은 `onSubmit`을 준다.
- **뷰어**: 읽기 전용 본문은 같은 스키마의 `MarkdownView`로 그려 편집할 때와 읽을 때 모양이 같다(D-076). 산출물의 변환 텍스트·Git md 정본처럼 BIT가 쓰지 않는 긴 문서도 같은 뷰어를 쓴다.
- **문서 편집기는 범위 밖**: 협업 편집·버전·위키 같은 문서 편집기는 1차 범위 밖이다.

### 파일 업로드 수명주기
- **선택기 UI**: 파일 업로드는 shared/ui의 공통 컴포넌트 `useFileUploader`·`FileUploader`로 한다. 엔진은 Uppy 코어와 S3 플러그인을 화면 없이 쓰고(서버의 사전 서명 PUT → 확정 흐름, `docs/conventions.md` 4절), 첨부창은 Astryx 컴포넌트와 토큰으로 그린다. Uppy Dashboard는 쓰지 않는다.
- **사진 보기**: 사진을 크게 보는 화면은 shared/ui의 `ImageViewer`(yet-another-react-lightbox)로 통일한다.
- **사진이 나타나는 방식**: 화면에 그리는 사진(프로필, 첨부 썸네일)은 업로드 때 잰 대표색(`dominantColor`)으로 자리를 먼저 칠해 두고, 사진이 도착하면 그 위로 서서히 나타나게 한다([화면 이동과 로딩](BEzXrFTF1X.md) "사진 자리"). 이미 받아 둔 사진(shared/lib/image-traits의 `isImageAtHand`·`noteImageArrived`)은 효과 없이 바로 보인다. 사진이 바뀌면 `<img>`를 주소로 새로 만들어(`key`) 옛 사진이 페이드를 대신하지 않게 하고, 몇 분마다 새로 발급되는 열람 주소는 이미 보인 사진을 다시 흐리지 않는다. 동작 줄이기 설정이면 바로 보인다.
- **임시 자원 관리**: 브라우저 로컬 미리보기 단계와 서버 저장 완료 단계를 엄격히 구분한다. 미리보기를 위해 발급한 `Object URL`(`URL.createObjectURL`)은 메모리 누수를 방지하기 위해 뷰가 언마운트되거나 업로드가 완료되는 즉시 명시적으로 해제(`URL.revokeObjectURL`)한다.
- **라이브러리 검증**: 외부 라이브러리 도입 시 실제 릴리즈 버전, 번들 크기, 보안 취약점 및 오픈소스 라이선스를 사전에 확인한다.

## 5. 웹 접근성 및 제품 자산 관리

### 접근성(a11y) 필수 체크리스트
- **아이콘 버튼**: 텍스트 없이 아이콘만 노출되는 액션 버튼은 스크린 리더를 위한 명확한 접근성 이름(`aria-label`)을 선언한다.
- **오버레이 제목**: 다이얼로그와 바텀시트는 고유한 제목 요소(`aria-labelledby`)를 반드시 연결한다.
- **키보드 내비게이션**: Tab 키를 통한 순차 포커스 이동, Escape 키를 통한 닫기, 그리고 오버레이가 닫힌 후 직전 포커스 위치로 안전하게 복귀하는지 검증한다.
- **사용자 환경 적응**: 긴 한국어 문장의 어색한 줄바꿈 방지, 라이트/다크 테마 환경에서의 명도 대비 기준 충족, 모바일 터치 타깃 크기(최소 44x44px)를 철저히 검증한다.

### 제품 자산 관리
- **로고 자산**: 로고나 심볼은 독립 파일 리소스로 분리하여 로드하며, 수백 라인에 달하는 복잡한 인라인 SVG 코드를 DOM 구조에 직접 삽입하지 않는다. 웹의 로고는 독립 SVG 파일을 CSS 마스크로 읽고 `--color-text-primary`를 칠해 앱의 팔레트·모드를 따른다.
- **아이콘과 설치**: 파비콘(`favicon-16.png`, `favicon-32.png`, `icon-192.png`)·iOS 아이콘(`icon-apple-touch.png`)·PWA 아이콘(`icon-512.png`, `icon-maskable-512.png`)과 매니페스트(`manifest.webmanifest`)는 `client/public/`에 둔다. 아이콘에는 투명한 곳을 두지 않는다. 투명하면 어두운 탭·홈 화면에서 글자가 배경에 묻히므로 기본 팔레트 Stone의 밝은 바탕(`#F3F3F5`)에 먹색(`#25252A`) 단색 심볼을 합친 불투명 PNG로 둔다. 확정된 곡선형 심볼 원본은 `client/src/shared/ui/brand/bit-symbol.svg`이며 가운데 i의 점도 심볼과 같은 단색이다. `npm run brand:generate --prefix client`가 이 원본으로 favicon SVG/ICO/16·32·64px PNG, Apple touch 180px, PWA 192·512px와 maskable 512px 및 manifest를 생성한다. 아이콘 배경은 전체 정사각형이며 별도 라운드나 흰 외부 여백을 넣지 않는다. maskable 원본의 축소·안전 영역은 유지하고 OS 마스크를 존중한다. 원본을 새로 그리거나 이전 로고 생성기로 교체하지 않는다. 재생성 후 diff와 실제 PNG 크기·불투명 배경을 확인한다.
- **제품 이름**: 화면의 제품 이름은 `PRODUCT_NAME`(`'BIT'`, `shared/config`) 상수 하나를 쓰고, 문구에 직접 적지 않는다. 정식 제품명이 정해지면 이 값만 바꾼다(D-024).


필터 동작은 Solar `tuning-2-linear`, 정렬 동작은 `list-vertical-linear`로 통일한다. 앱에서는 `NavIcon`의 `filter`/`sort` 이름을 쓰고, 원본 매핑 `client/scripts/generate-icons.mjs`를 고친 뒤 재생성한다. 생성된 `solar-icons.ts`를 손으로 고치지 않는다. 정렬을 포함한 표시 메뉴의 진입 아이콘도 `sort`를 사용하고, 오름차순·내림차순 방향 아이콘은 각각의 의미를 유지한다.


도메인 메뉴 아이콘은 `manuals` → notebook-2-linear, `resources` → folder-with-files-linear, `work-items`(이슈)·`tasks`(작업) → notes-linear, `roles` → shield-star-linear, `projects` → blocks-linear, `members` → file-smile-linear로 통일한다. 사용자 지정 프로젝트 마크는 덮어쓰지 않는다.


가로·세로 더보기는 외곽선 대신 채워진 Solar Bold Duotone을 사용한다. `more`는 menu-dots-bold-duotone, `more-vertical`은 menu-dots-vertical-bold-duotone이다. 이 둘만 기본 Linear 스타일의 예외로 아이콘 생성기에 명시한다. 순서 변경 손잡이(grip)는 더보기가 아니므로 변경하지 않는다.
