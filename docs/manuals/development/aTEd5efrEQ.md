# 업무·브랜치·커밋·리뷰 연결하기

BIT 업무는 변경의 이유와 남은 일을 보여 주는 계획 단위입니다. 메시지나 세션 하나마다 새 업무를 만들지 않고 같은 기능의 후속 수정은 기존 업무에서 이어 갑니다.

## 시작과 변경

1. 프로젝트와 업무를 찾고 `get_work_item_context`로 본문·이전 결정·댓글을 읽습니다.
2. 지금 맡은 일은 담당자와 시작일을 확인하고 진행 중으로 옮깁니다.
3. 현재 작업 트리와 관련 파일의 변경을 확인합니다. 다른 사람의 변경을 되돌리거나 함께 커밋하지 않습니다.
4. 프로젝트 규칙과 해당 영역 스킬을 읽고 변경합니다.
5. 중요한 판단과 결과·검증·미실행 범위를 같은 업무에 남깁니다.

## 이름으로 연결

업무 키를 먼저 발급받은 뒤 브랜치·커밋·PR에 사용합니다. 프로젝트 지침이나 실행 환경이 브랜치 접두사를 요구하면 그 규칙을 함께 지킵니다. 이 환경에서 새 브랜치를 만든다면 예를 들어 `codex/bit-148-development-manual`처럼 업무 키를 포함할 수 있습니다. 특정 호스트의 접두사를 모든 BIT 사용자에게 강제하지 않습니다.

커밋과 PR 제목에는 `BIT-148`처럼 실제 키를 적습니다. PR 본문의 `Closes #번호`는 저장소 이슈 번호이며 BIT 업무 번호와 무조건 같지 않습니다. 동기화가 켜진 경우 같은 이슈를 양쪽에 따로 만들지 않습니다.

## 리뷰와 완료

리뷰에는 결과 동작·이유·검증·남은 제한을 적습니다. PR로 병합할 변경은 결과 댓글을 남기고 완료 상태는 병합 연동에 맡깁니다. PR 없이 기본 브랜치에 직접 커밋하는 작업은 프로젝트 작업 규칙에 따라 완료 처리합니다. 코드 변경이 아닌 읽기·논의만으로 새 업무를 늘리지 않습니다.

API·스키마·문서가 함께 바뀌는 기능은 계약과 생성물을 같은 검토 단위에서 확인합니다. 릴리스는 따로 완료 업무를 쌓는 대신 태그·Release와 포함된 업무에 버전을 연결합니다.

## 기록의 공개 범위

BIT의 설명·댓글이 연결 저장소 이슈로 복사될 수 있습니다. 토큰·개인정보·내부 운영 설정을 넣지 않습니다. 확정 결정 원본과 업무의 결정 댓글 관계는 [문서 관리](pNDA17FCoQ.md)를 따릅니다.

## 근거와 적용 기준

앱 버전은 server/build.gradle과 client/package.json 기준 0.22.0입니다. 개발 커밋은 출시 버전과 구분합니다. 근거 링크는 현재 체크아웃의 원본이며, 실제 코드 발췌는 공백을 정규화해 대조했습니다. 실행 검사 이력은 BIT-148을 따르며 이 정적 검수는 새 실행/화면 검증을 뜻하지 않습니다.
