이 문서는 시스템 전반의 표준 오류 응답 형식(RFC 9457 Problem Details), 계층별 검증 책임, 보안을 위한 정보 은닉, 클라이언트 오류 처리 및 UI 피드백 원칙을 정의한다.

---

## 1. 표준 오류 응답 형식 (RFC 9457)

모든 API 오류 응답은 RFC 9457 Problem Details 표준 규격을 준수하며, 프로젝트 확장을 통해 일관된 스키마를 제공한다.

### 오류 응답 스키마
```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "입력값 검증에 실패했습니다.",
  "code": "WORKITEM_INVALID_INPUT",
  "traceId": "c8a4f91e-3b2a-4a6d-8f92-5b9e8c4a1234",
  "errors": [
    {
      "field": "title",
      "message": "200자 이하로 입력해 주세요"
    }
  ]
}
```

### 핵심 확장 필드 규약
- **`code`**: 클라이언트가 프로그래밍 방식으로 분기 처리할 수 있는 고유한 기계 판독용 오류 코드다. `<MODULE>_<REASON>` 대문자 스네이크 케이스 형식을 따른다 (예: `AUTH_INVALID_TOKEN`, `WORKITEM_NOT_FOUND`, `DECISION_ALREADY_SUPERSEDED`).
- **`traceId`**: 분산 추적 및 서버 로그 조회를 위한 고유 식별자다.
- **`errors`**: 폼 입력 검증 실패 시 상세 필드 오류 목록을 제공한다.
  - 보안을 위해 클라이언트가 전송한 원본 입력값(Raw Value)은 응답 본문에 다시 포함(Echo)하지 않고 `field`와 `message`만 제공한다.

## 2. 계층별 검증 책임 및 정보 은닉

### 계층별 검증 단계
오류는 발생 지점의 책임에 따라 계층별로 처리한다.
- **DTO 계층**: 필드 형식, 필수값 누락, 문자열 길이, 정규식 등 정적 입력 제약 조건을 검증한다.
- **Application 계층**: 사용자의 실행 권한 및 유스케이스 관점의 엔티티 현재 상태를 검증한다.
- **Domain 계층**: 비즈니스 불변식(Invariant) 및 도메인 엔티티의 상태 전이 규칙을 검증한다.
- **서블릿 필터 및 인증 단계**: 보안 필터 및 인증 단계에서 거부된 요청도 일반 비즈니스 예외와 동일한 Problem Details 형식으로 응답을 통일한다.

### 정보 은닉 및 보안 처리
- 사용자가 속하지 않은 워크스페이스의 프로젝트·업무·결정·세션·산출물·첨부파일처럼 존재 여부 자체를 알려서는 안 되는 자원은 '자원 부재(404 Not Found)'와 '접근 권한 부족(403 Forbidden)'을 외부에 구별하여 노출하지 않는다. 존재를 유추할 수 없도록 일관된 모호화 응답을 반환한다.

## 3. 클라이언트 오류 핸들링 및 UI 피드백

### 공통 오류 가로채기(Interceptor)
- 프론트엔드 HTTP 계층은 표준 오류 응답을 파싱하여 중앙에서 해석한다.
- **세션 만료 (`401 Unauthorized`)**: 전역 인터셉터에서 세션 만료를 감지하여 로그인 경로로 전환하고 캐시를 초기화한다. 단, 로그인 요청 자체에서 비밀번호 불일치 등으로 발생한 401 응답은 인터셉터 처리에서 제외하여 로그인 폼에 정상적으로 실패 메시지를 렌더링한다.

### 경로 값 형식 오류의 찾을 수 없음 처리
- 조회(GET)가 400으로 거절되고 `errors`의 필드 이름이 모두 그 요청의 쿼리에 없으면, 형식에 맞지 않은 값은 경로 값(`{id}` 등)이므로 화면은 그 조회를 404와 같이 찾을 수 없음으로 다룬다(shared/api의 `isNotFound`). 서버는 경로 값 형식 오류를 그 변수 이름으로 `errors`에 담는다. 명령(POST·PUT·DELETE)의 400은 이렇게 다루지 않는다.

### UI 오류 격리 및 수준별 피드백
- **국소화 피드백**: 오류의 성격에 따라 필드 단위(입력란 하단 에러 텍스트), 영역 단위(컴포넌트 Fallback), 라우트 단위(에러 바운더리)로 분리하여 표시한다.
- **셸 보호**: 인증 실패를 제외한 일반 비즈니스 로직 오류나 국소 조회 실패로 인해 애플리케이션 전체 셸(GNB, 사이드바 등)이 언마운트되는 장애를 방지한다.

## 4. 사용자 메시지 및 재시도 분리 원칙

### 메시지 매핑 및 내부 정보 노출 차단
- 사용자에게 표시되는 오류 메시지는 클라이언트가 보유한 `code` 기반의 다국어 매핑을 최우선 적용하고, 안전성이 검증된 서버 `detail` 문구를 보조로 활용한다.
- 서버 내부의 미처리 예외(`500 Internal Server Error`)는 시스템 내부 스택 트레이스나 DB 오류 문구를 절대 노출하지 않으며, 표준 안내 문구와 추적용 `traceId`만 표시한다.
- 프레임워크가 직접 답하는 오류(없는 주소, 허용하지 않는 메서드, 읽을 수 없는 본문·값)는 상태에 맞는 공통 코드(`COMMON_NOT_FOUND` 404, `COMMON_METHOD_NOT_ALLOWED` 405, `COMMON_NOT_ACCEPTABLE` 406, `COMMON_UNSUPPORTED_MEDIA_TYPE` 415, 그 밖의 4xx는 `COMMON_INVALID_REQUEST`)와 그 표준 문구로 답한다. 프레임워크 기본 문구는 보낸 값과 내부 클래스 이름을 담을 수 있어 쓰지 않는다. 형식이 맞지 않는 필드 값(쿼리·경로 값, 본문 안의 날짜 등)은 `errors`에 필드 이름과 '값의 형식이 올바르지 않습니다'만 담고, 빠진 쿼리 값은 '필수 입력값입니다'로 답한다. 본문이 JSON으로 읽히지 않아 가리킬 필드가 없으면 `errors`를 두지 않는다.
- 컨트롤러에 닿기 전에 거절되는 요청도 같은 형식과 `traceId`로 답한다. 쿼리의 퍼센트 인코딩이 깨진 요청(`cursor=%%%%`), 보안 방화벽이 막는 주소(`//`, `;`, `..`), Tomcat이 스스로 거절하는 주소(경로의 `%2F`, 깨진 인코딩)는 400 `COMMON_INVALID_REQUEST`이며 이때도 보낸 이름과 값을 되풀이하지 않는다. 오류 페이지(`/error`)는 컨테이너가 넘긴 오류를 그 상태의 공통 코드로 답하고, 직접 부르면 404 `COMMON_NOT_FOUND`다(`shared/web`의 `ProblemErrorController`, `ProblemErrorReportValve`).
- 입력 제약(Bean Validation) 위반의 `errors[].message`는 검증기 기본 문구 대신 제약마다 정한 한국어 문구로 쓴다(서버 `shared/web`의 `ValidationWords`). 필수값은 '필수 입력값입니다', 길이는 '200자 이하로 입력해 주세요', 이메일은 '유효한 이메일 형식이 아닙니다', 정규식은 '값의 형식이 올바르지 않습니다'처럼 답하고, 표준 제약이 아닌 것은 코드가 애너테이션에 적은 문구를 쓴다. 메서드 검증의 경로에 붙는 메서드·매개변수 이름은 떼고 클라이언트가 보낸 필드 이름만 남긴다.

### 명령과 조회의 재시도 책임 분리
- 데이터 저장(Mutation)이 성공한 후 목록 재조회(Query) 과정에서만 일시적 네트워크 장애가 발생한 경우, 화면에 '조회 재시도' 액션만을 제공한다. 이미 서버에 성공적으로 반영된 데이터 변경 명령을 다시 실행하도록 유도해서는 안 된다.
- 프록시나 게이트웨이 환경에서 API의 404 응답을 500 서버 에러로 변환하거나 SPA의 `index.html`로 잘못 폴백하여 응답을 왜곡하지 않는다.
