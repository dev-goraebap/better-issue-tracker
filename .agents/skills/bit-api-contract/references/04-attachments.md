이 문서는 파일 첨부와 산출물 원본의 모듈 소유권, 사전 서명 URL(Presigned URL) 기반 직접 업로드 워크플로우, 저장소 어댑터, 접근 권한 인가, 파일 삭제 및 가비지 컬렉션(GC), 보안 검증 지침을 정의한다. 테이블은 `docs/06-schema.md` 9절, 저장소 결정은 D-029다.

## 1. 파일 모듈 소유권 및 다형 연결 구조

파일 관련 메타데이터와 영속 데이터는 독립된 `file` 모듈이 전담 소유한다.

### 영속 모델 분리
- **`blob`**: 스토리지에 저장된 원본 파일의 물리적 메타데이터(크기, MIME 타입, 스토리지 키, 체크섬 등).
- **`attachment`**: 비즈니스 업무 엔티티와 파일 Blob 간의 다형 연결(Polymorphic Association) 정보.
- **`pending_upload`**: 사전 서명 URL 발급 이력 및 만료 상태.

### 다형 연결(Polymorphic Link) 규칙
- 업무 엔티티와의 연결은 `owner_type`(예: `work_item`, `comment`), `owner_id`(엔티티 UUID), 그리고 첨부 용도를 나타내는 `name`의 조합으로 식별한다. 순서는 `position`이다.
- 각 업무 모듈은 `file` 모듈의 내부 테이블을 직접 참조하지 않고, `file` 모듈이 공개한 계약 인터페이스(`FileFacade`)를 통해서만 첨부파일을 관리한다.
- `shared/storage`의 저장소 어댑터는 순수한 스토리지 I/O만을 담당하며, BIT 업무의 인가 지식을 포함하지 않는다.

### 산출물 파일
- 산출물 정본과 파생본(텍스트 변환·PDF)은 `attachment`를 거치지 않고 `artifact_version.blob_id`, `artifact_rendition.blob_id`로 `blob`을 직접 가리킨다. 업로드 흐름(2절)과 검증·정리는 같다.
- 1차에는 산출물을 다시 올리면 `current` 버전 행을 덮어쓰고, 이전 blob은 정리 대상이 된다(D-019).
- 작업항목 설명·댓글에 붙는 이미지 등은 `attachment`로 붙인다.

### 본문이 가리키는 파일
- 확정한 첨부는 업로드 id를 그대로 자기 id로 쓴다(`FileFacade.attach`). 그래서 작업항목 설명·결정 본문·세션 요약·댓글 같은 Markdown 본문은 저장하기 전부터 `![이름](attachment:<id>)`(사진)·`[이름](attachment:<id>)`(파일 블록)로 첨부를 가리킨다. 본문을 읽고 바꾸는 서버 도우미는 `io.github.goraebap.bit.module.file.DocumentFiles`(`referencedIn`, `repoint`)다.
- 본문은 첨부의 일부를 가리킬 뿐이고, 건수·용량 한도와 접근 검사는 그대로 첨부로 한다. 본문에서 빠진 첨부를 떼는 것은 화면이 저장할 때 뺄 id로 보낸다.
- 한 첨부를 다른 소유자에게 나눠 줄 때는 `FileFacade.copy`로 같은 blob을 함께 쓰는 새 첨부를 만든다. 첨부를 지울 때 그 blob을 아직 쓰는 다른 첨부가 있으면 blob을 버리지 않고 저장소에서도 지우지 않는다(`discardBlobs`가 실제로 버린 키만 돌려준다).

## 2. 사전 서명 URL 기반 직접 업로드 워크플로우

대용량 파일 전송 시 애플리케이션 서버의 네트워크 대역폭과 메모리 부하를 방지하기 위해, 클라이언트가 스토리지로 직접 전송하는 사전 서명 `PUT` 방식을 채택한다.

### 저장소 어댑터 (D-029)
| 어댑터 | 언제 | 동작 |
| :--- | :--- | :--- |
| **로컬 (기본)** | 저장소 설정이 없을 때. 도커만 띄워도 업로드가 된다 | `LocalObjectStorage`가 데이터 볼륨 폴더(`STORAGE_LOCAL_ROOT`, 로컬 실행 기본 `server/data/files`)에 둔다. 사전 서명 URL은 서버의 `/api/v1/storage`를 가리킨다 |
| **S3 호환** | 접속 주소(`STORAGE_ENDPOINT`) 등을 설정했을 때 | 어댑터 하나로 AWS S3·Cloudflare R2·MinIO를 모두 지원한다. 접속 주소·지역 등 설정만 다르다(R2는 region `auto`) |

- 로컬 어댑터의 URL도 허용한 키·형식·크기와 만료를 HMAC으로 서명하므로 흐름과 화면 코드는 S3 호환 저장소와 같다. `/api/v1/storage`는 브라우저가 서명 URL로만 부르고 생성 타입으로 부르지 않으므로 OpenAPI 문서에 넣지 않는다(`@Hidden`).
- 파일 저장소는 로컬 어댑터가 내장되어 있어 켜진 기능 목록(D-030)에서 항상 켜져 있다. 로컬이면 볼륨 백업은 사용자가 챙긴다. 두 어댑터를 모두 테스트한다.

```
[클라이언트]                     [업무 모듈]              [File 모듈]              [로컬 폴더·S3 호환 스토리지]
     │                                │                       │                              │
     │ 1. 업로드 세션 생성 요청 ───────┼──────────────────────>│                              │
     │    (파일 메타데이터 전달)       │                       │                              │
     │ 2. Presigned PUT URL 반환 <────┼───────────────────────│                              │
     │                                │                       │                              │
     │ 3. 파일 바이너리 직접 PUT ────────────────────────────────────────────────────────────>│
     │                                │                       │                              │
     │ 4. 첨부 확정 요청 ─────────────>│                       │                              │
     │                                │ 5. 권한 검사 & 확정 ──>│ 6. 스토리지 객체 검증        │
     │                                │    (소유권 바인딩)     │<─────────────────────────────│
     │ 7. 확정 완료 응답 <────────────│                       │                              │
```

### 단계별 처리 지침
1. **업로드 세션 발급**: 인증된 사용자가 파일 메타데이터(파일명, 예상 크기 등)를 전달하면, `file` 모듈은 유효기간이 짧게 제한된 사전 서명 `PUT` URL과 필수 전송 헤더를 생성하여 반환한다.
   - *응답 본문 예외*: 이 응답은 클라이언트가 즉시 소비해야 할 URL과 헤더를 포함하므로, 변경 작업의 "본문 없음" 기본 규칙의 명시적 예외로 OpenAPI 스펙에 선언한다.
2. **스토리지 직접 업로드**: 브라우저 클라이언트는 발급받은 URL로 직접 바이너리를 전송한다.
3. **첨부 확정(Confirmation)**:
   - 클라이언트가 업로드 완료 후 소유 업무 모듈(작업항목, 산출물 등)에 첨부 확정을 요청한다.
   - 업무 모듈은 사용자의 업무 권한을 확인한 뒤 `file` 모듈에 최종 바인딩을 요청한다.
   - `file` 모듈은 세션 발급자와 확정 요청자의 일치 여부, 스토리지에 실제 저장된 객체의 실제 크기(Byte)와 MIME 유형을 교차 검증한 후 상태를 영속화한다. 클라이언트가 전송한 MIME 문자열이나 스토리지 키 접두사만을 맹신하지 않는다.

> [!NOTE]
> 바이너리 업로드는 MCP가 아니라 웹·REST로 한다(D-022).

## 3. 다운로드 인가 및 경로 분리

- **서버 중심의 접근 제어**: 첨부파일과 산출물 파일의 조회, 다운로드, 브라우저 미리보기 요청은 반드시 해당 파일을 소유한 업무 모듈의 권한 검증(워크스페이스 멤버십과 역할)을 통과한 후에만 스토리지 접근 URL을 발급한다.
- **IDOR(Insecure Direct Object Reference) 방어**: 클라이언트가 요청 파라미터로 임의의 `owner_type`과 `owner_id`를 전송했다는 사실만으로 파일 접근을 승인해서는 안 된다. 현재 세션 사용자(또는 API 키 주인)가 해당 엔티티에 실제로 접근할 수 있는지 비즈니스 인가를 필수 검증한다.
- **보안 격리**: 비공개 업무 파일(산출물 원본, 첨부)의 서명 경로와, 비인증 사용자에게도 노출되어야 하는 공개 파일이 생긴다면 그 경로는 스토리지 버킷 및 접근 정책을 물리적/논리적으로 완전히 분리한다.

## 4. 삭제 수명주기 및 가비지 컬렉션 (GC)

### 부모 엔티티 삭제 시 처리
- 부모 비즈니스 엔티티가 삭제되면 연관된 첨부 연결(`attachment`)을 해제하고, 실제 스토리지 상의 물리적 객체 삭제 태스크를 영속 큐/이벤트 로그에 기록하여 비동기 처리한다.

### 고아 자원(Orphan Data) 정리
- 다형 연결 구조는 데이터베이스 외래 키(FK) Cascade 제약 조건을 사용할 수 없다.
- 따라서 업로드 세션 발급 후 최종 확정되지 않고 방치된 미완료 업로드(`pending_upload`)와, 부모 연결이 끊어진 고아 Blob 데이터(덮어쓴 산출물의 이전 blob 포함)는 백그라운드 주기 배치 작업을 통해 스토리지와 DB에서 안전하게 영구 제거한다.
- 스토리지 삭제 실패 시 재시도 메커니즘을 적용하여 자원 누수를 방지하며, 삭제된 파일은 복구되거나 재접근할 수 없도록 보장한다.

## 5. 파일 콘텐츠 검증 및 보안 새니타이징

업로드된 파일은 서비스 내에 안전하게 게시되기 전 엄격한 검증 파이프라인을 거쳐야 한다.

### 포맷별 검증 기준
| 파일 포맷 | 필수 검증 및 처리 절차 |
| :--- | :--- |
| **SVG (벡터 이미지)** | 스크립트 실행 위험을 방지하기 위해 `<script>`, `onload`/`onerror` 등 인라인 이벤트 핸들러, 외부 자원 참조, XML 외부 엔티티(XXE)를 완전히 제거하는 화이트리스트 기반 새니타이징(Sanitization)을 거친 후에만 게시를 허용한다. |
| **PNG / JPEG (비트맵)** | 파일 헤더만 확인하지 않고 실제 이미지 디코딩 라이브러리를 통해 파일 손상 여부와 실제 픽셀 해상도를 검증하여 악성 페이로드가 숨겨진 변조 이미지를 차단한다. |

- **미검증 파일 격리**: 유효성 검증을 통과하지 못했거나 처리가 완료되지 않은 원시 파일 객체는 외부에 절대 노출하거나 공개 URL로 제공하지 않는다.
- **텍스트 변환·PDF**: 산출물의 파생본은 트랜잭션 밖 작업이 만들고 `artifact_rendition`의 상태만 갱신한다. 1차 어댑터는 서버 안의 Apache POI + PDFBox(텍스트 변환, D-031)와 HTML 렌더링(PDF, D-032)이라 항상 켜져 있고, `converter`에 어댑터와 버전을 남긴다. 어댑터라 바꿀 수 있다(D-030).
