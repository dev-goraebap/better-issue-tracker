## 1. 명명 규칙 및 파일 분리 표준

### 컴포넌트와 파일의 1:1 대응
- **단일 책임 원칙**: 한 파일에는 오직 하나의 컴포넌트만 정의한다.
- **예외 없는 분리**: 메인 컴포넌트를 보조하는 서브 컴포넌트, Context Provider, 전용 SVG 아이콘, 라우터 연결용 래퍼 컴포넌트도 모두 개별 독립 파일로 분리한다.

### 파일 및 식별자 명명 체계
| 분류 | 명명 규칙 | 예시 |
| :--- | :--- | :--- |
| **컴포넌트 및 파일명** | PascalCase (컴포넌트명과 파일명 일치) | `WorkItemTable.tsx`, `UserAvatar.tsx` |
| **페이지 컴포넌트** | `*Page` 접미사 필수 | `DecisionListPage.tsx`, `ArtifactDetailPage.tsx` |
| **커스텀 훅 (Hook)** | `use*`로 시작하는 camelCase | `useWorkItemFilter.ts`, `useDisclosure.ts` |
| **일반 유틸 및 설정** | kebab-case | `date-utils.ts`, `auth-interceptor.ts` |

## 2. FSD 레이어 배치 및 모듈 경계 규칙

코드 배치는 Feature-Sliced Design(FSD) 계층 구조(`app → pages → widgets → features → entities → shared`)를 엄격히 준수한다. Steiger는 `recommended` 규칙을 쓴다.

### 코드의 기본 배치 위치
- 신규 기능 코드는 해당 기능을 최초로 소비하는 **페이지 내부의 세그먼트(`pages/<그룹>/<페이지명>/api`, `model`, `ui`)에 우선 배치**하는 것을 기본으로 한다.

### 상위 레이어 추출 기준
- **`features`**: 2개 이상의 독립적인 화면에서 실제로 재사용되는 '사용자 인터랙션 및 비즈니스 액션'만 추출한다.
- **`entities`**: 2개 이상의 독립적인 화면에서 실제로 재사용되는 '도메인 모델, 타입 정의, 조회 로직'만 추출한다.
- **`widgets`**: 헤더, 사이드바처럼 독립적이면서 복합적인 기능을 수행하는 대형 UI 블록만 추출한다.
- **추출 금지 사유**:
  - `app` 레이어의 라우트 로더(loader)나 전역 Provider에서 참조된다는 이유만으로 다중 화면 재사용으로 간주하지 않는다.
  - 미래의 막연한 재사용 가능성이나 단순 파일 길이 증가만을 이유로 성급하게 상위 레이어로 승격하지 않는다.

### 페이지 그룹
`pages`는 아래 네 그룹으로만 나눈다. 그룹 폴더에는 코드를 두지 않고 슬라이스만 둔다. 한 층·그룹의 슬라이스는 Steiger 기준(20개)을 넘기지 않으며, 닿으면 메뉴의 묶음과 같은 이름으로 하위 그룹을 둔다.

| 그룹 | 페이지 | 메뉴 기준 |
| :--- | :--- | :--- |
| `pages/workspace/<페이지명>` | 홈, Inbox, My Tasks, Members, 문서함 | 워크스페이스 메뉴 |
| `pages/project/<페이지명>` | 보드, 백로그, 타임라인, 결정, 산출물, 세션·회의 | 프로젝트 메뉴 |
| `pages/settings/<페이지명>` | account, workspace, project, admin | 설정 |
| `pages/entry/<페이지명>` | 로그인, 시작 안내(onboarding) | 앱 셸 밖의 진입 화면 |

목록과 상세·작성은 각각 슬라이스다(예: `pages/project/decisions`, `pages/project/decision-detail`).

### 슬라이스 캡슐화 및 의존성 규칙
- **공개 API(Public API) 원칙**: 슬라이스 외부에서는 반드시 슬라이스 루트의 공개 `index.ts`만을 통해 export된 요소만 import한다. 슬라이스 내부 깊숙한 파일 경로로의 직접 접근을 금지한다.
- **교차 참조 금지**: 동일한 레이어에 속한 다른 슬라이스 간의 상호 참조(Cross-slice import)를 엄격히 금지한다.
- **임의의 그룹 폴더 금지**: 위 네 페이지 그룹 외에 모호한 공유 목적의 그룹 폴더를 임의로 신설하지 않는다.
- **슬라이스 없는 레이어**: `app`과 `shared` 레이어는 슬라이스를 두지 않고, 역할별 세그먼트(`ui`, `lib`, `config` 등)로 직접 구성한다.

## 3. 상태 관리 및 렌더링 순수성

### 파생 상태(Derived State)의 올바른 처리
- 리액트의 렌더링 함수는 항상 순수 함수처럼 동작해야 한다.
- 부모 props나 기존 state로부터 계산해낼 수 있는 파생값은 `useState`에 복제하지 않는다. `useEffect`로 상태를 복제하고 동기화하는 안티패턴을 금지하며, 렌더링 계산 도중 직접 연산하거나 메모이제이션을 적용한다.

### 부수 효과(Side Effect)의 엄격한 격리
- **사용자 명령 분리**: 사용자의 클릭이나 입력에 따른 상태 변경 및 API 호출은 `useEffect`가 아닌 이벤트 핸들러 또는 TanStack Query의 `mutation` 실행부에서 직접 처리한다.
- **`useEffect` 사용 한정**: Effect는 외부 시스템 구독, 타이머 등록, 브라우저 DOM API와의 필수적인 동기화 목적으로만 최소한으로 사용하며, 구독 해제나 타이머 취소를 담당하는 정리(Cleanup) 함수를 반드시 반환한다.
- **서버 상태와 입력 초안 분리**: TanStack Query가 반환하는 서버 데이터는 순수 읽기 전용(Read-only)으로 간주한다. 사용자가 입력 및 수정 중인 폼 데이터는 별도의 로컬 초안 상태(Draft State)로 격리하여 유지한다.

## 4. 성능 최적화 및 런타임 안정성

### 훅 최적화의 의도적 사용
- `useMemo`와 `useCallback`은 실제로 브라우저 프로파일러를 통해 계산 비용이 크다고 측정된 경우나, 자식 컴포넌트의 props 참조 안정성이 엄격히 요구되는 경우에 한해 근거를 두고 적용한다.
- React Compiler 활성화를 당연시하여 기본적인 의존성 배열이나 렌더링 비용 관리를 소홀히 하지 않는다.

### `React.StrictMode` 정합성
- 개발 환경의 `React.StrictMode`로 인해 컴포넌트가 2회 반복 마운트/렌더링될 때 발생하는 문제는 플래그 변수로 억제하지 않는다.
- 부수 효과의 중복 실행 방지 및 적절한 클린업 함수 구현을 통해 수명주기 책임을 올바르게 교정한다.
